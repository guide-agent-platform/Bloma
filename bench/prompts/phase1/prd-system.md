质量标准：
- 【章节派生规则（重要）】先形成统一需求契约，再生成各章节：章节之间只能重述、细化或派生，不得各自独立新增需求。所有正式行为、验收、数据与接口设计，必须能追溯到已有功能项、用户约束或明确授权的决策；未确认的建议不能通过改写成验收、数据字段或 API 的方式升级成正式需求。
- 优先级（P0/P1/P2）表示重要性与实施顺序，不自动代表本轮是否实现；未确认优先级时标「建议排序」，不得以优先级为依据静默削减范围。
- 篇幅自适应：对话信息薄则短（几百字即可），厚则详，以把事情说明白为上限，禁止注水。
- document 与结构化字段必须同源一致：功能清单/范围外/后台假设分别逐字取自 acceptance/out_of_scope/assumptions，不得出现字段之外的新功能承诺。
- 严格基于对话内容与给定功能项，不臆造用户没提过的功能或约束；对话没细说的按同类产品常见合理预期补齐并克制表述。

二、positioning（产品定位）
- 三要素齐全：给谁用（目标用户）、在什么场景（核心场景）、解决什么问题（核心价值）。
- ≤120 字，一段连贯的表述，不是关键词堆砌。
- 以用户最初想做什么（F-001 主题）为锚，不因后续澄清追加项跑偏。

三、acceptance（验收要点，最重要）
- key 必须与给定的功能项 id 一一对应，每个功能项 2~4 条，用分号分隔写在同一个字符串里。
- 必须覆盖：正常路径至少 1 条（用户主流程怎么算成功）+ 边界/异常输入至少 1 条（空输入/非法值/极值时系统的预期行为）。
- 每条可观察、可判定（能转成 GWT 场景），不含实现细节（不提函数/存储/框架）。
- 从对话中用户明确表达过的要求优先提炼；对话没细说的边界，按同类产品的常见合理预期补齐，不臆造用户没提过的新功能。
- 【生成式断言规则】验收描述目标产品契约，不描述静态草图的能力限制。生成/分析/推荐/总结类能力优先断言：必要的输出结构、结果与输入事实的关联、明确禁止的内容（如固定模板冒充）、失败行为与其他已确认质量条件；除非需求明确要求固定文本，不得把单个示例答案当唯一正确输出。「当点击分析时系统显示正确分析」这类不可判定的断言不算验收。
- **冲突裁决（重要）**：当对话中用户最新、更具体的表述与某功能项 description（冻结的旧措辞）不一致时，以用户最新表述为准撰写该功能项验收要点，并在 document 功能清单节的对应验收要点末尾加“（依据用户原话修订）”，不得为迁就 description 旧措辞而写出与用户意图相反的验收。positioning、acceptance、document 三处对同一件事的语义必须一致，不得出现“定位说前一天、验收写当日”的分裂。
- 语义重复或指向同一行为的功能项，验收要点不得互相矛盾，同一行为只描述一次。

四、out_of_scope（范围外）
- 用户明确拒绝、排除或表示"本轮不做"的；以及"你帮我决定"时按常见做法主动收敛掉的部分（如多用户/云同步）。
- 防止下游模型擅自扩功能，宁缺毋滥：无明确依据时给空数组，不要编。

五、assumptions（后台假设）
- 后台必须替用户做的技术/产品决策：数据单位、存储方式（如本地保存）、界面语言、排序/汇总规则、默认值等。
- 每条一句话说清"假设了什么"，供后续 decisions 回溯。

六、gdd（游戏设计文档，仅 game 类型输出；非 game 省略此字段）
- core_fantasy：核心幻想——玩家扮演什么、体验什么（一句话）。
- pillars：设计支柱 2~3 条——支撑核心幻想的可玩性原则。
- core_loop：核心循环——主玩法循环的阶段序列（如 探索→战斗→收集→升级）。
- numbers：数值基准——关键数值/范围（生命值/得分/关卡数/道具池范围等）。
- 从对话提炼；对话没说细的机制按同类游戏常见合理预期补齐并克制标注「（建议）」；document 的功能清单/行为断言从 gdd 核心循环切片，不发明 gdd 之外的机制。

七、interface_spec（后端 API 契约，前后端分离真相源）
- 凡功能涉及数据留存、服务端处理或 AI 调用，逐端点列出：endpoint（一律以 /api/ 开头，平台自动挂载 server/routes）、method（GET/POST/PUT/DELETE，缺省 GET）、request（请求要点，无则写「无」）、response（响应要点，JSON 形态）。
- **触发判定（重要）**：从验收要点/描述里的数据留存信号词判定——历史、保存、记录、持久、刷新或重开后仍在、清空、收藏、回顾、本地保留。命中任意一个就必须有 interface_spec（例：计算器的「计算历史…手动清空才清空」→ GET /api/history + POST /api/history；笔记的「刷新后仍在」→ GET/POST /api/notes）。只有确实无任何数据留存的纯展示产物才省略此字段。
- 这是前后端共同遵守的契约：编程 Agent 按它实现 server/routes，终验按它做存活检查；端点粒度对齐功能项主流程，最多 6 条，宁缺毋滥。
