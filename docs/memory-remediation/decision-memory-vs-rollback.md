# 决策单：记忆与回滚的关系 + 撤销名单截断（第 2 项）

> 提出：2026-09-12｜触发自：记忆栈审计裁定 ①②③④ 与 D0 落地后的两个开放问题
> **签署要求**：决策人须**含非实现者**（威胁模型与本文档不得自证）；建议 = 产品角色 + 安全 Owner 会签
> 关联：`threat-model.md` §9（语义变更登记）、`revocation-and-cross-session.md` §7（截断未决项）、`metrics-budget.md` §2（不加缓存的反例）

---

## 0. 为什么要决策

撤销名单让"删除后不再注入"在**注入侧**成立（learnings / session-recall 已接，D0 完成）。但仍有两处需要裁定：

1. **回滚会不会让已删记忆复活？**（快照归档里含记忆文件 → 回滚恢复 → 磁盘上文本回来）
2. **撤销记录会不会被截断，导致老文本重新可注入？**（上限丢最旧 vs 文本仍可能从转录/快照恢复）

---

## 1. 决策一：记忆与回滚的关系

### 现状（代码事实）

- `platform-services.ts:518`：`include_documents=true` 时把 `documents/` **整目录**归档（含记忆文件，若存在）；
- `:858`：回滚时 `cpSync(archive, documentsDir, {force:true})` **整目录**恢复（且不剪除目标端多余文件）。

### 三个选项

| 选项 | 做什么 | 语义后果 | 代价/风险 |
|---|---|---|---|
| **A 归档排除** | 新快照归档时按**文件粒度**排除 `learnings.jsonl` / `memory.json` / `project-map.md`（保留 `prd.json`） | **记忆跨回滚存续**：回滚不再恢复记忆，也不删除现有记忆 | 产品可见行为变更（用户可能预期"回滚连记忆一起回"）；历史快照不受影响 |
| **B 恢复侧过滤** | 恢复时跳过/改写已撤销条目 | 只保证"删掉的不被复活" | **不推荐**：① 只跳整文件 → 丢掉该文件未撤销条目（破坏回滚保真）；② 恢复时改写 → 真改"回滚=回到快照状态"的保真语义 |
| **C 注入侧 + UI 侧覆盖**（现状延伸） | 注入侧按指纹过滤（**已实现**）+ UI 不展示已撤销条目（下一批） | 磁盘上可能出现"复活"的文本，但**永不进入模型上下文**；UI 层同步不展示 | 依赖撤销名单始终可靠（见决策二）；磁盘残留需在 UI/文档如实告知 |

### 分析

- **C 已经把 prompt 级复活堵死**（learnings / session-recall 均按指纹过滤，且为只读侧排除、不改写数据）；B 在 C 之上只能再覆盖"UI 展示"与"磁盘残留"，而 UI 无需靠 B（可在 UI 层过滤）。
- **A 与 C 不互斥**：A 让载体更少（新快照根本不含记忆），C 保证既有载体不泄漏。选 A 是对"回滚应否带上记忆"的产品表态；选 A 后 B 可直接取消。
- **B 独立存在的理由很弱**（见上表两处硬伤），除非日后要求"回滚时必须把记忆恢复到快照当时状态"（那反而不该过滤）。

### 推荐

**以 C 为主（不做 B）**；A 由产品表态：
- 若产品认为"**记忆是项目的独立资产，不应随版本回滚**" → 采纳 **A**（同时取消 B）；
- 若产品认为"**回滚就该连同记忆一起回**" → 不采纳 A，维持 C（此时唯一残留风险是 UI 显示，UI 排下一批处理）。

## 2. 决策二：撤销名单截断 vs 可恢复载体

### 问题

`bloma-revocation-index.json` 现有上限 `MAX_FINGERPRINTS = 5000`，超限**丢最旧**（静默）。若某被删文本仍可从**会话转录**或**历史快照**恢复，则该指纹被丢弃后，文本会**重新变为可注入** → "删除不可复活"被截断策略破坏。

### 三个候选

| 候选 | 做法 | 成本 | 风险 |
|---|---|---|---|
| ① `retain_until` / `recoverable` 联动 | 指纹带保留期，与快照保留期/转录存在性联动 | 中（需判断"是否仍可恢复"） | 逻辑复杂，"可恢复"判定本身易错 |
| **② 取消丢最旧，改按大小告警** | 不再静默丢弃；文件超阈值只**告警 + 决策日志**，由人决定 | **低**（约 40B/条，5000 条 ≈ 200KB；10 万条 ≈ 4MB） | 文件无上限增长（对本应用可接受） |
| ③ 先做 A（归档排除）再允许截断 | 先确认无快照残留，再保留截断 | 依赖决策一 | 转录仍含文本 → 截断后仍可召回（不彻底） |

### 推荐

**②**：撤销记录是**安全账本**，静默丢弃与"删除不可复活"直接冲突；而增长成本在本地应用里可忽略。若日后需要硬上限，也应"**告警 + 拒绝删除**"，而不是静默丢最旧。

> 注：候选 ③ 不能单独成立——会话转录始终可能含文本，故截断风险与 A 无关。

## 4. 若不决策的后果（残留风险登记）

- 决策一未定：**A 与 B 都不做**，即维持 C —— prompt 级安全已闭环，残留 = 磁盘/UI 层的"复活可见"（需在 UI 交付时告知）；
