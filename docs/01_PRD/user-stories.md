## 1. 角色与故事分布

| 角色 | 类型 | 故事数 | 说明 |
|------|------|:---:|------|
| **零基础用户** | 真实用户 | 10 | 平台存在的唯一理由。所有设计决策以他们为最高优先级 |
| **向导 Agent** | 系统角色 | 4 | 唯一面向用户的对话方。故事描述它为用户提供的能力，而非内部实现 |
| **编程 Agent** | 系统角色 | 3 | 在后台生成和修复代码。故事描述它支撑的交付能力 |
| **裁判 Agent** | 系统角色 | 3 | 独立质量门禁。故事描述它保障的交付底线 |
| **研究者** | 真实用户 | 2 | 课题组成员，通过数据看板分析用户行为 |

> 共 **22 条**故事。格式：`作为[角色]，我希望[能力]，以便[价值]`。每条 P0 故事附带 1-2 个关键 GWT 验收骨架。

## 2. 零基础用户（U）— P0 核心

> 用户画像见 PRD §3.1。不会编程、不看文档、通过"看"判断好坏、抗拒技术术语。

### U-01 · 用日常语言描述我想做的软件

**优先级**：P0 ★ | **Phase**：1 | **PRD**：§5.1

作为**零基础用户**，我希望打开应用后直接对着聊天框说话就能描述我的想法，系统用几个简单问题帮我理清思路，以便我不需要学编程也能开始做软件。

```gherkin
Scenario: 用自然语言启动项目
  Given 用户已进入工作区
  When 用户输入"帮我做一个记账应用，要能分类查看"
  Then 系统用自然语言回复，确认它理解了哪些要点
  And 回复中不含技术术语或配置选项

Scenario: 想法模糊时被友好引导
  Given 用户输入"帮我做个东西"这样非常模糊的描述
  When 系统无法确定具体方向
  Then 系统用引导性措辞追问，提供 2-3 个具体示例方向
  And 不使用"你说得不清楚"等负面措辞
```

### U-02 · 在两道门之间选一个适合我的

**优先级**：P0 ★ | **Phase**：1 | **PRD**：§4.1、§4.2、§13.2

作为**零基础用户**，我希望启动应用后看到两个清晰的选择——"快速试试看"和"长期认真做"——以便我根据自己的需求选对路子，不用了解背后的技术差异。

```gherkin
Scenario: 首次启动看到两个模式入口
  Given 用户首次启动应用
  When 模式选择页加载完成
  Then 看到"快速尝鲜"和"精细打磨"两个卡片
  And 每个卡片用生活化语言说明适用场景

Scenario: 选完后进入工作区
  Given 用户点击任一模式卡片
  When 页面切换完成
  Then 进入统一的工作区布局（对话区+预览区+时间轴）
  And 向导 Agent 发来第一条问候消息
```

### U-03 · 很快看到一个草稿来判断方向对不对

**优先级**：P0 ★ | **Phase**：1 | **PRD**：§5.2

作为**零基础用户**，我希望在我描述完想法后，一分钟内就能在右边看到一个能点击操作的简易版本，以便我快速判断"系统理解对了吗"，而不是等了半天才发现做偏了。

```gherkin
Scenario: 一分钟内看到可交互预览
  Given 用户已确认需求方向
  When 系统开始生成验证草图
  Then 60 秒内预览区出现可点击的页面
  And 页面展示核心功能的最简版本

Scenario: 生成超时也有交代
  Given 草图生成超过 120 秒仍未完成
  When 超时触发
  Then 系统告知"花的时间比预期长"，并展示已生成的部分
  And 用户可选择继续等待或重新生成
```

### U-04 · 在预览上直接指出我不满意的地方

**优先级**：P0 ★ | **Phase**：1 | **PRD**：§5.2、§13.5

作为**零基础用户**，我希望在预览的草图上直接点击我不满意的位置并描述问题，就像在纸上圈出来说"这里改一下"，以便我不需要用任何技术词汇就能表达修改意见。

```gherkin
Scenario: 点击不满意的区域
  Given 预览区展示着草图或 MVP
  When 用户点击某个元素（按钮、文字、布局区域）
  Then 该区域高亮，弹出输入框"这里有什么问题？"
  And 用户可输入文字或直接关闭（表示"你猜"）

Scenario: 连续两次没改对时系统主动追问
  Given 同一区域已被修改两次但用户仍不满意
  When 用户再次点击该区域
  Then 向导 Agent 主动追问更具体的问题帮助用户表达
```

### U-05 · 等待时看到安抚提示而不是干等

**优先级**：P0 ★ | **Phase**：1 | **PRD**：§13.6

作为**零基础用户**，我希望在系统生成软件的过程中看到进度提示和安抚文字，以便我知道系统还在工作、没有卡死，也不会担心它搞坏我的电脑。

```gherkin
Scenario: 超过 5 秒显示进度文案
  Given 系统正在执行生成任务
  When 耗时超过 5 秒
  Then 对话区或预览区出现进度提示
  And 文案说明当前在做什么
  And 耗时尚未超过 10 秒时不显示安全感说明

Scenario: 超过 10 秒显示安全感说明
  Given 系统正在执行生成任务
  When 耗时超过 10 秒
  Then 对话区或预览区出现进度提示
  And 文案说明当前在做什么，且包含"安全""放心"等安抚关键词
```

### U-06 · 拿到一个功能完整的可用版本

**优先级**：P0 ★ | **Phase**：1 | **PRD**：§5.3

作为**零基础用户**，我希望在我确认草图方向正确后，系统给我一个所有功能都能正常使用的完整版本，让我像用正常软件一样操作它，之前指出的问题也都改好了。

```gherkin
Scenario: MVP 包含全部确认的功能且可运行
  Given 用户已确认草图方向
  When MVP 生成完成
  Then 预览区中的每个功能均可正常操作
  And 草图中被标记不满意的地方已被修正
  And 向导 Agent 用自然语言告知"做好了，你看看"

Scenario: 生成出错时不显示技术信息
  Given MVP 生成过程中出现错误
  When 系统检测到错误
  Then 预览区展示安抚性提示，不含代码、堆栈或 HTTP 状态码
  And 系统自动尝试修复
```

### U-07 · 一键回到之前的版本

**优先级**：P0 ★ | **Phase**：1 | **PRD**：§13.4

作为**零基础用户**，我希望在底部时间轴上看到项目经历的关键节点，点一下就能回到那个版本，就像"撤销"一样简单，以便我不用担心改坏了回不去。

```gherkin
Scenario: 通过时间轴回退
  Given 项目已生成至少两个快照
  When 用户点击时间轴上的某个历史节点并在确认弹窗中确认
  Then 预览区恢复到该快照状态
  And 向导 Agent 告知"已经回到之前的版本了，一切都在"

Scenario: 回退后之前的版本仍在
  Given 用户已从"MVP v1"回退到"草图 v1"
  When 回退完成
  Then "MVP v1"的快照仍保留在时间轴上，用户可再次跳转回去
```

### U-08 · 被告知具体哪里和预期不一样，而不是笼统警告

**优先级**：P0 ★ | **Phase**：2 | **PRD**：§10.4

作为**零基础用户**，我希望当系统自动检查发现它做的东西和我想要的之间有差距时，用我能听懂的话告诉我具体缺了什么，并让我自己决定要不要继续改——而不是给我一个看不懂的技术警告。

```gherkin
Scenario: 功能偏差让用户知情并选择
  Given 裁判 Agent 发现 MVP 缺少用户要求的功能
  When 自动修复已达上限
  Then 向导 Agent 告知"你提到想要按月统计，但当前页面里没有这个功能"
  And 用户可选择"再改改"或"现在这样就挺好"
```

### U-09 · 用点卡片的方式做选择，不用每次都打字

**优先级**：P1 | **Phase**：1 | **PRD**：§13.1

作为**零基础用户**，我希望当系统需要我做选择时，大部分时候能直接点卡片选项来回答，以便省去打字的麻烦，但想打字的时候仍然可以打。

```gherkin
Scenario: 系统以卡片形式提问
  Given 向导 Agent 需要用户做出选择
  When Agent 提出澄清问题
  Then 问题附带 2-3 个可点击的卡片选项
  And 选项列表中包含"你帮我决定"
  And 用户仍可在输入框自由打字
```

### U-10 · 快消项目用顺手后升级为长期维护

**优先级**：P0 ★ | **Phase**：3 | **PRD**：§4.4

作为**零基础用户**，我希望当我的快消型项目已经能用了之后，系统主动告诉我可以升级为长期维护项目，以便以后能做更精细的改进和版本管理。

```gherkin
Scenario: 快消项目完成后看到升级入口
  Given 用户已标记快消型项目为"完成"
  When 用户回到工作区
  Then 系统展示升级提示，用自然语言说明升级后能获得什么
  And 用户可选择立即升级或暂不升级
```

## 3. 向导 Agent（GA）

> 向导 Agent 是唯一面向用户的对话对象（PRD §6.2）。以下故事描述它为用户提供的关键能力。

### GA-01 · 读懂用户意图并引导澄清

**优先级**：P0 ★ | **Phase**：1 | **PRD**：§6.3

作为**向导 Agent**，我希望能够从用户的自然语言描述中准确提取核心意图，用不超过 3 个精准问题澄清模糊之处，以便用户不需要自己先把需求想得滴水不漏。

```gherkin
Scenario: 从模糊描述中提取可执行的需求
  Given 用户输入了一段日常语言的描述
  When 向导 Agent 分析输入
  Then 产出一份可被编程 Agent 理解的功能要点
  And 对用户的追问不超过 3 个问题
  And 每个问题附带卡片选项
```

### GA-02 · 根据项目模式自动调整内部工作方式

**优先级**：P0 ★ | **Phase**：1 | **PRD**：§4.3、§6.3

作为**向导 Agent**，我希望在快消型下自动完成技术选型和工程决策且不打扰用户，在长期迭代型下在关键节点征求用户确认，以便不同模式的用户获得适合自己的透明度。

```gherkin
Scenario: 快消型下后台自动决策
  Given 用户在快消型工作区
  When 需求确认后需要技术选型
  Then 所有技术决策在后台完成，用户全程无感知
  And 决策结果记录在 decisions.md 中备查

Scenario: 长期迭代型下关键方案与用户确认
  Given 用户在长期迭代型工作区
  When 架构方案产出
  Then 用户看到结构化的功能描述（非技术语言）
  And 用户可确认或提出修改
```

### GA-03 · 从对话中自动整理需求文档

**优先级**：P1 | **Phase**：1 | **PRD**：§7.1

作为**向导 Agent**，我希望在关键检查点（草图确认后、MVP 交付前、每轮迭代后）自动从对话历史中提取和更新需求文档，以便文档始终反映最新状态而不需要用户或开发者手动维护。

```gherkin
Scenario: 草图确认后生成 PRD 初稿
  Given 用户确认了验证草图方向
  When 检查点触发
  Then 系统自动从对话中提取功能需求并生成结构化 PRD 初稿
```

### GA-04 · 记录重大决策以便日后回溯

**优先级**：P1 | **Phase**：2 | **PRD**：§5.4

作为**向导 Agent**，我希望在系统自动做出高影响决策时（技术选型、架构方向等），自动生成一条标注记录保存下来，以便用户日后说"换成 MySQL"或"回到之前的方案"时，我能快速找到相关决策并评估改动成本。

```gherkin
Scenario: 高影响决策自动标注
  Given 系统做出了一项影响多个模块的技术决策
  When 决策生效
  Then 自动生成决策标注（含原因、影响范围、可逆性、替代方案、时间戳）
  And 标注保存为 decisions.md 条目
```

## 4. 编程 Agent（PA）

> 编程 Agent 不直接面对用户（PRD §6.4）。以下故事描述它支撑的核心交付能力。

### PA-01 · 快速产出可交互验证草图

**优先级**：P0 ★ | **Phase**：1 | **PRD**：§5.2

作为**编程 Agent**，我希望在收到需求描述后 60 秒内生成一个可在沙箱中运行的单文件 HTML 草图，以便用户能立刻看到方向对不对，而不是空等。

```gherkin
Scenario: 60 秒内交付单文件草图
  Given 收到需求描述和 UI 建议
  When 开始生成
  Then 60 秒内产出一个包含内联 CSS+JS 的单文件 HTML
  And 包含 1-3 个核心页面，数据为静态模拟
  And 该 HTML 在沙箱 WebView 中可正常渲染
```

### PA-02 · 从规约构建功能完整的 MVP

**优先级**：P0 ★ | **Phase**：1 | **PRD**：§5.3

作为**编程 Agent**，我希望在用户确认草图方向后，基于完整规约生成功能齐全、结构规范的 MVP 应用，并为每个功能自动生成和运行 GWT 测试，以便交付物有质量保障。

```gherkin
Scenario: MVP 覆盖全部规约功能并通过测试
  Given 规约定义了 N 个功能项
  When MVP 生成完成
  Then 每个功能项均有可运行实现
  And 每个功能项至少对应 1 个 GWT 验收场景
  And 全部 GWT 测试通过
```

### PA-03 · 代码出错时自动修复，修不好就安全回退

**优先级**：P0 ★ | **Phase**：1 | **PRD**：§6.6

作为**编程 Agent**，我希望在代码运行失败或测试不通过时自动尝试修复，最多 3 次，修不好则回滚到上一个健康快照并通知向导 Agent 与用户沟通，以便小错误不阻断用户流程，大问题不静默失败。

```gherkin
Scenario: 自动修复 → 熔断 → 回滚
  Given 代码运行失败或 GWT 测试不通过
  When 自动修复尝试 3 次后仍不通过
  Then 系统回滚到最近健康快照
  And 通知向导 Agent，由其告知用户发生了什么并给出后续选项
```

## 5. 裁判 Agent（J）

> 裁判 Agent 是独立质量门禁（PRD §10.1）。以下故事描述它保障的交付底线。

### J-01 · 确保每个功能都经过测试验证

**优先级**：P0 ★ | **Phase**：1 | **PRD**：§10.2

作为**裁判 Agent**，我希望在代码交付前自动检查：需求文档是否完备、每个功能是否都有对应的验收测试、所有测试是否全部通过，不通过则退回修复，以便交付给用户的东西不会漏功能。

```gherkin
Scenario: 硬约束检查——文档+测试+通过率
  Given 代码已提交裁判审查
  When 裁判执行硬约束检查
  Then 验证 PRD 含项目名称和核心功能
  And 验证每个功能项至少对应 1 个 GWT 场景
  And 验证全部 GWT 测试通过
  And 任一不通过则生成退回报告，列出具体不通过项
```

### J-02 · 检查文档和代码是否对得上

**优先级**：P1 | **Phase**：2 | **PRD**：§10.2

作为**裁判 Agent**，我希望用 AI 评估需求文档中描述的功能是否都在代码中实现了、边界条件是否被覆盖，输出"通过/建议改进/退回"三级判定，以便不让"文档说一套代码做一套"的情况溜过去。

```gherkin
Scenario: 软约束评估——逻辑一致性和边界覆盖
  Given PRD 和代码均已就绪
  When 裁判执行软约束评估
  Then 逐项检查 PRD 功能是否在代码中有对应实现
  And 检查边界条件和异常场景是否被覆盖
  And 输出三级判定（通过/建议改进/退回）并附具体说明
```

### J-03 · 安全问题强制修复，不把它变成用户的选择题

**优先级**：P0 ★ | **Phase**：2 | **PRD**：§10.5

作为**裁判 Agent**，我希望在检测到安全漏洞时强制触发修复——这个修复不计入普通问题的退回次数，修不好也要明确告知用户具体风险——以便安全问题的处理优先级高于功能偏差，且用户不会被要求对不懂的技术风险做决定。

```gherkin
Scenario: 安全问题独立于普通退回流程
  Given 裁判检测到 XSS 或注入类安全漏洞
  When 安全漏洞被识别
  Then 系统强制触发自动修复，不计入普通退回次数
  And 安全修复独立计数，上限 3 次
  And 多次修复失败后告知用户具体风险（生活化语言），最终决定权在用户
```

## 6. 研究者（R）

> 研究用户为课题组成员（PRD §3.3）。P2 优先级，Phase 4 实现。

### R-01 · 通过数据看板了解用户行为全貌

**优先级**：P2 | **Phase**：4 | **PRD**：§14.3、§14.4

作为**研究者**，我希望在一个后台看板中看到所有关键埋点事件的统计数据（FIRT 耗时、完成率、模式选择比例、放弃节点等），并能按模式和时段交叉筛选，以便从宏观层面理解零基础用户使用自然语言开发软件的行为模式。

### R-02 · 导出脱敏数据做统计分析

**优先级**：P2 | **Phase**：4 | **PRD**：§14.2、§14.6

作为**研究者**，我希望将脱敏后的用户交互数据导出为标准格式（CSV），不含用户的真实业务内容，以便在外部统计工具中进行显著性检验并支撑科研论文产出。
