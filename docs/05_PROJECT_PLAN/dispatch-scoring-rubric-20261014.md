# 实验评分规则：固定清单、操作证据与体验评审

用户提出为什么不能由 Codex 评分、评分器依据什么。可以由 Codex 实际操作并评价；自动化不是评分的前提。正式对照须在生成样本前固定需求、检查清单与计分口径，不能看见某个模型的结果后改标准。采用混合评审：业务项按冻结清单操作、留证；高重复检查可以脚本辅助；主观体验另列，不代替功能正确性。评分工具也会误判，需要抽查和校准。

## 依据和当前覆盖

唯一业务依据是冻结的用户需求、确认 PRD 的功能/业务规则/验收场景及确认 UX。平台内部调用记录只能证明执行过程；模型自称完成、HTTP 200、正常退出、截图漂亮都不能单独证明功能正确。

- L1：已有独立 GUI 六项 `add-trim / empty-rejection / toggle-isolation / filters / delete-isolation / restart-persistence`。6/6 只代表这六项；平台声明七项需求、模型自测和 PRD 全部细节另列，不能互相替换。
- L2：`experiments/dispatch-difficulty-v1/L2/suite.json` 的 14 项。
- L3：对应 L3 清单的 22 项。
- L2 原S1方法试点：v1有限输入14/14，v2新ID非法日期复评13/14。固定场景在正确参考及15种故障上校准；新预登记S1/S2配对各一轮，均14/14，见 [L2 配对结果](dispatch-l2-pair-result-20261015.md)。参考UI适配器的可选空日期允许null或空字符串，业务语义不变；名称等控件映射仍需逐产品核对，不称为通用全自动评分器。
- L3 原样本原生交付、独立验收19/22；新增8项后续完成参考8/8及9个显式故障变体检出，见 [L3 校准](dispatch-l3-calibration-20261015.md)。没有修改原产品或原评分，不宣称校准覆盖所有等价错误。单轮单任务不能支撑难度效应、调度收益或模型总体优劣。

## 每项评审的四步

1. 建立独立测试数据目录，保存初始数据与日期/时区；按清单准备输入，同名对象至少两条，不能靠标题推断唯一身份。
2. 通过真实界面输入、点击、切换、关闭重开；文件选择可以由受控脚本模拟选择路径，导入/导出与业务处理仍走产品原有入口。不得直接调用业务层替代 GUI 链。
3. 对照预定结果读回界面、计数、状态、导出文件或重开数据；保留操作顺序、截图/DOM、前后数据差异、失败说明和版本哈希。
4. 记录 passed / failed / pending。产品明确违反规则为 failed；操作驱动不支持、环境故障或证据不足为 pending，写明原因，不能把它算成产品通过或模型业务失败。

例如同名任务隔离：建两条同名记录 A/B；只完成 A，确认 B 未完成；取消 A，确认 B 仍未完成；再删除 A，确认 B 与状态保留；关闭并重开确认结果。只有实际完成这些动作才评价这条链，不能从源码有 toggle/delete 方法推断通过。

## 业务分与流程状态

全部预定检查完成后，功能 Q=通过项数/全部预定项数，等权；任一必需项失败则完整功能成功=false。有 pending 时完整 Q=null，另报已测分项，不缩小分母制造满分。基础六项子分与复杂新增项分开，保留每项结果。

原生 ready/failed/cancelled/timeout、独立功能成功和样本有效性三列分开。平台提前取消执行器等基础设施问题不能当成模型能力失败；可记录现场产物缺哪些功能，但不把非最终产物用于正式模型效果比较。任何漏测和不支持的操作必须明示。

## 主观体验另列

Codex 可按下列冻结维度评价 1–5 分；每个分数至少给一条实际观察，不能仅凭印象：

| 维度 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|
| 找到主要操作 | 入口不可找到/不可用 | 能找到但有明显歧义 | 操作名称和位置清楚，核心路径直接 |
| 状态与结果反馈 | 无法判断是否成功 | 有反馈但不完整 | 成败、当前筛选与计数一致且易懂 |
| 错误与恢复 | 丢输入/无恢复提示 | 提示错误但下一步不清楚 | 保留输入/原数据，说明可执行的下一步 |
| 阅读与操作清晰度 | 文字或控件无法正常使用 | 基本可用但存在拥挤/对齐问题 | 信息层次清楚，控件易读易操作 |
| 交付说明 | 启动/数据位置不明 | 能启动但限制与备份说明不足 | 启动、限制、数据位置和备份迁移有实际依据 |

这是代理评审的观察分，不等于真实目标用户满意度、认知负担或可用性结论。正式论文宜由独立人类抽查或第二评审按相同尺度复核；Codex 同时参与平台修复和实验执行，不能声称其评价完全盲法或无偏。

## 难度清单的补充操作

L2 项目名称用 ` 工作 ` 与 `工作` 检查去空格后的重复；两个项目建立同名任务，移动其中一条后核对全部字段与归属；项目删除必须先证明非空拒绝，再移走任务证明空项目能删。日期记录测试当日 T，构造 T-1/T/T+1 及已完成的 T-1，过期只含未完成且早于 T。若检查跨午夜或无法固定日期，先暂停该项，不能混用“今天”。

组合筛选同时指定项目、状态、优先级、过期和大小写搜索，预先写出目标 ID 集合，核对交集而非逐个筛选看起来正确。备份先在空目录恢复，再导入混合有效/无效、内容冲突样本，比较完整前后状态；重复导入不得增量重复，也不得合并同名任务或删除备份外记录。

L3 在上述基础上先建合法依赖链，再测自环、两节点环、三节点环；分别检查两个前置的完成门禁与已完成后续对取消的限制。批量操作按批后状态判合法，并混入一条不合法项验证全部回滚。撤销只撤最近成功的一笔，失败操作不能挤掉撤销项，撤销本身不变成无限反复撤销的新操作。最后用两个独立窗口测不同任务更新合并及同任务旧版本提交冲突。

## 记录、校准和变更

每组使用相同动作模板与数据关系；生成者自测与独立评审证据分别保存。标准记录包含 run_id、输入/平台/评分规则哈希、评审身份、开始结束时间、日期时区、动作、预期、实际结果、证据路径与结果分类。现有 `manual.json` 可承载 id/passed/evidence，完整操作记录另存 JSON/Markdown；pending 不写成 passed=false 的产品失败。

自动化增加前，使用正确参考行为和明确故障反例检验：正例全部通过，反例的对应检查必须失败，空操作不能冒充完成。人工/代理评审同样可用小样本相互核对。正式样本若发现评测适配器缺陷，保留原结果为未确认；统一修复、定版本后复评完整配对，不只给失败模型临时改标准。

## 下一步边界

先依据本规则对复杂任务做少量实际评审与方法校准，再决定哪些高重复动作自动化；完整六组需统一版本和资源，并在开跑前安排费用。当前不因评分方法讨论自动启动新的付费矩阵。
