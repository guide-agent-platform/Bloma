## 已接线行为

- `lean-production.ts` 复用当前 Pi、委派生命周期、最多两并发、父模型与共享请求/输出/金额预算。A 结束制作前，宿主检查当前候选是否有完成的 C 结构化审阅；缺失时实际启动只读 review 子会话并等待回收。
- C 使用独立任务书，只拿确认目标、业务预期、约束、候选身份及只读文件工具，不继承 A 的成功叙述或开发现场工具。不提供命令、写文件、图片、再委派或宿主验收工具。普通 review 仍可作只读调研，但不能替代专用 C 协议。
- 审阅前停止本会话开发实例和服务，拒绝未完成命令或活跃写入工人。审阅期间协作策略冻结受管写入和命令；外部文件变化会在提交和收口时使身份不匹配。沿用原执行边界，这不是 OS 沙箱。
- 候选身份使用现有发布文件清单摘要（含依赖）、确认需求/外观身份、受管运行时和能力绑定版本、平台信息。宿主动态生成 review/finding ID，不能由模型指定版本或最终状态。普通业务数据与报告沿用发布清单的可变目录规则，不声称冻结了真实用户数据。
- C 必须实际调用 `read_quality_review` 和至少一次成功的 `read_file`，再调用 `submit_quality_findings`；单说 PASS、只提交文本、未读取就交空数组均不能完成审阅。读取动作不证明审阅能力或覆盖充分。
- 台账原子保存于 `PROMA_HOME/software-quality/<project>.json`，在生成工程外。保存每次候选、委派身份、结构化疑点、确认需求引用、未知项、复现/复测结果、观察摘要及验证候选 ID。损坏不可静默清空；新审阅中断后不能回退使用旧审阅放行。

## 工具与状态

A 使用 `start_quality_review`、原有 wait/get 委派工具、`read_quality_findings` 和 `check_quality_finding`。C 只使用只读文件工具及专用 read/submit 协议。模型不能直接写入“已证实”“已关闭”。

finding 包含 requirement、expected_source、category、severity、location、trigger、evidence、reproduction、unknowns。宿主逐字核对确认预期；引用未知需求作为建议，预期不符作为争议，不能拿这些条目登记已复现缺陷。

宿主复现沿用 `verifySoftwareCandidate(force=true)` 与当前冻结 GUI/CLI 案例：指定案例名必须实际产生对应需求编号的执行结果，GUI 原生结果还须有实际断言。首次失败须对应原审阅候选，保存失败观察后才记 confirmed。后续相同案例、冻结规则、目标与环境绑定在修复候选实际通过，且整体验证通过，才记 closed；源码变化保留旧失败，不会由一句“修好了”关闭。未复现疑点保留 not_reproduced/未知结果，不计作修复成功。

仅已确认的 high/critical 缺陷必须闭合；疑点、争议、范围外建议不变成无限阻塞。关闭证据须匹配当前候选和规则。新候选必须重新审阅；最终验证后及延迟交付收口前再检查台账。预算停止后仍执行已有免费宿主验收，但缺少当前 C 审阅时保留结果并阻止交付，不追加费用或重置预算。
