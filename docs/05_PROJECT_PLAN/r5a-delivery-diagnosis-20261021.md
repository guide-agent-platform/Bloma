# r5a 交付失败原因复核（2026-10-21）

结论：直接终止点已查明。平台拒绝未验证交付是合理保护，但其 `unverified` 分支没有补证与复核闭环，首次出现即记作 `gate_exhausted`。这确实是平台交付机制的缺口，不能笼统归因于产品六项业务失败。生成产物另有可在受控桥延迟条件下复现的首屏恢复问题，两者应分别处理。

## 直接原因：未验证直接终止，没有耗尽两次修复

封存运行树 `8224ac088b9103cddeca231596ae9a99940290f9` 与主工作区对应源码相同。`main/desktop/quick-production-review.ts:108-120` 的实际逻辑是：

- pass 放行；
- 只有 fail 且有 findings 才消耗 quick-review 修复预算，至多两次，交回原实现者；
- unverified（包括证据缺失、审阅执行错误、带具体疑点的未验证）统一落入 gate_exhausted，停止。

r5a 实际事件为：V启动1次、结束1次、quick_verifier_repair **0次**。执行账本没有 quick-review 计数。因此，本轮并非“V后自动修复两次仍失败”，而是 V 首次判 unverified 就直接收口；`EXPERIMENT_GATE_EXHAUSTED` 名称在本例没有准确表达停止原因。原日志和终态不回写。

不能通过把所有 unverified 变成 pass 或盲目送代码修复解决。需要区分：具体源码问题交修复；验证范围缺失交补证；审阅/环境故障交恢复；纯风格或无用户可见影响的接口差异不得仅凭疑虑无限阻塞。补证、修复和复核均需有界并保持同一累计预算。

## V 的两项疑点分别核实

1. **启动时序：存在条件性缺陷。** 实际生成 UI 在 boot 一开始设置 booted=true；正常模式 DOMContentLoaded 后300ms调用boot，平台桥再等120ms仍未就绪便报错。如果 pywebviewready 在其后到达，第二次boot因标记直接返回，已有任务不自动加载。使用原始生成 HTML/JS 和原始 bridge.js，在离线DOM中控制桥注入顺序，复现“桥后续已可用，列表仍空，加载失败横幅保留”；早就绪对照正常显示已保存任务。此为受控时序复现，不是本机真实WebView正常启动失败率，也未证明此前六项GUI测试失败。生成源码未改。
2. **新增回包view：未证实业务缺陷。** add_task未带当前view，返回默认all，但前端明确随后调用list_tasks(currentView)。在同一离线实际UI执行中，已完成视图新增未完成任务后，仍显示原已完成任务，视图保持completed；调用记录为add_task(all)随后list_tasks(completed)。此前真实六项独立验收也通过。接口可统一，但现有证据不足以把这条差异认定为阻断性交付错误。

复现范围、调用记录、前后源码哈希见 `outputs/experiment-r5a-20261021/delivery-diagnosis/probe.json`；脚本同目录。Python API为注入替身，DOM执行实际生成代码，未调用付费模型，未修改原样本。首版诊断脚本误从严格eval的window属性读取局部变量，断言失败；改为读取真实DOM选中状态后通过，不将诊断脚本失败记成产品故障。

平台现有启动冒烟验证窗口存在/响应/稳定，并不等价于已验证正常pywebview桥首屏业务。业务驱动与外部六项使用HTTP驱动桥，覆盖范围与正常桥存在差异。V指出这个覆盖缺口有依据，但平台应具备补这条证据的路径。

## 写入边界冲突是独立的恢复问题

调度者自行冻结的写入计划未包括 `00_SCAFFOLD/contract.json`；后续 run_core_verification 工具要求这个契约文件。两次写入被宿主正确拒绝，子问题里的口头授权不能改变宿主登记计划，重登记又因已派遣被拒绝。暴露的是工具前置产物与计划校验/修复范围协议没有完整衔接，不应靠关掉写入保护绕过。

该冲突延误了本轮，但之后实际已进入正式核心检查及V，所以它不是最终 run_finished 的直接原因。旧交接问题在本轮也确实已越过，不能与本次V分支混为一谈。

## 修复顺序

优先修平台的“未验证→分类→补证/修复→复核”闭环和停止原因；补正常启动桥的业务证据能力，明确运行前置产物与受控修复范围，再重新封存实验。生成UI的boot成功标记/失败重试也需要修，但不在已封存r5a原样本上修改。此次只做原因复核，0次新付费请求，不重启实验，不更改r5a评分或V结论。
