# 执行到验收反馈的底层改进：第一批

基线 `62d3f3c`。依据学习助手全过程评估，优先处理宿主反馈丢失案例粒度、单项失败导致所有功能标红、定位超时被直接判为适配问题的缺口。沿用现有 Pi、进程服务、测试运行器和版本门禁，没有增加模型、前置角色或付费调用。

## 实现

- 原生 node:test 验收输出 `case_results`，保留冻结案例名、F 编号、实际通过／失败／未验证／未运行、交互／断言计数与有界错误。模块提前结束时保留已经完成的结果，其余声明案例为 not_run；后来的成功不能抹掉同一案例较早的失败。失败断言可能在计数增加前抛出，不能把这种真实失败误作“没有执行”。
- 旧动作表在存在明确 `acceptance_refs` 时，按实际 expect／expect_file 步骤返回同类结果。缺乏映射的旧失败报告保守记为未验证，不能猜测每个功能都失败；历史通过语义保持兼容。
- 核心验证按每个功能关联的全部案例聚合：有失败为 failed，全部必要案例有实际断言并通过才为 passed，缺失／跳过／未运行仍为 unverified，证据内另记 not_run。整套失败继续阻止交付；局部证据不构成整体 PASS。源码变化、运行异常或零真实交互不会保留局部通过凭据。
- 本机场景／能力协议范围在核心报告和公开工具回执中明确标记。该范围不等于真实 AI 教学质量或完整产品独立验收；本批没有用局部结果补出外部效果证据，也未重解释旧项目记录。
- 原生结果带结构化 `failure_kind`：assertion／runtime／bootstrap／incomplete。诊断优先使用宿主类型和实际 expected／actual；只有“等待 locator 超时”而无断言事实时，返回 category=unknown、classification_basis=unresolved，下一步检查实际应用。不会因为错误文本包含 Timeout 就自动授权修选择器／延长等待。旧格式保持原有兼容诊断路径，尚未改成所有驱动的统一类型系统。
- verify_app 返回逐功能与逐案例信息，优先列非通过案例；最多内联16案例、每项错误600字符、64功能，完整结果保存在宿主报告，避免整段重复日志进入上下文。结构化未知原因也进入 tool feedback，不再被外层按 failed 自动改成产品断言失败。

产品主循环、真实数据、确认范围、正式业务输入／断言、预算和费用规则保持原有边界。第一批不修改用户学习助手的四个业务缺陷，不自动重新验收它。完整验收语义分层、通用夹具与AI服务、缓存失效解释及上下文组成计量属于后续批次，不能据此宣称已经全部完成。
