# 验收与子会话执行修复：首批

日期：2026-10-10。起点：sprint2 / 1342d01。用户确认先完成一批修复，观察效果。排查证据见 `run-artifacts/bloma-acceptance-audit-20261010/REPORT.md`。

## 解决的问题与现行行为

最新「叶氏系统论工艺推演器」在五次验收后仍 blocked：早期名称扫描和状态读取误报消耗修复预算，最后故障种子报告的方法与实际变更不一致。验证子会话12轮预算反复耗尽，调度员看到无法调用的驱动工具；清理临时脚本也形成自删脚本链。

本批把标准验收和强化检查分开，同时补执行便利性：

- **标准模式（默认）**：业务驱动实际执行、场景/核心需求覆盖、入口及现有安全门仍保留。静态测试检查作为诊断记录；不自动修改产物运行变异测试，因此这些诊断不会消耗拒收修复次数。
- **严格模式**：启动环境 `BLOMA_VERIFY_POLICY=strict`，或者调用方显式 `verificationPolicy: 'strict'`。继续执行静态反空拒收和种子检查。调用方显式值优先，其他环境值回退标准模式。没有新增设置页面。
- **证据呈现**：`00_VERIFY/fault-kill-report.json` 记录 policy、静态发现和未执行项；阶段遥测记录 `verification_policy`，checkpoint 不把未运行变异写成通过；过目页展示待复核诊断和未运行检查。驱动执行证据不再冒充完整GUI操作证据。
- **种子定位**：选择和变换使用同一 AST 节点，支持类方法；CLI 的 `--self-check in argv` 不算空值校验；同名保存/回调只修改选中的函数，不改所有同名方法。元数据与实际变更一致。
- **检查器误报**：Python DOM `.eval()`、注释和普通字符串不命中内置动态执行规则；真实内置 eval/exec 和现有明确风险规则仍检测。调用来源不再使用截断64字符AST指纹，前后读取/重新赋值不被判成同一值；直接别名比较仍检出。清理与截图辅助异常降级是待复核项，测试函数吞异常仍检出。
- **基础设施故障**：严格模式注入后的环境阻塞记 not_run，不记 killed；恢复失败停止并报 driver-blocked，避免带着变异入口交付。
- **执行工具**：`run_project_script` 支持互斥的 script/code；短代码最多16000字符，在项目工作目录以 Python `-c` 参数执行，保留原解释器、环境白名单、次数/超时上限；不需要写自删脚本。无效参数不消耗执行次数。implement/custom 均装配执行和依赖安装工具。
- **模型工具面**：常驻工具按阶段过滤；架构/脚手架不展示驱动工具，verify可当场通过 `run_project_driver` 获取反馈，宿主收口仍独立复跑。
- **预算**：桌面 implement/custom 24→32轮；verify 的 research 12→24轮；其他research维持12；仍受父轮次上限约束。这是首批校准值，不声称是最优预算。

工具参数校验参考了本地 Proma `bf3e98c` 的 `agent-tool-input-validator.ts`（运行前检查参数，权限与输入校验职责分开）；本批适配已有 Bloma Python 执行器，添加 script/code 互斥与长度限制，没有移植通用命令或权限体系。

## 首批之外

本批没有重构完整验收状态机，没有增加用户验收状态字段，没有实现通用命令/文件删除/进程管理工具，也没有全局累计token预算或按失败签名的增量重验。安全扫描仍是现有启发式规则，本批只纠正已复现的Python名称和文字误报，不将其称为完整安全证明。严格变异仍按入口文件首个适用节点注入，尚未具有业务F-id到模块/方法的可靠目标映射。
