## 五、测试冻结是否被改松

**本轮没有查到正式冻结之后降低既有预期的证据。**

- tests/acceptance.mjs 的可见修改发生在 00:24–00:33，早于首次正式登记；其中包括等待“本条新回答”而不是读到上一条引用，以及记录行滚动／定位等修正。开发期修改测试不等于绕过冻结，但也说明测试设计不是事先独立确定。
- 对保存的 8 个发布候选逐个取样：tests/acceptance.mjs SHA-256 均为 `e630375904db4e432ab27df7e7cd5e17c5e6de996032eb28dcee02648fadab38`，sample.pdf 均为 `24c0c60ec35d0ddb04766336ab1970b764eded954ada16ed2a082c471c0b759e`。后期改夹具生成脚本不等于这份冻结 PDF 的字节变化。
- 仅见一个冻结 native digest `e8e95f84...`；最终 adapter 记录 previous=current，changes=[]。该记录自身不能代替历史，但与上述候选逐一相同的脚本／夹具哈希相互印证。1500ms 断言没有在后期变大。
- 当前 native-test 机制允许定位和有界等待适配、追加检查；保留旧案例签名及支持逻辑／夹具身份，未执行的引导计划只有凭宿主记录才能修订。本轮正式失败后的主要修改落在产品与环境。

因此本轮漏检的首要解释是**冻结了偏窄的测试，而非查到模型在失败后把正式测试改绿**。

## 六、最终验收确实执行了什么

GUI 规则绑定当前需求及 UX，有 11 个带 F 编号的 node:test 案例。最终报告记录 38 次交互、41 次断言，initial 阶段 10 个案例，真实 reopened 阶段 F-008 一例。宿主运行模块、采集实际测试事件，要求每项有断言、整套有交互，不接受跳过／未执行／未知 F 编号当通过。

此外还运行产品实际模型客户端入口的本机 HTTP 探针：`real_request / auth_error / model_error / rate_limited / invalid_response / unconfigured`。这里的 real_request 指实际调用客户端并访问本机测试服务，**不是访问真实供应商**。当前实现要求 5 次 HTTP 请求和 6 项有效结果。静态安全、LAUNCH 正常窗口启动／响应／稳定／关闭、候选源码与依赖身份检查也参与最终裁决。

执行独立性和标准独立性必须分开：本轮宿主独立运行了测试，但测试、sample.pdf 和 GUI 中的 HTTP mock 都由实现模型编写。最终 `independent.status=disabled`，没有 B 模型独立设计或外部数学质量验收。

## 八、宿主裁决和结果表达的问题

当前 `verifyLeanBehavior` 将 GUI 整套 status 赋给所有 covers，然后和特殊能力结果合并；当通过时，需求的 implementation 也按 verification=passed 推导为 implemented。这样编号覆盖和窄案例通过被提升成了全需求实现结论。反方向上，单个 GUI 性能／导入失败时，回执常把全部 11 项列为 failed，不能表达“某项失败、其它未执行或已有局部证据”，也增加模型定位噪声。

凭据机制本身有价值：running 写前失效、完整通过才可复用、五分钟有效期、绑定需求／UX／规则／源码／运行环境／宿主实现，交付前再次核对候选版本。本轮未查到失败凭据直接放行、原生测试跳过或跨候选旧 PASS 被用于交付的证据。不过最新凭据会覆盖旧状态，adapter同digest记录也会覆盖同名元数据；历史还要从会话与失败候选拼接，审计性仍可提高。

模型的 verify_app 通过后，宿主收口、长期型用户确认都可能再验同一候选。本轮确有不同 evidence 目录和较晚凭据，用户点击后又等待数分钟。这增加成本但不增加标准独立性。源码有严格缓存键，现场又存在本聊天同步构建宿主的情况；缓存失效究竟来自哪些输入，当前记录不足以独立归因。不能简单建议跳过复核；应先记录命中／失效理由及耗时。

用户看到 completed、11项 passed、implemented，很容易把它理解成“教材讲解、完整推导和单步追问均已验证”。生产收口文字确实提示真实供应商效果尚未测，但其边界没有体现在逐项状态中。当前状态适合表达“本机固定场景和客户端契约通过；AI 质量待验”，而不是完整教学需求的验收证明。

## 九、建议的改进顺序

1. **优先补验收语义与结果分层。** 每项分别记录本地行为、协议契约、真实外部效果和独立设计来源；覆盖编号不自动推出全部 implemented。F-005/006/007 的真实教学质量在缺证据时明确待验，保留本机试用能力，不擅自增加付费调用。
2. **加入能区分对象身份的反例。** 同资料两题再追问旧步骤；A资料已有笔记、B资料新回答后回看A；合法块ID配错误quote；搜索命中后换资料。判断引用必须核对原文，不只看ID或标签。
3. **平台供给通用验收设施。** 提供独立的标准PDF/DOCX、多文件／损坏文件夹具及可控AI服务，记录产品实际发出的上下文和回答来源；避免每个生成项目重新写测试服务器和文档生成器，也不要让“设施可用”替代业务预期。
4. **改善诊断与隔离。** 返回每案例及每功能 passed/failed/not_run，保留最先失败的引导错误；将渲染响应、自动化等待和窗口可见性分开计时。对发布副本依赖解析先定位平台／打包问题，再决定是否应重写成熟文档解析库。
5. **记录验收历史和缓存原因。** 每次保留需求／规则／候选／宿主版本、测试阶段、检查层次、是否复用及失效原因。确认阶段按变化决定复核范围，保留已有防旧PASS门禁。
6. **再做A＋B固定任务对照。** B 独立设计应优先覆盖上述关系反例；比较漏检、误报、产品修复／设施排障、用户介入及实际总费用。当前单例没有对照组，不足以证明第二模型收益或平台优劣。

本报告只评估并提出改进顺序，未修改代码／真实项目以改变这轮结果，也未重新签发PASS。文档本地提交，不 push；用户原有生产流程文档两行改动保留。
