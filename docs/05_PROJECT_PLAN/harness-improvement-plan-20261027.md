# Harness 改进与可选建议恢复计划

日期：2026-10-27。检查基线：`sprint2 / c8aeb28`。

## 目标与本轮范围

按用户确认的方向，先减少验收设施排障和试用中断，再实验多模型的独立验收价值。本轮恢复原有“AI 灵感建议”的用户能力，并规划后续批次；不在本轮顺带重构验收、试用或启用第二模型。

现状：旧 `generateAgentIdeas` 与需求/PRD 弹窗仍在，但 `lean-v1` / `software-v1` 由 `handleLeanGuide` 整理短任务单，跳过了旧建议链。恢复用户能力不应重新启用整条旧 PRD、研究或审计流程。

## 批次 0：恢复需求确认时的可选建议（本轮实施）

- 在现有任务单整理请求中同时给出 0–3 条具体建议；宁缺毋滥，无额外模型调用，不冒充网络调研。
- 需求确认主面板展示建议、用户价值及采纳后应出现的行为，默认不勾选。
- 未采纳的建议不进入需求、UX、实现或验收；不改变原有约束与范围外事项。
- 采纳操作只根据宿主持久保存的建议合并功能，保留原 F 编号和原行为预期；更新任务单后由用户确认，整个采纳/回显过程不调用模型。
- 建议绑定当前项目、会话与任务单版本；过期或未知建议不得套到新任务；暂停/重启可恢复，不重复生成。
- 明确“直接做”时沿原目标开工，不能把附带建议自动视为授权。
- 不新增付费测试，不改用户已有项目或进程。只在隔离数据和模型替身下验证新增链路，并检查实际渲染。

验收：无建议时旧流程兼容；生成建议仍只有一次整理调用；采纳保留原需求并形成新确认版本；旧卡/未知 ID 拒绝；重启回显不消费建议或模型；未勾选、暂停及直接做均不隐式加入建议；界面可用键盘勾选且忙碌时禁用提交。

## 批次 1：验收证据隔离与具体故障诊断

1. 宿主为开发观察和正式验收分别提供工程外 `evidenceDir`，测试上下文与平台截图统一使用；保留源码和依赖字节保护。
2. 测试结束对候选做结构化差异核对：新增/删除/改变的相对路径、类别、相关步骤；明确测试输出误入程序目录时的修复位置。
3. 统一 product_assertion / test_adapter / environment / harness 故障信息，提供期望、实际、允许修改范围和下一步；不让模型靠扫描宿主代码猜协议。
4. 定位、等待与导航修复和业务输入/断言变更分开处理；冻结的业务语义保持不变，安全的测试适配有明确更新入口和版本记录。

验收：故意产生截图不会污染候选；故意修改业务源码/依赖仍拒绝；报告可指出具体差异；取消/崩溃/写盘失败不会复活旧 PASS；同类设施错误不驱动盲目修改业务程序。

## 批次 2：独立持续试用

- 区分用户试用、模型调试和自动验收，使用不同进程身份和数据目录。
- 有可运行版本即可提供明确标记的试用入口；自动验收不关闭用户试用实例。
- 试用绑定明确版本；更新成功后提示切换，失败时保留上一可用试用版本。用户反馈记录所见版本。
- 区分演示原型、测试数据试用、正式用户数据；不把草图或截图伪装为运行程序。端口、单实例锁、残留进程和退出清理统一管理。

验收：验收开始/结束/失败期间试用仍可操作；数据互不污染；切换项目或版本不串实例；Bloma 重启后的未知 PID 不被接管；交付后仍从已验证候选启动。

## 批次 3：小范围引入第二模型的独立验收设计

- 位置：需求和界面确认后、实现前。模型 B 根据需求与确认设计提出关键业务输入及预期，优先不读实现；模型 A 实现和修复。
- 宿主冻结业务预期，确定性执行与裁决；B 的意见不是 PASS。定位和测试适配不能降低预期。
- 可选增加对真实画面/操作结果的独立视觉检查，补充窄 DOM 断言的盲区；不以视觉审阅替代数据和业务断言。
- 能力与渠道显式配置，有界调用、超时和费用分摊；缺 B 时明确状态，不默默自审冒充独立。
- 建议机制与验收机制分开：建议默认可忽略；只有用户采纳并确认后的功能才进入必需验收。

启用前置：批次 1 稳定；当前渠道、余额、价格、累计账本与请求前金额保护经核对，并有明确的新测试预算。规划不是新增付费运行授权。

## 批次 4：固定任务对照与取舍

固定同一批任务、确认目标、可用预算与验收目标，对照单模型与 A+B；保留全部失败、中止和人工介入记录。

指标：首次可试用/最终交付耗时、产品修复与设施排障耗时、真实缺陷漏检与误报、总费用/物理请求、用户介入次数。不能把最后修好的一次案例当成成功率；模型多写了测试或多做了审阅也不等于有效收益。

## 后续建议入口

本轮恢复需求确认时的建议。制作中或交付后的主动建议另做一批：允许 Agent 留下“供参考”的建议而不中断制作；用户选择本轮采用/以后再说/不采用后，才按影响进入范围确认。不能复用 `propose_scope_change` 冒充用户已提出的新需求，也不能用提建议绕过已冻结范围。

## 验证与交付规则

每批做相应的单元、宿主恢复、界面行为和必要真实进程验证，记录范围与证据后单独提交；不 push。计划和新增功能不改写此前用户的 `production-workflow-v2-20261020.md`。当前 Bloma 已在运行的进程不因本轮构建或验证被重启；新构建需要用户下次重启加载。
