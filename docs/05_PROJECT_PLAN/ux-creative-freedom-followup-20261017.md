## 2. 当前生产链核对

实际链路为：已确认 PRD → `prd-confirm` 解析模型环境 → `runUxConfirmGate` → `generateUxSketch` → 静态 HTML 与 `UxDesign` 关联校验 → 用户 UX 确认 → `confirmed.html` / `confirmed.json` 与宿主凭据绑定 → quick / longterm 实现。

- 同一提示词还固定 Windows 示意标题栏、页脚；修订时要求保留未提及部分。这些规则适合确认布局，但会限制大幅探索。
- [ux-sketch.ts](../../main/guide/ux-sketch.ts) 的 `getSystemPrompt()` 确实消费该默认值，优先允许本地覆盖。

**判断：已确认视觉方向被主动限制；不能据此宣称解除限制必然得到惊艳 UI。**

### F4：分享对话中的 Kimi → GLM 分工不能直接当成当前路由事实

- [prd-confirm.ts](../../main/guide/prd-confirm.ts) 第 372 行起，在桌面 PRD 确认后调用 UX 门时使用 `category: 'prd'`，并传入 `pending.channel_id`。

- 虽然系统存在 `sketch` 类别配置，不能因此认定这条桌面 UX 入口真的按 sketch 类别运行。实际优先级、模型名和回退必须从本次运行请求中核对。
- 抽查归档在草图生成前记录的 PRD 路由为 DeepSeek Flash，而不是链接中助手反复使用的 Kimi。历史归档配置也不能代表现在所有项目。

**判断：本轮不切换模型，也不以升温作为已证实的解决方案。首次视觉对照固定实际模型与采样参数，避免把换模收益混入规则收益。**

### F5：当前 UX 重试是解析反馈，不是看图后的设计反馈

- `generateUxSketch()` 经 [llm-call.ts](../../main/kernel/llm-call.ts) 提交文本任务，按 HTML / JSON / 引用等问题重试。
- 在该函数的生成、解析、暂存链中，未见将渲染截图回传模型后做视觉评审的步骤。现有其他阶段的截图、GUI 驱动或点选纠错能力，不等于 UX 生成已具备此闭环。
- 当前 `UxDesign` 表达页面、动作和状态关联，不包含显式视觉主张、候选方向、字体角色、项目设计 tokens 或视觉评审记录。

**判断：视觉反馈值得试，但应放在首次松绑对照之后；需要单独核对图像输入能力、截图方式与调用成本。**

### F6：输出协议存在可清理的竞争文字

内置 system 和 `buildSketchPrompt()` 的用户任务要求“只输出 HTML”，结构化主线又追加优先级更高的“只输出 JSON”。后者已声明优先，不等于主线一定失败，但会增加格式理解负担。应按是否携带背板只生成一种输出说明，并保留旧纯 HTML 调用的兼容测试。

## 4. 分阶段实施方案

### P0：先把生效输入和失败原因变成可核对的基线

目标：知道每份普通界面究竟来自默认低保真设计、关联失败兜底，还是实现还原损失。

1. 记录实际启动 home、构建提交、覆盖来源与哈希、最终装配提示词哈希、实际模型 / 渠道 / 采样参数。只导出白名单元数据，不导出密钥或整份 env。
2. 清理 F6 的 HTML / JSON 输出说明竞争；保留结构化与旧调用两条解析路径。
3. 复用已有 `ux-design-attempts.jsonl`、`ux_sketch_staged`，把 schema / 关联错误、请求失败、超时、模板或文字降级区分记录。现有 `onAttemptFailure` 可供引擎接线，避免另建一套日志系统。
4. 将草图来源纳入对照表：`llm`、`template`、文字方案分别统计；兜底结果可以如实展示，但不能计成“模型高保真设计成功”。

涉及文件：`main/guide/ux-sketch.ts`、`main/guide/prd-confirm.ts`、`main/guide/ux-confirm.ts`；测试入口：`tests/unit/guide/ux-sketch.test.ts`、`tests/unit/ux-design-contract.test.ts`、相关路由测试。

完成标准：可以从一次运行记录重建实际视觉任务的来源和接收结果；所有旧确认、停止、范围变化与防篡改约束仍通过。P0 不预设已经提高审美。

### P1：做一次最小视觉松绑对照，暂不建设新设计平台

在隔离实验输入中建立两组，先用一个共同 PRD 各生成一次：

| 项目 | E0：当前基线 | E1：开放视觉表达 |
| --- | --- | --- |
| 用户功能、PRD、F/W/AC、安全与资产边界 | 相同 | 相同 |
| 实际模型、采样、重试与金额预算规则 | 相同 | 相同 |
| 视觉目标 | 当前低保真规则 | 根据用途形成明确视觉主张，自主决定布局、字体层级、颜色和组件表现，输出完整静态高保真稿 |
| 候选数量、截图和评审 | 单个候选，统一渲染评审 | 单个候选，统一渲染评审 |
| 自动看图修订 | 无 | 无 |

本轮只改变视觉约束。三方向搜索、升温、换模型和图像反馈都后置，以免解释不清改进来自哪里。

若首对有明显价值，再用两个未针对性调试过的 PRD 各跑一对；最多先形成 3 对、6 次首轮生成，格式重试额外计数并计费。这是工程筛选，不作为统计显著性或通用能力结论。每个尝试都保存，不手修某组结果再参加比较。

评审记录具体观察，不只记总分：

- 视觉性格是否贴合用途；构图与信息层级是否明确；排版、内容和细节是否完整。
- 主操作是否容易找到，文本是否可读，空态 / 失败态是否合理。
- 同一窗口尺寸与内容下是否溢出；至少补一个较小窗口检查。无脚本稿只能证明静态状态，不宣称交互已验。
- 隐去组别、随机左右顺序后记录用户成对偏好及理由；模型自评只作建议。
- 同时记录关联通过率、模板降级、金额、耗时和人工干预；降级算该次生成结果，不能挑掉失败后只比较漂亮稿。

建议推进条件：用户偏好 E1，且需求覆盖、安全和基本可读性没有退步；两个保留任务中没有出现相同的严重回归。未达到则先定位模型输出 / 关联失败 / 视觉目标问题，不扩大架构改造。

所有真实模型调用前重新核对实际可用渠道、图像能力（需要时）、价格、余额和金额上限；token 上限不替代金额保护。历史实验额度和模型分工不自动转为本次新实验预算。本轮没有发起这些调用。

### P2：将优秀设计可靠地交给实现者

仅在 P1 获得有价值的设计后进行：

1. 从选定方向提取项目 tokens、字体角色、布局原则、关键组件和状态说明，附在版本化设计记录中；保留旧 `UxDesign` / 确认元数据的读取兼容。
2. 同步调整 quick、longterm 任务书、`PATTERNS.md`、骨架注释和形状拼装提示，明确已确认设计优先于默认视觉样式；保留桥接、状态反馈和测试锚点。
3. 对关联失败分开保留候选 HTML 与诊断，优先修正设计记录；绝不因预览漂亮而跳过 F/W/AC 校验或重新解释验收。
4. 用现有桌面壳实现一个案例，比较“高保真稿”和“真实程序截图”，并实际操作主流程、失败恢复、留存与缩放；排查字体、间距、色彩和布局损失。
5. 新规则只用于新实验与新项目；`provisionDesktopSkeletonV2()` 当前跳过已有文件，不能把“模板更新”报告成“历史项目已更新”。

完成标准：选定设计的视觉特征在真实桌面中保留，核心业务可用，确认绑定与基础验证不回退。单测证明装配和控制，截图与真实操作证明该案例的视觉及交互范围。

### P3：再分别试候选搜索和看图修订

- 候选搜索：先探索 3 个布局 / 视觉主张有实质差别的方向，再选择展开，不把三个配色版本当成三个方案；记录候选数和总成本。与单候选比较时承认额外计算投入，若要归因机制则匹配总预算。
- 视觉反馈：截图 → 具体问题及位置 → 最多 1–2 次修订；固定需求和确认范围，核对模型确实收到图片。截图失败或模型不支持图像时如实记录，不用文本猜测冒充视觉评审。
- 两项分开引入，保留全部尝试和选优过程，避免只展示最好截图。
