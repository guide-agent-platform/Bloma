# Q3：B 案例依据、争议与宿主台账

日期：2026-10-30（Asia/Shanghai），起点 `c75738a`。本批完善已有实现前 B 设计和执行路径；B 仍为可选 GUI 案例设计，未扩张到 CLI/API、C/V 费用或新模型路由。未调用真实供应商，未启动历史实验。

## 实际接线

B 继续仅接收确认需求、约束、确认设计与案例设计提示，不看实现、不使用文件/执行工具。仍使用原单次调用、超时、12 案例/每案例 32 步、单独授权、金额硬保护及共享请求预算。确认目标改变后也不能再次使用同一操作的旧 B 授权自动重发；正常同输入冻结结果仍可只读复用，不重置累计费用。

`independent-semantics.ts` 负责保留并检查 B 的业务提案。每案例增加当前 requirement_hash、逐字 expected_source 和错误面声明；断言记录预期依据：引用先前 fill 的输入（索引、值、对象必须一致），逐字引用确认预期中的固定业务值，或明确 unresolved/question。没有依据、引用别的对象、凭空编造固定值或规则未知，保留 disputed，不执行对应断言，也不把它记成产品缺陷。冻结提案本身不被修写。

每需求须有正常案例；多对象、异常、取消、重开分别给案例或带来源/理由的不适用、待澄清说明。多对象结构要求两个对象和不同输入、再次修改其中一个对象、各自断言；取消须明确 cancel 操作和其后断言；重开须有真实 restart，且重开后有断言。宿主对确认资料中明确的正向类别标记做保守检查，不能仅凭 B 的“不适用”跳过已明确提及的行为；明确排除的文本不因此变成新增要求。

这些是有界的来源、引用关系和执行结构检查，不是完整自然语言语义证明。输入回显仍可能被 B 错用于有转换规则的业务，固定值也可能被引用到错误条件；未识别到的适用性仍是 B 的声明，不能把分类数量、不适用说明或 source 引用当成完整业务覆盖。超出当前可表达依据的预期应保留争议，不编造通用计算规则或新增功能。

## 争议入口与停止条件

`challenge_independent_case` 已进入父制作工具面，只接受具体 case_id、理由和证据。它记录 `implementer_claim`，不能删除案例、改冻结断言、取消已确认缺陷或裁决为通过。未解决争议会使当前 B 语义状态未就绪，并进入验证凭据身份；先前缓存 PASS 立即失效。只有新的确认目标/独立设计及实际验证才能形成新的当前义务，不提供模型自行解除争议的按钮。

实现前遇到未就绪 B，宿主把争议和缺失覆盖记入同一 finding 台账，进入 `blocked_for_user_decision`；A 不会为了满足这些预期开工。执行中提出争议也不能继续调用 C/V 混成通过。`read_production_context(independent-design)`、`read_quality_findings` 和验收反馈提供当前来源、覆盖、案例状态及未知项。缺少适配控件不等于缺少产品功能，不能擅自添加范围外功能迎合 B。

## 执行、复现与关闭

- 从 Q1 模块提取 `quality-ledger.ts`，继续使用同一工程外原子台账；没有另造台账或 Agent 引擎。C/V 的身份、图片授权和关闭约束保持原路径。
- B 各案例用独立的短临时数据/浏览器目录，防止上一案例污染下一案例；同一案例的 restart 段保留该案例数据，执行真实重开。证据使用独立运行 ID 和案例序号目录，报告记录完整候选 ID/源码身份，不靠长目录名承担身份。临时目录删除前核对解析后的绝对父目录和前缀，失败截图与报告保留在工程外。
- 每案例分别记录 passed、failed、unverified、not_run。仅实际 `GUI_ASSERTION_FAILED` 对应冻结 expect 才确认行为失败；缺适配器、定位/环境错误及语义争议保持未验证，不硬判为产品缺陷。逐案例保存 incomplete 进度，取消或中断不把部分执行变成完整通过。
- `verifySoftwareCandidate` 将 B 的宿主观察接入共享 finding：绑定冻结设计版本、案例、需求、候选、规则和原始失败摘要。正常执行过程中保留验证锁，不能在异步台账写入阶段重叠另一次验证。
- A 通过原 `check_quality_finding` 对 B 案例复测；只能重跑原冻结设计，不能拿同名的 A 自测冒充。先有真实失败，再有当前候选的同契约通过，并且整体核心/独立/启动验证通过，宿主才关闭。争议导致整体验证未就绪时，复测工具返回错误，不能把历史 closed 标签当作本次成功。
- 确认需求被移除或预期改变时，旧 B 意见可标 superseded，保留历史，不计为修复成功。仅 B 设计更新、删除/重命名案例不能消除同一确认预期下已复现的缺陷。跨设计的原案例迁移和裁决仍需明确处理，缺少原契约复测时保留未闭合，不能套用新 B 的 PASS 关闭。

## 验证与证据

新增 `independent-quality.test.ts` 使用受控 query 生成一次 B 提案、真实 Node/browser 软件及现有宿主观察器，不调用供应商：

1. A 自测只检查 A 保存，实际通过；B 多对象案例修改 A 后发现 B 被污染。B 的正常、取消、空输入及重开案例各自保留状态。修复实现后，原冻结案例复测通过，台账保留失败与通过，B 设计字节未改、设计 query 总数仍为 1。
2. 实现者再对已验案例提出争议，不能传入 resolved/closed；旧验证缓存失效，当前 B 状态转未就绪，不能借“B 错了”跳过案例交付。
3. 未确认的新预期不执行，生成 disputed finding；正常制作入口在 A 或新 B 请求之前等待澄清，需求指纹不变。缺适配器只产生未验证 finding，不伪装已复现产品缺陷。
4. 对象引用错误、无来源固定值、只有多对象标签、取消后未验、终止于 restart、规则 unresolved、以不适用跳过已明确类别等反例均检查；未知功能编号和可执行步骤沿旧拒绝规则处理。
5. 原 B 授权、单次请求、超时/中断、冻结字节、适配器、安全预算回归继续执行；增加“确认目标改变也需新 B 授权”反例，不使用旧证明再次花费。
