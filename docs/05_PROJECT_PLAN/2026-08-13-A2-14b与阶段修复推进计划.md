## 工作项 1：对话阶段如实性修复（当前缺陷，不依赖 Sprint 3）✅ 已完成

> 目标：用户问「好了吗」时，模型按**项目存储的真实阶段**作答，不再错报「还在草图阶段/还没收到完成通知」。

### 需要完成的内容

1. **护栏改用权威阶段**：`main/orchestrator.ts` 的 sketch_ready 护栏从「只查 `input.current_stage`」改为「以 `findProject(project_id).current_stage` 为准，项目索引缺失才回退渲染端上报」——与编程路径注入逻辑（`buildProgrammingSystemTurn` 的 authoritativeStage）保持一致。
2. **渲染端阶段同步加固**：权威阶段解析提前到 `runAgent` 顶部（`recordSessionActivity` 之后），引导路径 `shouldUseGuideAgent`、sketch_ready 护栏、编程路径 `buildProgrammingSystemTurn` 统一读 `authoritativeStage`，渲染端上报仅在项目索引缺失（如测试环境）时回退。
3. **编程路径如实回答 ready**：`buildProgrammingSystemTurn` 补充规则——阶段为 ready/completed 时直接告知「项目已经生成好了，请看右侧预览区」，不得用「还没好」「还在生成」措辞。
4. **测试**：`tests/unit/orchestrator-sketch-ready.test.ts` 增加用例——项目存储已 `ready`、渲染端上报 `sketch_ready` 时，护栏不拦截、SDK 历史注入 `当前项目阶段：ready`，模型回复如实。

### 验收标准

- `tsc --noEmit` 通过 ✅。
- `npm run test:all` 全绿（含新增用例）✅（161 用例，7 套件）。
- 手动：新建项目→确认草图→MVP 完成后，问「好了吗」应回「已经好了/请看右侧预览」。

### 预计改动面

`main/orchestrator.ts`、`tests/unit/orchestrator-sketch-ready.test.ts`。已完成，改动小。

### 附带修正的行为变化

`tests/acceptance/sprint0/agent-storage-lifecycle.test.ts` 的 `S0-STORE-006` 原以渲染端上报 `generating_mvp` 进入编程路径，但 `createProject` 后项目存储阶段实为 `clarifying`——改权威阶段后该消息被正确路由到引导路径。已让该用例 `updateProject(... current_stage: 'generating_mvp')` 使存储与上报一致，回归其验证「存储生命周期」的本意。

## 工作项 2：Sprint 3 · A2-14b LLM 生成型 MVP（核心）✅ 已完成

> 目标：从「模板优先」升级为「按已确认需求真实生成可运行代码」，让用户要的计算器真的被生成出来。

### 落地说明（2026-08-13）

- 新增 `main/mvp-engine-llm.ts`：`generateMvpLlm()` 经 SDK 流式查询生成真实可运行代码；模型可写白名单 `index.html`/`src/*.js`/`src/*.css`，`package.json` 系统重写、`static-server.js` 系统接管（模型 content 一律忽略）；路径穿越/绝对路径/白名单不匹配 → 整批拒绝走模板兜底；120s 硬超时（超时→模板、外部取消→抛错）。
- `main/programming-orchestrator.ts` 的 `runMvpTask` 接入 LLM 路径 + 模板兜底（`resolveMvp`）；`run_command` 强制覆盖为 `npm start`（真实沙箱启动仍硬编码 `node static-server`）；`resumeBlockedFlow`（mvp_repair）透传 `query`/`channel_id`。
- `buildSdkEnv`/`SDK_ENV_ALLOWLIST` 从 `orchestrator.ts` 移至 `channel-manager.ts`（orchestrator 重新导出，保持既有测试 import 兼容），打破 orchestrator ⇄ programming-orchestrator 运行时循环。
- `main/orchestrator.ts` 新增生产侧 `getSdkQuery()`；`main/ipc.ts` 确认草图（accepted）时经 `getSdkQuery()` 透传 query 给 `runMvpTask`；`shared/types.ts` 的 `ConfirmSketchInput` 增补 `channel_id?`。
- `main/gwt-service.ts` 增功能断言模式：LLM 产物按「四则按钮 + `src/app.js` 含 `calculate`」判定（同源拉取 `/src/app.js`），模板产物沿用原文匹配。
- 测试：`mvp-engine-llm.test.ts`（12）、`mvp-engine.test.ts`（+6）、`blocked-decision.test.ts`（+1 resume LLM 路径）、`gwt-service.test.ts`（+1 功能断言）、`ipc.test.ts`（+1 query 透传）；同步修正 7 处 `channel-manager` mock（`importOriginal` 保留 `buildSdkEnv`）与 `mvp-testing-flow` 的请求计数。

### 需要完成的内容

1. **MVP 生成接入真实模型**：在 `main/mvp-engine.ts`（当前纯模板、确定性）旁新增 LLM 生成路径（A2-14b），输入为 `sketch_generated` 事件落盘的 `requirements`（`main/project-service.ts` 的 `readLastSketchRequirements` 已有此能力），经 SDK 生成 `index.html`/`src/app.js`/`src/styles.css` 等真实文件。
2. **模型失败兜底**：LLM 生成失败/超时/空输出时回退当前模板路径，保证管线永不因生成中断——沿用现有 snapshot + health + 测试链路。
3. **与既有链路衔接**：生成的文件仍走 `runMvpTask` 的快照归档、GWT 测试（`runPostMvpTestingFlow`）、`ready` 广播，不破坏现有状态机。
4. **测试**：A2-14b 单元测试（mock SDK 生成计算器代码 → 断言文件落盘、快照归档、测试进入）；失败兜底测试；端到端 feature 场景补一条「生成结果为真实计算器」。
5. **进度广播**：生成期间通过 `stage_changed` 广播 `generating_mvp` 各子步骤（若可行），供工作项 1 的如实回答依赖。
