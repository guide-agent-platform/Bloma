# 学期任务台：从零真实制作与独立业务测试

2026-10-25，北京时间；宿主源码基线 8154e25。结论：**生成的程序通过独立业务复验，但 harness 没有完成正式验收和交付，整条自动交付通路本次判为未完成。**

## 案例与方法

新项目 063292c4-8693-48ba-b9d9-5662f9cca830，新会话 30ff26a2-5e86-4042-b239-f90e1debb80a。不是旧项目续跑，也没有复用笔记本程序。隔离测试 home 与浏览器配置，使用 DeepSeek 官方 deepseek-flash。

通过公开项目创建 IPC 处理器和生产 runAgent 服务，依次执行真实需求提炼、需求卡确认、草图生成、提出一次草图修改、草图确认、制作与真实浏览器调试。没有替换 SDK，没有由控制器代写业务程序或修改正式验收规则。测试操作者审阅实际需求和截图后，选择现有确认选项；这些测试确认不冒充用户亲自审阅。

案例包含课程、任务、学习记录三种实体及关联：课程新增改名与关联删除保护；任务编辑、日期、优先级及状态；组合筛选与搜索；正整数学习时长；四项实时统计；JSON 文件下载、整体恢复、重复导入；非法文件拒绝与原数据保护；本地持久化。8 项需求全部保留，制作过程不再错误地成为第 9 项业务功能。

原始需求和独立业务计划在模型运行前写入 request.txt 与 independent-plan.json，预检记录两文件摘要。独立检查只适配真实控件定位和备份字段名，没有降低业务预期。全程无 Computer Use、不占用鼠标键盘；浏览器交互使用 Playwright。

## 完整通路为何没有完成

最终 projects.json 仍为 active / generating_mvp，desktop_blocked.reason=verification-incomplete，说明为 MONETARY_BUDGET_EXHAUSTED。未找到正式 GUI 验收登记文件，也没有 active.json 验证版本；工具事件中 register_gui_check 和 verify_app 均为 0 次。因此不能把独立测试通过写成正式交付成功。

新增测试沿用用户之前明确授权的追加 3 元窗口，初始已计价 0.180077 元。本案例 40 次物理模型请求，计价上界增加 0.661318 元；窗口合计 0.841395 元，剩余 2.158605 元。

当前每次请求按 1,048,576 输入 token 和最多 8,192 输出 token 预留，官方峰值输入 2 元/百万、输出 8 元/百万，因此单次预留为 2.162688 元。剩余金额比该预留少 0.004083 元，下一次请求不能准入。保护按设计正常拦截，**不是供应商余额不足，也不代表已实际消费接近 3 元**。没有重置计价、减少未知责任、另开预算或绕过 guard。

旧第一窗口仍保留已报告 0.747882 元及中断请求最坏预留 2.162688 元，原总上界 2.910570 元不变。新增窗口 0.841395 元与旧窗口合计责任上界 3.751965 元。所有费用是 token 计价上界，不是供应商精确账单。

## 此次具体暴露的不足

1. **草图默认状态质量不稳定。** 第一版把空名、非法时长、关联删除、导入失败等提示同时铺开，统计总数与课程样本数不一致，样本日期陈旧。正常反馈后错误提示与数量、日期改善，但导航分区反馈仅部分兑现，仍有长页。已保留原版和改版，不把“重画成功”直接当作质量通过。
2. **调试工具缺少直接选择下拉选项的动作。** 模型对 select 误用 fill，实际失败；随后将任务筛选、任务课程/优先级/状态从 select 改成按钮组。gui-observer.ts 的 fill 直接调用 locator.fill，公开动作集合没有 select。可用按键路径不能消除这个常用能力缺口；本例出现了为适配测试能力而改变产品控件的返工。后者为工具事件与代码差异支持的判断，不是已量化的普遍结论。
3. **调试与收口顺序仍低效。** 制作阶段 39 次工具调用：14 次 edit_file、10 次 inspect_app；其中 3 个工具错误包括 2 次修改源码后忘记 reload 和 1 次下拉填充误用。到预算保护触发仍未登记正式验收，没有完成“先保证可验收、再继续打磨”的收口。
4. **测试预留策略对小额预算过于保守。** 两轮草图约消耗本案例计价的 37%，随后全上下文预留提前阻断正式收口。需要改善可证明的请求费用上界、预算展示和收口优先级，不能简单删除费用保护或把小额 token 费用当作无上限授权。

产物本身在这组冻结业务场景下表现好于平台终态所暗示的结果；harness 的效率、草图可靠性和交付收口仍需修复。没有据此得出比其他 agent 更好或更差的统计结论，也没有宣称所有输入和使用场景都无缺陷。
