## 发现与修复

| 范围 | 已确认问题 | 修复后的行为 |
| --- | --- | --- |
| AI/连接器密钥补偿 | 公开配置已rename成功，但锁清理失败使调用抛错；原补偿会删除新配置已经引用的Key | 补偿前重读公开引用，只移除能证明未引用的新密文。引用已提交或状态无法读取时保留密文，返回明确“保存结果需核对”，重新载入可使用实际已保存Key |
| 任务退出与写盘失败 | 不合作handler使close无限等待；重复close可能重复关闭fd；running状态写入失败会留下永远占用的active槽位 | close默认最多等待5秒，可显式0–30000ms；超时标interrupted/needs_review，返回closed:false，保留owner。handler真正退出后才释放；进程已退出后才可显式恢复死owner。首次状态写入也在try/finally中，close幂等 |
| 同步回执目标 | 原回执仅绑定连接ID和来源，修改写入目标后仍可能返回旧“done”；队列去重也可能挡住真正的新目标操作 | 回执绑定实际写入URL、方法、网络及凭据引用/鉴权作用域；显示名称不改变作用域。队列输入绑定连接修订，异步取Key后再次核对，旧配置不发送。无目标作用域的旧回执须人工核对，不自动当成功或重发 |
| 人工核对与重试 | 将未知写入确认成not_applied后，同请求仍被旧记录拦住，无法显式再试；网络返回可能覆盖并发人工核对 | 保留每次尝试记录。人工确认未执行或已知拒绝后，下一次显式提交可创建新尝试；不自动重试，同一目标和同一输入最多10次尝试。pending/unknown仍不重发；已完成的人工作用域核对不被晚回复覆盖 |
| JSON语义比较 | 同版本记录中对象键顺序不同会误报版本冲突 | 数据比较与任务输入摘要使用规范JSON顺序；数组顺序仍有意义。未修改既有备份校验格式 |
| 效率分析输入与存放布局 | 未知variant可能进入配对并抛异常；JSON证据和样本同目录会互相误识别 | 异常样本、缺成对variant、非法证据结构均拒绝比较。新记录采用samples-v2子目录；旧布局明确要求迁移，原文件保持不变，不重置真实账本或丢弃失败样本 |
| 任务错误脱敏 | 任意全大写handler异常会被原正则视为公开code，可能把秘密样式文本送到界面 | 只允许固定组件错误码；其他异常返回TASK_FAILED并保留原因摘要及unknown依据，原始消息不进入任务公共结果 |

首轮9条反例有8条出现异常、1条确认迁移失败保留原数据；同一根因的AI/连接器两条不算两个独立可靠性样本。另写全大写异常反例确认公开错误泄露路径。JSON证据布局问题来自源码复核并加入正反例，不能把后补检查冒充首轮已执行。

## 长期使用补齐

原队列把全部历史计入1000条限制。本轮增加显式 `archive(ids)` / `history()` 及工作台“归档已结束任务”：保留完整输入、检查点、结果、错误和去重凭据，释放可见任务容量；相同请求返回archived:true而不重新执行业务。仍受记录库32MiB/2万条总量限制，不承诺无限历史。未核对的外部副作用、活动任务和interrupted任务拒绝归档。

归档是保留历史，不是清除去重或计量。界面对“已归档请求”和“新任务已入队”分别显示。暂未增加密钥删除/未引用密文清理UI；本轮只修复补偿的一致性，不自动删除无法证明安全的密文。
