## 应处理项

### H01 · P1 · 约束提取的 60 字、5 条与固定前缀会丢掉真实用户约束

位置：`main/guide/constraint-extractor.ts:31`、`:33`、`:56`、`:60`、`:80`、`:165`。

- 单个子句超过 60 字直接 `continue`，没有保存、分页、待确认或遗漏标记。注释称“截断保真”，实际是整条跳过。
- 同条消息提取到 5 条就 `break`，第六条即使明确合法也不会进入确定性约束列表。
- 仅凭“补充说明：”“目标：”等正文前缀判定合成轮，真实 user 消息也会整轮被跳过。

反例已复现：`必须离线;不要登录;禁止联网;必须导出;必须备份;不得上传数据` 只返回前五条；75 字的明确“必须……”约束返回空数组；真实 user 轮 `补充说明：不得上传数据` 扫描结果为空。

**影响边界：**原始会话仍可能保留原话，模型也可能从原始历史理解它；本次没有证明平台实际上传数据。但“确定性持久化保证长期不遗忘”的覆盖被这些固定过滤破坏，历史重扫仍应用同样的过滤，不能补回。

建议：约束事实完整保存，长度/条数限制只用于展示或分批处理；合成消息依据持久化的来源身份标记过滤，不能依赖普通用户也会使用的句式。预算不足必须显式报告未处理范围。

### H02 · P2 · 关键任务最多 6 条，与“全部 P0 必须覆盖”冲突

位置：`main/model/prd-backplane.ts:229`、`:232`、`:233`、`:240`；`main/guide/prd-engine-llm.ts:636`；消费者 `main/coding/delivery-status.ts:220`。

LLM 任务先截 4 条，每条功能引用先截 6 个，补齐 P0 时总任务数再封顶 6 条。反例：7 个 P0、LLM 未给任务，定稿只覆盖 F-001～F-006，F-007 丢出关键任务清单。重复的 LLM 任务还会占用总名额，使更少的不同 P0 就能触发缺口。现有单测甚至直接锁定“总量截 6”，没有验证完整覆盖不变式。

**适用边界：**关键任务挂载取决于 `BLOMA_KEY_TASKS`，缺省关闭；已有背板中的任务仍有消费者。这不意味着今天的桌面核心验收会漏验 F-007，`core-verification` 另按全部 requirements 校验。本问题在关键任务承诺、确认卡及相关交付状态路径，不应扩大成“当前全部验收只测六项”。

建议：任务可以合并、分页显示，但必须保留每个必交功能的关联；生成不足时完整补齐并验证覆盖，不能用总条数破坏不变式。

### H03 · P1 · 停止词子串直接控制流程，误把产品需求当作叫停

位置：`main/desktop/user-intent-lexicon.ts:22`、`:44`、`:49`；实际消费者 `main/desktop/desktop-route.ts:396`。

中文使用 `includes`，没有识别动作对象、引用或否定。`增加取消按钮`、`任务执行时显示停止按钮`、`不要停止，继续执行` 都返回 stop。

不仅是纯函数问题：路由反例确认 `增加取消按钮` 使项目写入 `desktop_blocked.reason=user-stop`，调度员根本没有启动。

**适用边界：**发生在桌面消息进入停止意图分支时；交付后反馈、MVP 确认反馈等较早分支有自己的处理，不能说所有阶段都这样。

建议：明确短指令和结构化停止动作可直接暂停；普通产品描述需识别指令对象与否定，保留快捷停止出口。继续增加排除词不能解决这一类语义冲突。

### H04 · P2 · 需求关键词直接决定能力义务和验收探针

位置：`main/desktop/core-verification.ts:115`、`:120`、`:127`、`:148`；`main/model/prd-backplane.ts:271`、`:279`。

当前仍用描述文字识别语音、模型和前缀改名能力：

| 输入反例 | 本次观察 |
| --- | --- |
| 不需要语音识别 | 即使普通场景通过，仍要求 ASR 登记并返回 unverified |
| 不需要真实模型调用 | 仍要求 llm 登记，返回 unverified |
| 联系人按编号前缀筛选并支持给联系人改名 | 触发文件系统前缀改名探针；本地注入“不支持联系人接口”的探针返回后，核心门为 environment_blocked |
| 按日期整理本地文件 | CAP 派生器把“整理”变成“由真实模型调用完成”的义务 |

前三条验证了宿主的实际选择/门禁逻辑，文件探针执行被替身隔离，没有执行真实产品或文件改名。CAP 派生挂载取决于 `BLOMA_CAP_CONTRACT`，缺省关闭；不能把这个条件风险说成所有项目当前都强制使用模型。

今天较早的机制修复已阻止“跨功能拼词”和“无关撤销”误触发，**该修复有效，不能重复报为未修**；这里是同一功能内的对象歧义、否定和能力推断仍有问题。专用探针本身的固定反例有价值，问题在于适用条件不可靠。

建议：确认需求时记录明确的能力类型、操作对象和实际入口/适配协议；验收读取该声明并绑定需求版本。固定 Logic 接口应作为平台支持的适配协议明确公布，未支持的能力报告适配缺口，不能通过删除失败门禁获得绿色结果。

### H05 · P2 · 8 KiB 展示摘要被用作验证事实源

位置：`main/desktop/process-driver.ts:246`、`:362`、`:387`；`main/desktop/core-verification.ts:107`。

驱动先从完整 stdout 解析场景，报告另保存 `stdout.slice(0, 8192)`。核心验收却再次解析这个截断后的 `stdoutExcerpt`，没有使用完整的场景证据。

反例：9919 字符的输出，前面是诊断日志，尾部 `PASS actual_input`。真实驱动编排返回 pass，并已解析到 actual_input；核心门仍把该场景读成 unverified，还提示名称不一致，提示中的实际名称却与登记名相同。

**判定：**8 KiB 作为人读摘要合理，作为验收输入不合理。本次证实的是错误拒收，不能说它在这个反例里产生假通过。

建议：完整输出流解析后生成结构化、按确切登记场景聚合的证据；摘要只用于显示。不能简单切换到现有 `report.scenarios` 就结束修复，因为现有驱动解析器对空格场景名及多种输出方言的语义还需统一，重复 FAIL 必须保持从严处理。

### H06 · P2 · 桌面路径固定 640000，覆盖调用方的显式输出预算

位置：`main/desktop/desktop-route.ts:260`、`:509`、`:706`；对照 `main/orchestration/stages/agent-dispatch.ts:151`、`main/platform/llm/model-resolution.ts:193`。

上游按渠道得到 maxTokens，`DesktopRouteInput` 也声明了该字段，但内部阶段输入未传递它，启动调度时直接写 640000。独立路由反例：传入 4096，真正交给 dispatcher runner 的是 640000，实验开关关闭。

640000 作为用户历史指定的缺省值可以保留，不能因此覆盖渠道/调用者的显式值。实验绑定之后另有模型预算和传输层上限，因此本次没有证明实验配置的请求、金额或供应商硬限额被突破；问题明确位于普通桌面接线的显式配置传递。

建议：将预算作为运行上下文传递，缺省值在单一解析入口决定。实验的显式冻结策略单独按其条件执行；不能为了修这条而改写旧样本或擅自降低用户设定的 640000 缺省。

### H07 · P1 · 固定全局密钥缓存名，切换配置源后仍会使用旧来源

位置：`scripts/multi-vendor-run.mjs:42`、`:44`、`:106`、`:119`；相关 `scripts/channel-key-reader.cjs:27`。

辅助多厂商脚本把解密结果放入两个固定临时文件名，缓存命中只看 30 分钟 mtime，不核对 home、渠道文件、user-data 或来源指纹；TTL 只控制是否复用，不会自动删除明文缓存。读取器还会打印密钥前 10 字符。

已用**源码中的原始 loadKeys 函数和内存假文件系统**复现：请求来源 home-B，命中 fixture 中 home-A 的缓存，key reader 调用数为 0。只使用公开的假字符串，没有读取、输出、改动任何真实凭据。

**影响边界：**该辅助脚本可在不同配置源或并发运行间串用账号/渠道；默认缓存位置也留下明文凭据。这不是主程序 safeStorage 已失效，也不是已证明发生错误扣费。

建议：凭据留在受控进程内传递；若确需临时文件，使用单次唯一、权限受控并在 finally 清理的路径。任何缓存必须绑定配置来源与版本，并避免打印密钥片段。修复无需读取现存密钥内容。

### H08 · P2 · 历史模型与账号选择固化在通用多厂商工具中

位置：`scripts/multi-vendor-run.mjs:42`、`:48`、`:52`、`:60`、`:130`、`:138`；入口仍在 `scripts/README-automation-tools.md:11`。

脚本强制三模型、中文渠道名、智谱账号短 ID `97b3075f`，缺省读取 Proma `channels.json`，而 Bloma 主程序使用独立的 `bloma-channels.json`。它的注释记载的是历史特定渠道/账号决定，另有“永久承载”和“应急充值后改回”的相互冲突说明。

**判定：**对某个冻结实验，锁定模型和账号合理；留在通用工具入口、默认套用到后续项目不合理。这里不能依据旧记忆把今天 M1/M2/V 改回 2026-10-13 的配置，当前制作实验使用自身已冻结配置。

建议：保留历史 profile，将角色、完整渠道 ID、模型和来源配置移到显式、版本化的执行 profile；运行前显示实际绑定并校验。缺配置明确失败，不默认改用另一家模型，也不把辅助工具当作当前六组实验的入口。

### H09 · P2 · 视觉 MCP 默认仓库根目录多退一级

位置：`scripts/bloma-vision-mcp.cjs:19`、`:21`。

脚本位于仓库 `scripts/`，却以 `path.resolve(__dirname, '..', '..')` 为默认根；缺少 BLOMA_ROOT 时实际定位到 Desktop，寻找 `Desktop/scripts/vision-diagnose.mjs`，而正确文件在仓库内。

已在无环境覆盖的隔离 VM 中执行原始模块的初始化逻辑，得到默认目标 `exists=false`、正确目标 `exists=true`，未启动子进程、截图或模型。显式设置 BLOMA_ROOT 可以绕过此问题，但不修复默认入口。

建议：默认从脚本位置退一级定位仓库，显式覆盖继续保留；启动时检查目标文件，给出可操作的路径错误。
