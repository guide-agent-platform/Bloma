## 1. 目标与实施原则

目标：让 Agent 复用已验证的通用行为，把主要工作集中在业务差异、界面设计和实际问题修复；减少重复协议实现、环境排障和无效验收。优先兑现用户选择的模型多模态与通用 HTTP API／Webhook 集成。

产品模板采用可组合模块：后台接口、公开配置、必要UI适配、运行样例和独立反例一起交付。界面随用户确认设计接入；模块不强制整页换肤，不自动加入用户未采纳的功能。

沿用 software-v1、持续 Pi、现有准备工具、进程监管、候选封存和宿主裁决；不增加强制规划/审查模型阶段。首期以已有可验证的 Windows / Node / Electron 路径为主；已有 Python 客户端/产物保持兼容，新增语言适配单独登记。

所有新增准备选择器、文件名和接口均须在实施时落实到实际工具和说明，不能只增加提示词。准备组件、执行结束、本机契约通过、真实外部效果和正式交付分别记录。现有需求能力门、确认、费用和证据失效规则保留。

## 6. 共用组件交付契约

| 项目 | 实施要求 |

| 描述与版本 | 组件ID、版本、用途、适用运行时、依赖/文件摘要、公开配置schema、已验证范围、限制和使用说明 |

| 配置和密钥 | 公开默认配置随工程；运行配置和用户数据在产品数据目录；Key运行时注入或用产品自己的可信密钥存储，不进模板/报告/平台渠道复制 |

## 7. 三个固定组合场景

先编制与实现无关的需求和独立预期，再实现样例；模型生成阶段使用相同需求、设计与计量口径。可控服务和固定应用只能证明工程链路。

| 场景 | 用户目标 | 使用组件 | 必需验收 | 验证层次 |
| --- | --- | --- | --- | --- |
| C1 图片记录同步助手 | 选择两张不同图片，分别分析、校正结果并同步到指定外部记录；失败可核对 | T01、T04、T02、T03、T06 + AIService | 原图/请求/结果/记录身份一致；旧响应不串图；重复同步/通知不重复生效；取消及重开可恢复状态 | 先真实图片+受控服务；再明确配置的真实视觉服务与外部API |
| C2 团队资料归档工作台 | 批量导入文档/图片/音频，显示处理进度，检索结果并导出；处理失败保留成功资料 | T01、T04、T02、T05、T06、T07 | 混合坏文件、重复/同名文件、任务取消、来源定位、检索切换、导出读回、真实重开 | 先成熟解析与真实本机OCR/ASR、受控AI；再真实模型质量和代表性资料 |
| C3 API事件跟进台 | 拉取分页记录并接收Webhook，形成可查询状态与可追溯处理记录 | T01、T04、T02、T03、T07 | 断页/重叠页/游标提交、签名/乱序/重复、鉴权/限流、待核对副作用、重开恢复 | 先真实本地HTTP与固定业务期望；再具体供应商专用适配与真实账号范围 |

T08在上述已通过的固定候选上单独做包与干净环境检查，不重复把同一业务操作算作新独立样本。B7启动前核对已冻结的业务预期与候选身份；B9另行封存真实生成/服务对照的版本、预算和判定协议。

## 8. 验证层级、效率指标与证据

| 层级 | 证明什么 | 不能据此推导 |
| --- | --- | --- |
| L1 组件单元/故障注入 | schema、身份、状态、取消/错误及存储分支 | 完整UI、真实供应商或生成成功率 |
| L2 实际进程/本地HTTP/原生GUI | 产品入口、组件接线、文件/数据/界面操作与重开 | 模型理解质量、真实外部业务效果、安装包资格 |
| L3 独立业务核对 | 按事先需求和反例实际操作，记录逐案例结果 | 未覆盖需求全部正确；同一模型自编测试不自动独立 |
| L4 真实模型/外部服务 | 实际路由、请求、返回、业务副作用与领域质量 | 跨模型/账号/任务的通用可靠性 |
| L5 包/干净环境 | 对应包在指定新环境启动、升级和数据保留 | 所有机器、所有OS或完整发布运维能力 |

每批产出版本/任务/配置身份、命令及退出码、逐案例结果、必要截图、数据前后快照和失败原因。失败、未运行、未知与成功分开；重复复跑不累计为独立成功样本。低影响文档轮只做相关文档检查，不用大量运行测试替代内容核对。

| 指标 | 采集口径 | 判定方式 |
| --- | --- | --- |
| 首次可试用时间 | 从确认范围进入制作到实际可启动并完成主路径；记录候选版本 | 与同任务/设计/环境条件的基线比较，不把静态草图当可试用 |
| 最终交付时间 | 包含修复、宿主验收、必要人工确认与实际交付 | 不把模型结束、命令退出或中间PASS当交付 |
| 设施排障耗时 | 依赖/入口/测试适配/宿主问题单列，原因未知另列 | 核对重复故障和诊断是否缩短定位；不能把所有耗时归因模型 |
| 重复验收耗时 | 记录实际检查次数、范围、复用及失效理由 | 只有相同证据口径才可比较；不以删必需检查制造提速 |
| 请求/用量/费用 | 全链路含准备、修复、额外验收模型，保留物理请求/完整账本 | 无实际费用证据不写0元；产品AI费用与制作费用分别记录再合并比较 |
| 用户介入 | 范围调整、配置、修复协助和确认分别记录 | 用户确认不等于独立完整验收，漏记录保持未知 |
| 缺陷漏检/误报 | 从独立业务核对或人工审计取证 | 未审计不写零缺陷；单个修好案例不换算成功率 |

B9先冻结任务、版本、必要通过条件和对照方式，再运行。模板只减少了重复实现时，可以报告该事实；“更快/更便宜且质量不下降”须由上述实际对照支持。阈值应随具体任务的必需行为预登记，不在失败后改预期以取得收益。

## 9. 逐批执行、职责与变更规则

每批顺序为：核对当前代码/已有证据 → 写本批范围与独立预期 → 实现并接入 → 对应层级验证 → 记录限制/原始失败 → 本地提交和交接。默认不push。复用现有fixture、工具和上游做法，不为形式增加角色。

| 角色/输入 | 责任 |
| --- | --- |
| Codex工程工作 | 在明确实施批次内完成代码、必要验证、本地提交、文档与可接手证据；保持用户已有改动 |
| 用户方向 | 决定能力优先级、具体真实集成对象和产品目标；本计划按当前选择优先多模态及HTTP/Webhook |
| 真实服务条件 | 在使用实际模型/账号前明确可用渠道、账号/写入范围、费用与数据范围；本计划本身不创建凭据或追加费用 |
| 验收裁决 | 宿主依据绑定当前版本的实际证据裁决；独立核对补充业务反例；模型意见不能自行签发最终PASS |

新增供应商、语言、平台、公开发布或计费路径应注明对当前批次的影响。未明确的真实外部条件不阻碍本机工程进展；对应真实效果保持待验证。优先级变化更新本表及依赖，不追溯把计划改成已完成。
