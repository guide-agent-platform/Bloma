## 1. 调研方法和证据边界

先问五个问题，再筛资料：最近一个月执行底座、协作、上下文、验证、面向普通用户的产品各发生了什么变化？哪些收益有实验支持？哪些设计正在被撤销？哪些只是接口/发布变化？哪些适用于 Windows 本地软件生成？没有预设“多 Agent 更好”“单 Agent 更好”或“应该换底座”。

覆盖 10 个开源项目、6 个产品/平台、1 项标准动态、7 篇本月论文；另外抽查 3 项开源改动的实现及测试 diff。结构化来源、日期、版本、阅读深度、适用限制见 [证据清单](agent-frontier-sources-20261101.json)。这是一轮有边界的跨来源调查，不是穷尽全部论文的系统综述，也不是产品实测排行榜。

- 开源：以发布 tag 和 GitHub API 的 `published_at` 为准，stable 与 canary 分开。表中开源日期换算为北京时间，清单同时保留 UTC；不拿抓取日期冒充发布日期。
- 产品：打开官方明确日期的发布/工程原文。发布日期保留原站标注；只证明公开提供或声称的能力，不代表本次账号可用或已复现收益。
- 论文：核对 arXiv 提交/修订日期。3 篇进一步读方法、结果或局限，4 篇仅做摘要与版本级筛选，分别标注。全部未独立复现，不将预印本写成已确立共识。
- Bloma：读取当前 package 与已安装 Pi 版本、主运行分流、Pi适配、上下文、协作工具、质量门及评测绑定。实现核对与旧测试报告分开，不宣称本轮重跑了产品验收。
- 搜索覆盖产品日志、开源发布、论文和引用链；聚合榜单/社交帖子只用于发现线索。多次检索返回旧论文或无关内容，按日期和主题剔除。旧 kimi-cli 已归档，继续追查其 successor kimi-code；没有把旧仓库当作没有进展。

## 6. 证据支持哪些结论，又推翻哪些预设

| 候选判断 | 支持证据 | 反证 / 不确定性 | 决策 |
| --- | --- | --- | --- |
| 多Agent越多越先进 | Deep Agents/Goose增强异步协作 | Anthropic报告耦合专家合并收益；本地缺真正无C/V对照 | 拒绝数量导向；用隔离信息面和实际收益决定 |
| 必须换成另一成熟SDK | 多家SDK和开源底座持续成熟 | Bloma已用Pi；升级也受自定义桥、权限、计费约束 | 先审计/适配现有Pi；只有具体不满足项才做替代执行器试验 |
| 只需加更严验收 | 版本证据与宿主门仍重要 | SpecGuardBench显示验证器也可能误杀合法实现 | 同时测漏报和误报；新门必须有业务来源 |
| 更大上下文/更多记忆一定更好 | 长任务和经验复用在发展 | Kimi缩读量、OpenCode调缓冲；Bloma窗口与真实渠道可能不一致 | 测上下文投入是否产生收益，保留按需加载与失效机制 |
| 主动探索应立即覆盖所有任务 | 浏览器工具和产品化试用成熟 | 成本/环境/原生桌面覆盖未知，已有固定验收有效 | 先对复杂GUI做可关闭的小范围独立试用，固定验收不变 |
| 前沿已让现有项目整体过时 | 标准技能、异步、产品生态更成熟 | Bloma证据绑定/能力组件有真实基础；没有公平端到端比较 | 判为“运行接入与效果证据需追赶”，不作整体性能排名 |

## 7. 优化路线：每批有假设、入口和退出条件

### R0：先修正比较方法，形成小而完整的样本集

扩展既有 `harness-evaluation.ts`，不另造研究平台。把策略身份拆成模型/实际路由、runtime版本、上下文策略、B/C/V/探索是否启用、工具与技能版本；保留真实调用、失败、人工介入、账本和环境身份。“强主循环”和“多Agent协作”必须能独立比较，不能继续借B开关代称。

建议样本库覆盖6类任务：新建多对象数据应用、已有应用增量修改与数据迁移、长后台任务与取消、复杂GUI多状态操作、资料解析/API接入、语音等真实环境能力。先用其中2类作小规模pilot，确认测量链、成本与判据可靠，再按实际预算逐步扩到每类至少3次工程筛选，不一次性启动全矩阵。需求只描述用户目标；UI-only变更和中断续跑作为增量子场景。固定确认范围/外观、外部业务预期与数据；运行顺序随机或交错。

先同模型比“主循环+宿主固定验收”与当前策略；再对收益最大的错误面逐一加入C/V/B/主动探索；最后小规模换模型检查交互。研究变体只在隔离评测入口存在，不降低正常产品门。不同产品最佳配置另作体验比较，不能与同模型harness消融混为一组。

主指标：外部业务通过、误报/漏报、人工干预、失败后恢复、交付后缺陷、全部失败也计入的每成功任务成本、耗时分布。少样本只用于发现退化，不能给稳定成功率；一次错误不靠多次挑最好结果掩盖。

退出条件：先在受控样本证明策略身份没有混淆、统计包含失败，且合法/非法操作均真正执行；真实调用必须先有本批模型/预算安排。用户本次只授权调研，不据此跑付费矩阵。

### R1：优先补运行接入和上下文效率，而不是先增加角色

1. 对Pi 0.85.1→窗口内稳定1.x做API/事件/持久化/压缩差异表，单独对截断调用与结果配对建立适配回归。比较保留旧版打补丁与升级两条方案，保留回退。
2. 真实模型的输入窗口、输出/思考限制进入显式元数据；未知渠道保守回退并说明来源，不继续无差别128k，也不盲信代理宣传窗口。确认计费准入覆盖压缩与重试。
3. 沿现有context catalog增加受控技能发现与按需读取。先少量平台自有技能，固定来源/版本/触发条件；不要直接开启工程中任意扩展、prompt或系统指令。检验不用技能、错触发及失效技能反例。
4. 对read/list/grep等无副作用工具做局部并行实验；每次调用必须独立ctx/toolCallId。写入、安装、GUI状态改变仍按依赖排序；并行取消、共享账本、结果归属均须保持。
5. 错误返回提供“现状、拒因、可用下一步”，参考OpenCode失配提示；不以扩大写匹配或吞掉权限错误换成功。

退出条件：适配恢复/取消/图像/usage回归通过，原冻结验收不退化；在R0样本上实际降低无效读取、同错重试或耗时。只减少tokens但业务变差，不算优化成功。任一收益不成立便保留旧路径，不为升级而升级。

### R2：把“验收器质量”作为独立改进对象

保留现有B来源和争议机制，针对每条重要业务预期准备：正确实现、同样正确但布局/数据结构不同的实现、一个真正违反规则的实现。检验B/适配器/断言是否同时接受前两者、拒绝后者。再从历史实际失败和可解的密封缺陷样本评估C/V，而不是只让模型复述已知缺陷。

入口：`independent-semantics.ts`、`independent-quality.ts`、`independent-verification.ts`、`quality-ledger.ts`。复用已有失败/复测证据，不让测试生成者修改隐藏判据；预期不确定进入澄清，不强行定义成错误。

退出条件：合法替代实现无新增硬阻塞，已确认缺陷不能因改案例名或换候选消失；报告漏报、误报与未验证原因。若增加B成本却没有独立检出收益，应收窄触发范围，而非追加更多B提示词。

### R3：只对证据表明有必要的GUI，增加独立主动试用

在当前候选的副本/独立数据上，给试用者浏览器操作与观察权限，不给源码写入、改需求或验收台账权限。它自行选择操作序列，发现问题后输出可重放步骤/截图/候选身份；宿主确认，A修复，再复测。现有V仍可承担低成本截图审阅，不强行改成所有任务的完整浏览器会话。

先评估原 `inspect_app` / Playwright观察器能否复用，再比较Browser Use适配器；不要同时引入多个浏览器栈。Windows原生应用、麦克风与文件对话框另设能力范围，不拿网页通过冒充桌面全覆盖。

退出条件：在冻结缺陷与自然失败样本上，比现有C/V+固定验收额外发现有效问题；环境错误不能记作产品bug，探索成本可解释，取消后无遗留进程或数据污染。没有增益则保留为按需诊断，不常驻。

### R4：把能力转成普通用户可持续使用的产品

这条线可与R1/R2并行做设计，实施按前述证据选择：

- 提供“当前可用版本、这次变化、已实测路径、未验证事项、失败时如何恢复”的产物视图，反馈直接指向版本/控件/问题；复用台账，而不是向用户展示内部角色术语。
- 把已有工程导入、用户数据迁移、版本回滚和可携带交付作为与从零生成同等重要的目标。优先本机无开发依赖环境验收，再扩真实干净机器。
- 对用户明确需要AI功能的产品，把现有AIService、HTTP和工具组件组合为产品自己的任务助手；先一个可验证用例，工具动作有真实业务效果，使用产品自己的凭据。它是产品功能，不是开发流程新增一个经理Agent。
- 项目经验只沉淀经过验证、带来源与适用版本的操作知识。失败轨迹可以作为候选经验，但不能自动升格为系统规则；跨项目复用必须测是否减少重复错误及是否引入误导。

退出条件：普通用户能完成一次真实使用、明确一次修改、保留旧数据并升级到新版本；交付后实际启动和业务结果可复核。页面好看、录像存在或内部测试全绿各自都不足够。

## 8. 暂不投入及重新考虑的条件

- 不立即换掉Pi或整体吸收任何上游；先证明具体适配缺陷及替代收益。
- 不开放无边界多Agent互写/互调用；只有独立任务在真实样本有收益时，增加相应隔离执行能力。
- 不把SkillMem潜在记忆训练、自动自我改写harness、全自动夜间记忆列为近期主线；当前API/预算/可信验收条件不匹配。
- 不复活旧PRD内审、旧实验驱动或以新名重做已经退役流程。
- 不按公开排行榜挑一个“最强模型”替代对照，也不把公司案例的速度/成本直接套到Bloma。

最先值得开工的具体批次是R0策略身份澄清与R1适配审计；先完成无需付费的受控回放、已有测试与差异定位。R2可以直接复用既有业务样本。主动试用和更广泛协作由这些结果决定是否进入生产默认路径。

## 9. 后续如何保持资料新鲜

以后每轮按同一窗口与模板记录：发布日期/稳定版本、实际变化、源码或评测证据、限制、对应本地入口、采用或拒绝理由。每轮至少留一项推翻原假设的证据。对Pi等直接依赖优先查releases/修复测试；对论文看任务设置与反例，不只摘要分数；对产品看用户闭环与真实可用状态。

本轮没有创建后台监测或订阅。持续跟踪清单是建议，不宣称之后会自动更新。未覆盖的项目、未深入读全文的论文、未运行的竞品和未做的真实对照均保留为未知，而非缺失或落后。
