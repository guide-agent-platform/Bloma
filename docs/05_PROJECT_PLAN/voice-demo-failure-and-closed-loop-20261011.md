# 语音演示故障与测试闭环：定位及技术方向

日期：2026-10-11。用户组会反馈：导师认为技术核心不够突出；最新语音录入案例虽完成验收，演示时有语音信号但没有识别文字。本轮核对实际产物与测试，执行了不打开麦克风/界面、不联网、不下载的缓存模型输入探针；没有修改原产物、模型资产、平台源码或项目状态。

## 1. 故障定位：真实音频的数据形状不符合识别接口

目标为「语音录入整理器」，project_id=`1f178567-0241-441c-a19e-da0dfa6edf27`。产物目录在 `.proma/agent-workspaces/default-software-builder/generated-projects/<project_id>/`。

`voice_audio.py` 的录音流使用 `sounddevice.InputStream(channels=1, dtype="float32")`。回调收到 `(frames, 1)` 数组，`numpy.concatenate(chunks)` 后仍是 `(N, 1)`；`AsrEngine.transcribe` 直接将它传入 `stream.accept_waveform(16000, samples)`。识别接口要求一维波形。

在产物自己的 Python 环境（NumPy 2.5.4、sherpa-onnx 1.13.8）与既有 SenseVoice INT8 缓存上，已独立复现：

| 输入 | 结果 |
| --- | --- |
| `(6400,)` float32 一维波形 | 接受并完成解码 |
| `(6400, 1)` float32，模拟真实录音回调形状 | `TypeError: accept_waveform(): incompatible function arguments` |
| 同一列数组转换为连续一维波形 | 接受并完成解码 |
| 本机合成的固定中文 WAV，16kHz/单声道/16-bit PCM 转 float32 | 输出「我们下周四下午3点开会。」；输入参考句为「我们下周四下午三点开会」 |

该故障足以解释“收到音频却不能转文字”，并不是需要先换大模型的证据。固定 WAV 证明当前缓存模型可以处理真实音频数据；它不是实际麦克风录音，也不是识别准确率评测。零波形解码有非空文本，不能拿它评价正常语音准确率，后续必须单独验证静音/VAD 行为。

官方接口约束与本地复现一致：[sounddevice 回调数组](https://python-sounddevice.readthedocs.io/en/latest/api/streams.html)为二维 frames×channels；[sherpa OfflineStream](https://github.com/k2-fsa/sherpa-onnx/blob/master/sherpa-onnx/python/csrc/offline-stream.cc)描述一维 float32 波形。最终判断以本地已安装版本的实际 TypeError 为依据。

另有三个待修的稳定性风险，尚未通过真人录音复现其全部影响：

- 每约 0.4 秒在 PortAudio 回调中同步做整段识别；首次模型校验/加载也可能发生在回调中。应采用预热模型、录音只入队、独立识别线程和有界队列。
- 回调忽略音频 status/overflow，识别异常后仍可继续处于 recording 状态。需要明确错误、停止、重试及清理状态。
- 模型初始化失败保存在 `_error` 后没有重新准备路径，暂时性失败可能持续阻止本次进程重试。

## 2. 验收遗漏：真实界面动作覆盖的是文本模拟入口

DELIVERY 声明 79 项自测、20 项端到端通过，同时明确写「真实麦克风录音链路未在真机验证」。`e2e_drive.py` 设置 `LLM_PROVIDER=mock`，向 `simulate-input` 注入文本并点击 `btn-simulate`；它验证整理、标记、还原、撤销与保存，绕过了麦克风、PCM 适配和 SenseVoice 转写。

所以这些既有通过记录有其有效范围，但不能覆盖用户演示的：

`麦克风 → PCM 音频 → 输入格式适配 → 真模型转写 → 原始文字上屏 → 停顿整理`。

PRD 的 F-001 明确“输入语音”，F-002 明确“开始录音、说话时文字实时上屏”。它们依赖 ASR 能力。平台现有 quick 交付主要检查产物、安全与启动，对核心能力所需的真实证据没有充分约束；“已声明未测”仍可到 completed/delivered。问题不止是单个 ndarray Bug，也在于交付判据没有阻止核心能力被替代入口覆盖。

没有麦克风不妨碍用固定 WAV 验证真实模型与适配。录音硬件链未验证时，则应准确标注其状态，不能把文本模拟通过传播成完整语音输入通过。

## 3. 近期工程修复应怎样闭环

1. **修组件边界**：规范声道、采样率、dtype、连续性与 rank；录音列数组先转单声道一维，协商设备采样率后按契约适配。稳定适配器和真实样本测试由平台提供，供生成者复用。
2. **修运行机制**：模型预热、录音/识别/整理解耦；队列和停止时限有界，重复启动/停止/错误后重试可观测。
3. **补三层实测**：固定 WAV→真实模型；模拟录音回调的真实 PCM 形状→识别→文字事件；用户目标设备的实际录音→上屏→分段→整理。
4. **保留反例与回归**：本次二维输入永久进入回归；增加静音、不同采样率/声道、连续录音、开始—停止—重启及初始化失败场景。
5. **收口看核心能力证据**：覆盖核心能力的一条真实路径是必需项，静态启发式继续按诊断处理；不恢复每个细枝末节都硬拒收的复杂验收体系。

本轮只完成定位和接口探针，以上修复尚未实施；原产物不会因本报告自动恢复正常。

## 4. 可讨论的研究主线

建议把技术核心收敛为：**能力契约与证据约束下的反例驱动验证和修复**。

它的技术输入是已确认需求、所需能力及其依赖/接口约束；输出是具体能力已验证、失败或因环境尚未验证的状态，以及可复现的修复结果。可以分四部分研发：

- **能力依赖与契约建模**：把“语音输入”解析为采集、格式适配、ASR、分段、整理、UI 输出；明确每个能力需要什么输入与证据。文本模拟对应整理能力，不能覆盖 ASR。
- **证据传播与测试选择**：在时间/token 预算下选择能补齐核心证据缺口的测试，约束模拟/真实模型/硬件证据的适用范围，绑定代码、模型及环境版本。
- **反例生成、缩减与定位**：从真实失败中提取最小输入和动作序列，本例缩减为一个二维 PCM 数组；定位到接口边界，指导局部修复。
- **闭环判定**：修复后重放反例，再检查原核心场景和回归；关键路径未验证不能仅凭总 PASS 数宣称完成。

已有研究覆盖反例驱动程序修复，例如 [AAAI 2025 的 CEGIS + 故障定位工作](https://ojs.aaai.org/index.php/AAAI/article/view/32046)；[Hypothesis 状态化测试](https://hypothesis.works/articles/rule-based-stateful-testing/)也能生成动作序列。因此不能把“反馈给 Agent 再修一次”称为原创算法，普通测试通过也不是形式化正确性证明。

潜在贡献需要落实到明确的方法与对照：针对多 Agent 生成软件的能力依赖、证据强度和资源预算，提出测试选择/证据判定/反例定位方法，再验证能否降低“验收通过但真实使用失败”的比例与返工成本。当前是候选方向，不是已经完成的研究贡献。

## 5. 优先评价哪些指标

- 假阳交付率：被系统判通过的任务中，独立核心真实场景失败的比例。
- 核心能力真实证据覆盖：录音、ASR、整理等分别统计，模拟入口不跨能力计入。
- 修复成功率与复发/回归：固定预算内反例消失、原核心任务仍通过的比例。
- 成本：追加真实验证的耗时、模型/工具调用、token，与减少演示失败和重复修复的收益一起报告。

可比较原有自测流程、只增加能力契约、能力契约加反例闭环三组，任务和资源条件固定。先用语音案例验证机制，再推广文件、持久化、外部服务等能力。
