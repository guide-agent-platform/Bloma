# 用多 Agent 协作提高生成质量：工程实施方案

后续实施更新（2026-10-30）：Q1 已接入现有制作/委派/验证链，详见 [Q1 实施记录](quality-q1-implementation-20261030.md)。下文“尚未接入”和 Q1 入口是方案制定时的历史状态；当前 Q2–Q4 仍未实施，未进行真实付费质量对照。

日期：2026-10-30。核对基线 `59a7d68`。用户纠正当前重点：解决多Agent如何提高实际软件生成质量，不优先开展科研实验或增加角色配置。本文件取代上一份规划的当前工程优先级；研究设计留作后续背景。本轮交付机制和实施范围，尚未接入下述完整质量闭环，也不启动付费调用。

## 1. 决策

采用“一个制作与集成负责人 + 事前业务案例设计 + 事后专项找错 + 宿主复现/复测”的协作闭环。质量收益来自检查不同错误面、减少实现者自我验证偏差、闭合真实缺陷，而不是更多Agent给出好评。

第一优先是独立找错与修复闭环；并行写代码放在可明确划分的模块上，不能以更快产代码替代更好的成品。

## 2. 各Agent到底做什么

| 职责 | 可见输入/权限 | 必须交回 | 主要补哪类质量缺口 |
| --- | --- | --- | --- |
| 制作A/集成负责人 | 用户已确认目标与设计、工程、运行与验证工具；负责唯一集成入口 | 可运行候选、真实执行记录、逐条修复关联 | 完整实现、跨模块一致、依赖与交付；不再额外设一个只转述任务的经理模型 |
| 业务案例设计B | 实现前只看确认需求/设计；不看实现，不修改需求 | 正常/异常/多对象/取消/重开案例，预期来源与未明确规则 | 功能遗漏、做偏、看起来可用但真实流程错误。复用已有B底座，CLI/API扩展另做 |
| 代码/数据审阅C | 稳定候选、相关差异、已确认业务规则及必要运行事实；只读，不继承A的成功叙述 | 文件位置、触发条件、预期/实际依据、疑点及可复现办法 | 串对象、旧回调、状态不一致、写盘/恢复/配置补偿、接口错接、测试盲点 |
| 视觉/交互审阅V | 同一候选的真实截图、确认设计、必要DOM/操作事实；只读且看真实图片 | 具体可见缺陷、位置、操作序列和验证建议 | 布局/遮挡、单位/静态文案、空忙错状态、结果与当前对象不一致；附图不等于已经审阅 |
| 专项侦察R/实现W | R解决限定组件/协议问题；W只负责确定接口和独占文件范围 | 有来源的事实，或实际改动与未验项 | 陌生API、解析/运行环境、明确可拆分模块。按需开，不固定每次全员出场 |

这些是职责，可按任务复用少量会话，不要求同时驻留五个Agent。先沿现有最多两个并行子任务，集成/实际命令/验收归A和宿主。测试脚本、运行器、看门狗本身不算LLM Agent。

## 3. 完整运行顺序

1. **冻结目标。** 沿已有确认流程保留目标/设计版本。B先写案例与预期依据；没有明确的业务规则标“待澄清”，不得为了增加测试而擅自新增功能。B写错预期不算产品缺陷。
2. **A实现主路径。** 复用组件，生成可运行候选并完成基础运行检查。若有明确独立模块，A可委派W，但统一合并后才进入质量核查。
3. **冻结一个候选快照。** 记录源码/设计/依赖与环境身份；C审代码/数据，V审该版本的真实界面，可并行。A此时不边改边让审阅者判断旧版本。
4. **问题进入宿主台账。** Agent只提交finding，不提交最终PASS；每条问题绑定候选、需求、证据和触发条件。
5. **复现后修复。** 宿主/负责人执行受管的命令和实际界面操作，确认缺陷后由A修复。不能靠A一句“已修复”关闭问题，审阅者也不直接改代码和冻结断言。
6. **验证修复和相关回归。** 新候选使旧截图/审阅失效；复测目标缺陷及受影响路径，保留旧失败。疑点无法复现时记未确认/无法复现，不凑数算已解决。
7. **同版本交付。** 必需业务/核心/正常启动/GUI/数据检查通过，重要已确认问题有复测证据且无未闭合未知副作用，才交付。模型意见不能越过宿主证据规则。

C/V各自先基于自己的材料给结论，再由A综合；不要把A的自评或另一审阅者的结论作为它们的起始答案。分歧转为可操作的验证问题，不用投票决定程序是否正确。

## 4. 把“审阅意见”变成可执行质量机制

最小问题契约：finding_id、候选源码/设计身份、需求引用、问题类别、严重度、触发输入/操作、预期来源、已见证据、建议复现、未知项。不能只有“建议优化”“注意边界”或“整体不错”。

状态流为：疑点 → 已复现/已证实 → 修复候选 → 该候选复测通过；另有证据不成立、业务预期有争议、待外部条件。最终关闭由宿主执行结果绑定当前版本，审阅Agent和制作Agent不能自行把台账状态改为已验证。

台账不会把所有模型猜测变成无限阻塞：只有已确认、属于用户范围的重要缺陷进入必须修复集合。非需求内的增强另列建议；相互矛盾的预期先核对需求来源。预算/时限用尽保留未闭合问题和候选，不假装达标。

## 5. 例子：库存管理软件

用户已确认两件物品的入库/出库/编辑/删除和重开保留。

- B提前给出多对象身份与统计案例，例如改A不能改B、修改后列表与总数一致、重开读回；出库能否负数等未明确规则先澄清。
- A实现软件。C检查是否拿数组下标充当ID、异步响应是否覆盖新对象、记录写盘与统计是否一致。
- V核对实际界面，发现主数字已更新但邻近单位/静态零仍残留，或提交完成后还显示处理中。
- 宿主实际编辑/删除/取消并重开，确认真实结果；A修复。交付依赖这些事实，而不是“代码审阅说没问题”。

这几种检查利用不同信息面，有机会补上同一实现者写代码又写自测时的共同遗漏；效果仍需真实任务检验，不能仅凭角色划分宣布质量已经提升。

## 6. 当前已有的底座和缺口

已核对 `lean-production.ts`、`agent-tools.ts`、`production-completion.ts`、B设计及协作策略：已有真实委派、两并发、继承父模型/预算、只读/文件写权限、子任务回收、B冻结GUI案例和宿主验证。完成守卫会等待运行中的子任务并交回摘要。

主要缺口是：

1. 委派仍是通用子任务，尚无强制结构化的质量finding及宿主关闭证据台账。
2. C/V审阅材料、源码快照和当前结果的绑定尚未形成专用协议；父会话debug截图不能直接越权给子会话使用。
3. 审阅结束不等于意见已被复现、修复和复测，当前摘要不足以证明质量闭环已跑完。
4. 子任务目前没有独立命令/GUI执行权限。首期由主负责人受管执行，后续若开放测试型子Agent，先做专属进程/数据/候选隔离。
5. 普通软件子任务禁止另选模型。先用独立上下文/不同检查材料减轻偏差；异模型C/V要新加明确用途与费用授权，不能挪用只授权B案例设计的预算。

不会恢复已经删除的旧裁判面板/旧PRD审查管线，也不新建另一套Agent引擎。沿现有持续Pi、委派、预算和验证入口增量接线。

## 7. 实施批次与退出条件

| 批次 | 实际工程交付 | 必须验证的反例/结果 |
| --- | --- | --- |
| Q1 首批 | 稳定候选审阅任务、只读C输入/输出协议、finding台账、宿主复现与关闭、A修复关联 | 伪造PASS不能关闭；源码变化使旧意见失效；真实缺陷修复前失败/修复后通过；无依据意见不算已复现 |
| Q2 | V的授权图片/DOM材料与候选绑定、视觉问题交回同一台账 | 跨会话/过期/换图拒绝；实际发送图像且不以文件名/OCR替代；界面操作与源码证据同版本 |
| Q3 | B案例语义/误报处理完善，多对象/异常/重开覆盖与台账结合；CLI/API按需求扩展 | 实现者不能改冻结断言；B不能加新需求；无效预期被识别而非硬判产品缺陷 |
| Q4 | 按任务风险选择协作，必要时扩展隔离W/测试执行器、经授权的异模型角色 | 小改动不无条件启动所有Agent；两并发/文件冲突/取消/费用共享仍可核对；隔离执行不验错候选 |

Q1优先于增加模型下拉框、更多写入工人或多Agent互聊。现有B可按已有明确项目配置使用；新路径没有接线前，不在UI里宣称自动协作质检可用。

## 8. 怎样判断确实提高生成质量

先固定少量能暴露不同缺陷的任务和独立业务预期，在相同目标/设计/环境/资源条件下核对单负责人路径与新闭环。保留失败、人工介入及全部实际模型调用，不把受控回放或代码审阅条目数量当真实质量收益。

观察：首次完整业务路径通过、交付后发现的缺陷、多对象/重开/外部副作用错误、可见交互缺陷、问题复发与误报，以及完成这些质量要求的实际时间和全链路费用。重要的是同一外部业务标准下成品更好；多发现几条无关建议不算改善。

本机可先用注入缺陷与受控查询验证Q1/Q2机械链路；要验证真实生成质量，须明确当时模型/渠道、产品/账号范围、实际费率与完整预算后运行新的任务。旧实验和旧额度不自动恢复。
