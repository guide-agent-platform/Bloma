# Agent 基础反馈与执行闭环完善计划

日期：2026-10-12。计划基线：`d1615d5`；本地上游 Proma 对照版本：`bf3e98ca61dd8365eceaef876c0f7473700878a6`。工程实施及实际验证范围见 [执行记录](agent-feedback-execution-20261012.md)。

## 1. 目标与已有基线

让 Agent 每次工具调用后都能回答：实际做了什么、是否执行成功、验证证明了什么、失败属于哪一层、哪些工作仍未完成、下一步允许做什么。以此减少错误修复、反复读取与重复准备，再评估委派收益。

`d1615d5` 已验证参数结构校验、安装 import 错误回传、进程退出与场景结果区分、工具预算收口、SSE 有效进度超时与协议结束、架构组件事实及固定音频 Loader。基线为单测 243 文件/2258 项、集成 8 项、类型检查/构建通过；没有新一组付费生成闭环或提速证明。

当前关键接线缺口：`ToolOutcome.detail` 仅用于事件；`executeTurnToolCalls` 给模型的 tool_result.content 仍只有 output 字符串。事件 sanitizer 又只保留委派 id/status 等字段，因此 imports_verified、verification_status 没有形成统一消费协议。委派格式化输出也未明确展示全部 loop_status/预算原因。新增字段不能只存在类型或遥测中。

上游按件对照：执行前校验、错误保真、委派未收敛状态、能力调用取消与超时、结果压缩。记录源码/版本/适配差异；上游 SDK/Pi 和 Bloma 自有 loop 的权限、工具名与领域验收不能直接混用。

## 2. 实施顺序

### 批 1：统一工具反馈，接通三个消费端

入口：`main/agent/loop/agent-loop.ts`、领域工具、`shared/types.ts`、preload/renderer 的工具事件消费。

定义带 schema_version 的可选反馈结构，旧工具仍可兼容。先迁移高频路径：文件读取/写入/编辑、脚本执行、依赖安装、工程驱动、GUI 驱动、委派等待/读取结果。工具自己的语义断言不由统一层替代。

最小信息分开表达：

| 维度 | 信息 |
|---|---|
| 执行 | not_run/running/completed/failed/cancelled；执行 id、tool_call_id、耗时、退出码 |
| 错误 | invalid_input、permission、environment、product_assertion、verification_harness、budget、transport、unknown；原始错误与原因标识 |
| 验证 | passed/failed/unverified/not_applicable；验证对象、输入来源、实际断言结果 |
| 版本与证据 | 源码/声明指纹、报告引用、固定样本或真实设备来源、截断标记 |
| 恢复 | 未完成项、可重试性、必要前置条件和允许的恢复动作 |

模型收到紧凑 JSON 状态头与有界执行正文；编排器消费同一对象；界面展示短状态与可展开依据。完整 stdout/stderr 按工具需要落独立记录，摘要带引用。不能把 detail 全量放开到 renderer，继续用安全字段白名单；密钥和敏感配置不进入反馈。unknown 保持未知，不能仅靠错误文本关键词决定业务失败。

**完成条件**：三个消费端对同一次调用的状态一致；exit 0 + FAIL、pip 成功 + import 失败、未执行、超预算、固定音频均不被呈现为业务通过；JSONL 重放仍能取到紧凑状态；长输出截断不丢失状态头和证据入口。

### 批 2：任务状态、证据范围与续接交接

入口：`agent-collaboration.ts`、`delegation-tools.ts`、loop 终态、`core-verification.ts`、`core-delivery.ts` 和交付说明消费。

保留执行生命周期与任务完成度两轴：子 loop 结束或宽限轮输出总结，不能据此确定目标完成。把 loop_status、停止原因、未完成项、已变更文件、已执行验证及报告引用显式交给父 Agent。模型可报告进展；宿主依据实际产物/验证裁决完成度。

续接使用“已确认事实 + 当前版本 + 未完成项 + 最近失败证据”的短交接，保留原始历史可追查。避免把整份报告重复读入；文件变化时旧事实失效，不能为省读取而复用过期结论。相同版本重复读取先记录和提醒，不用简单次数阈值禁止合理复核。

语音、文件写入、GUI 和外部服务分别声明证据范围。固定输入不证明物理采集，接口调用不证明用户按钮流程。交付状态摘要由宿主报告生成，模型负责说明，不得用模型文档覆盖失败或未验证。

**完成条件**：宽限收尾/turn_limit 不会被父 Agent 当作工程完成；续接明确保留缺项；版本变化让旧验证失效；固定输入记录不进入真实硬件通过结论；用户看到的交付状态与宿主报告一致。

### 批 3：按失败类别恢复，统一累计尝试

入口：工具反馈适配器、`advance-rejection-loop.ts`、`core-delivery.ts`、运行注册表和请求账本。

| 失败类别 | 恢复方向 |
|---|---|
| 参数 | 回传具体字段，模型修正调用；不扣工具执行额度，模型请求仍计用量 |
| 环境/权限 | 修复解释器、依赖、资源或等待许可；不自动重写业务 |
| 测试基础设施 | 保存报告，定位等待/选择器/装配；业务状态不能因此被判失败或成功 |
| 业务断言 | 明确需求、场景、预期/实际和版本，局部修复后复验 |
| 传输 | 维持已发事件后不盲重发边界；记录最后有效进度与取消原因 |
| 预算/无进展 | 保存当前产物、证据与缺项，停止自动空转，支持明确续跑 |

分类尽量来自执行器与结构化报告；模型对根因的推测另存 hypothesis，不能作为宿主已确认事实。未知原因可进入一次有界诊断，不能靠猜测修改软件。

把核心修复、阶段拒收、环境准备/下载的计数归入同一项目运行上下文；子任务更名、重派或应用重启不能隐式清零。先沿用已有分项上限并对齐计数，不未经试验就叠加一个更紧的默认总额度。用户明确新需求与续跑的预算语义分别定义。

生产保持正常生成总时长缺省不硬限；无进展、下载和局部修复有界。实验驾驶器仍有固定时限，超限保留为未完成。进度必须有执行/证据变化，不能仅因心跳或重复日志增长认定任务推进。取消与超时核对资源回收，尤其脚本的后代进程。

**完成条件**：相同环境错误不会无限重派业务实现者；下载失败不会在新子会话从零累计；重启后计数恢复；取消后没有该运行遗留的受控进程；计数与请求账本可对账。

### 批 4：组件与资源可发现，减少重新选型

入口：`component-library.ts`、环境探测、组件物化、`speech_locator.py` 和阶段提示词装配。

把已有组件、来源版本、可用解释器、安装状态、缓存路径及校验状态提供为一次可追溯的工具结果，架构与实现共用。组件存在、依赖可 import、模型缓存匹配、产品业务通过是不同状态。

语音优先查平台 SenseVoice 资源；确有能力缺口时才比较替代方案，并列出新下载/验证成本。快路径查询不得每轮重算大模型 SHA；缓存校验策略基于文件版本并保留失效条件，不能仅凭文件存在称可用。测试适配器在反馈中明确标出固定输入，避免把其错误当成真实设备错误。

**完成条件**：已验资源被实际查询和消费；缓存完整时不触发下载；缓存缺失/损坏时给出明确结果；替代引擎有具体能力理由；模型与宿主能区分测试设备和物理设备。

### 批 5：小任务连续执行与选择性委派对照

前四批通过后，建立可切换的执行策略，先用于隔离实验：

- 连续主执行：同一执行 Agent 完成小任务核心实现及自测，宿主负责验收。
- 选择性委派：主执行保持上下文，独立验收者检查反例；确实独立的调查/模块才并行。

选型依据是任务能否独立交付、接口是否明确、写入范围是否隔离及验收者是否提供独立断言。不把角色数量或代码行数当作任务复杂度的唯一指标。保留现有流程作参照；未经对照不直接批量切换所有项目默认策略。

首轮真实生成试验从记账、文件两个固定任务开始，各跑两种策略，共四次。需求、模型/渠道、有效提示词、资源准备状态、时限与修复额度在开始前冻结；变化或中断如实单列。语音先补齐资源/测试来源的确定性回放，再纳入真实生成，避免先批量烧额度。可用额度不足时保留本地验证，真实试验标为待验证，不自动充值或换渠道。

**完成条件**：每次运行可追查首次业务通过、修复、停止与正式交付；同一独立验收脚本检查两种策略；有足够案例证据再决定默认策略。四次运行只作工程试跑，不宣称统计显著或泛化成功率。

## 3. 固定回归矩阵

先冻结现有反例和期望，再实现；验证脚本不得随产物输出降低期望。

1. 缺参数/类型错：工具未执行，明确字段，有效重试额度不丢。
2. pip 成功/import 失败：环境未就绪，原始错误可追查。
3. exit 0/场景 FAIL：业务失败；没有场景则明确未验证。
4. 心跳无进展、结束事件不关闭连接：有限结束、工具参数/usage 正确结算、不重复请求。
5. 固定 WAV 与设备替身：不能产生物理采集通过；Loader/替身错误保留测试来源。
6. 子任务预算耗尽且缺产物：执行结束，任务未完成，父 Agent 得到缺项。
7. 源码或声明变化：旧测试/缓存结论失效；相同版本允许受控复用。
8. 重派、续跑、重启：尝试计数、未完成项、证据和请求用量连续。
9. 相同环境失败无新证据：有限诊断后暂停；未知不被强行归产品失败。
10. 取消与迟到结果：受控进程回收，旧 run_generation 的完成结果不覆盖新运行。
11. 真实业务：记账 DOM→磁盘→重启；改名旧预览/越界/冲突/撤销；语音真模型音频适配/静音/停止重启。

每批执行对应单测与真实临时文件/进程探针；涉及 renderer/IPC 时补隔离 Electron 检查。最终执行单测、集成、类型检查和构建。必要验证通过后逐批 commit，记录失败和修复证据。

## 4. 判断改进是否有效

记录首次独立业务通过时间与正式交付时间，分开需求等待、模型请求、工具执行、环境准备、验证及修复耗时；并行重叠时间不重复相加。请求按 id 去重，保留缺 usage 和缓存口径。

重点指标：首次真实缺陷数、错误归因/误判完成数、修复次数、相同版本重复读取、重复环境准备、无进展等待、已知请求用量、最终交付状态。固定反例中的误判通过和错误拒收均要求为零；unknown/environment_blocked 与业务失败分别统计。

不得只报告最后成功者；人工中断、超限、测试适配器错误、模型错误结论和原始产物缺陷都保留。改前缺可比生成基线时，不计算提速或降本百分比。
