最初尝试 GLM Anthropic 端点，返回 `[1309] GLM Coding Plan 套餐到期`；与用户的常规 API 额度不是同一通路。随后改为 `zhipu` 类型、`https://open.bigmodel.cn/api/paas/v4/chat/completions`、模型 `glm-5.3`。常规 API 非流式工具调用及原生 SDK 的流式工具调用/工具结果续接均成功。期间 GLM 共有 118 条物理请求费用预留，其中 114 条有完整用量；不能据末次空流认定全部调用方式都错误。

## 三次终止的原因

| 样本 | 原始运行终态 | 本次定位 |
|---|---|---|
| G11 | failed / EXPERIMENT_REQUEST_BUDGET_EXHAUSTED | 用尽 128 次逻辑请求。交付声明将 GUI 场景放在宿主不消费的 `gui_scenarios` 字段，而 `scenarios` 中 F-006/F-007 登记成未实际输出的逻辑场景，导致反复修复仍未收口 |
| G22 | failed / runtime_error | 终端截图明确显示 `MONETARY_BUDGET_EXHAUSTED`。按完整 1M 上下文为每个 GLM 请求预留约 8.62 元，调度/实现请求重叠及早期失败预留叠加，造成实际用量估计不到 50 元时提前拒绝 |
| S2 | failed / runtime_error | 最后一次请求 297ms 结束，零正文、零工具、零用量；原生 loop 的空流守卫拒绝继续。此前空标题场景的声明名称使用双引号，Python `repr` 输出使用单引号，精确匹配失败而进入额外修复 |

原始事件保留不重写。G22 的准确错误来自 `quick-r1/G22/terminal.png`；S2 的空流由 `quick-r1/S2/main.log`、用量账本末次请求及 `agent-loop.ts` 空流守卫共同定位。旧日志没有保存 HTTP Content-Type、字节数或响应摘要，因此目前不能进一步确定 S2 是服务端空流、HTTP 200 JSON 错误被旧 SSE 读取器忽略，还是格式变体。不得把候选原因当成已证实根因。

本次补齐：账本记录响应 HTTP 状态、Content-Type、字节数、SSE data 行数、终止标记和响应哈希；不保存响应正文、认证头或密钥。HTTP 200 JSON 响应现在明确报 `PROVIDER_JSON_RESPONSE`，不当成正常 SSE 结束、不盲目重试。实验终止事件记录 `MONETARY_*`、`EMPTY_MODEL_STREAM` 等明确符号错误码，避免全部退化成 `runtime_error`。新驾驶脚本保留结束画面文本和终态原因，并支持 STOP 文件取消。

## 独立业务诊断

停止后用真实 WebView 界面与各自新的 APP_DATA_DIR 操作三份产物，不修改生成代码，不调用收费模型。固定检查：新增去空格、空白拒绝、同名任务完成状态隔离、三类筛选、删除隔离、重启保存。G11/G22/S2 均 6/6 通过。这是停止时产物的业务诊断，不等于平台已交付，不覆盖 PRD 的所有新增项，不形成完整六组的研究 Q。

证据：`diagnosis/{G22,S2,G11-final}/gui.json` 与 product.log。G11 首次诊断的控件适配器只识别原生 checkbox，未识别该产物的 role=checkbox；首次后续断言受前置状态缺失影响，该报告不作业务失败证据。补齐控件适配后重新使用全新数据复验；脚本现在把前置状态未建立的后续检查标 pending，避免把验收器失败冒充产品失败。
