## 1. 目标与边界

面向零基础用户，做深软件的开发、调试、交付和维护。第一阶段覆盖Windows本地Electron/Python工具、浏览器应用、命令工具；具体框架和组件由Agent根据任务与现有工程选择。用户表达用途、功能、数据与外部影响，不负责选择技术栈、填写验收协议或手动准备开发环境。

默认一个连续主Agent；独立任务才协作。沿用Pi、多供应商渠道、费用账本和已有版本边界。四项是平台开发路线，不是每个用户项目都必须经过的四个新阶段。不增加默认AC、强制角色轮转、长PRD或每次制作都运行的模型评审。

云托管、移动开发、任意桌面软件自动化和插件市场不属于这四项的首期目标。普通项目依赖可自行准备；系统级变更、发布和额外付费遵从用户授权。工作树、环境变量清洗与参数校验不能被宣传为OS沙箱。

## 3. A：持续调试真实程序

### 3.1 首期范围

建立宿主持有的DebugSession，记录project/session/operation、候选版本、受管理进程、端口、隔离数据目录、浏览器或Electron页面与日志位置。对外优先扩展现有inspect_app/start_service/read_process/stop_process；内部可有open/act/inspect/close，不为这些内部动作制造一排重复模型工具。

1. 同一个会话持续操作、观察、修复和重载。浏览器可连接本项目已拥有的开发服务，不重复抢同一端口；Electron走正常入口。用户正式使用的实例与调试实例分开。
2. 收集renderer控制台、未处理异常、服务stderr、失败HTTP请求/状态/耗时、必要IPC错误，关联触发动作和候选版本。默认不记录Authorization/Cookie/API Key或整段请求正文；上下文只传相关窗口，完整诊断留本机。
3. 补充文件上传/选择、拖拽、下载、键盘、滚动；以真实用户控件路径验证。测试文件来自明确任务附件或固定fixture，不能用模拟业务成功替代真实导入。
4. 截图按需提供给支持视觉的当前渠道。未知/纯文本渠道继续取得DOM与错误证据；不偷偷增加视觉模型调用。
5. 页面重载或代码构建后更新版本绑定；旧截图、旧console错误不能冒充新版本结果。关闭、取消、崩溃后的资源处理归宿主，不能仅标记cancelled就认为退出。

### 3.2 分批与验收

| 批次 | 实现结果 | 必须通过的用户路径 |
| --- | --- | --- |
| A1 生命周期 | 保留并复用调试会话，明确进程/端口所有权 | 连续操作不重建空数据；停止后进程和端口释放；未知PID不被接管 |
| A2 错误观察 | 控制台、服务错误、网络失败与动作关联 | 注入JS异常/HTTP500能定位来源；修复后同一实例重验；旧错误标记过期 |
| A3 文件交互 | 真实上传、对话框与下载证据 | 导入固定PDF/Word得到实际内容；损坏文件有错误反馈；导出文件可读回 |

首期不声称覆盖任意Qt/WPF/WinForms或整个操作系统。当前Python固定观察器继续可用，持续调试适配器按实际技术栈逐项增加。异常观察供Agent修复；最终交付仍需要目标相关的真实行为结果。

## 4. B：可靠增量修改

### 4.1 变更与发布候选

沿用现有版本、快照和用户备份，增加一致的“可用基线—修改候选—验证结果—发布版本”关联。最小记录包含代码版本、依赖锁摘要、启动入口、构建产物、数据schema和已有关键行为。运行中的正式版本使用稳定发布目录，不继续读取正在修改的源目录。

不在每次编辑后复制全部node_modules/运行时或调用模型写总结。源码用Git/差异快照，依赖按锁文件和运行时版本复用，发布目录只带实际运行需要的文件。日志、截图、数据和代码版本分别管理。

### 4.2 修改与数据更新

- 外观与缺陷沿当前范围直接修改；业务能力或数据语义变化复用现有范围变更确认。主Agent用短变更摘要识别接口/数据/关键行为影响，不新增固定架构审查角色。
- 优先运行受影响测试和已有关键路径，扩大检查应由变化或失败驱动。旧功能不能因新增功能消失；用户明确删除的功能则更新目标，不能永久锁死旧预期。
- 迁移先在数据副本演练，采用产品已有CLI/API/数据库事务；不强迫所有程序实现同一种类或旧Web目录结构。记录旧schema、新schema和恢复方式。
- 用户选择更新并保存后，取得一致性备份，迁移副本，验证候选，再切换正式版本。SQLite等应使用一致性备份/事务，不盲拷正在写入的文件。
- “回退程序”和“恢复某时点数据”分开。回退代码不自动覆盖最新记录；不兼容旧schema时给出明确恢复选择，不能把迁移后的数据交给不兼容旧程序继续写。

### 4.3 分批与验收

| 批次 | 实现结果 | 必须通过的用户路径 |
| --- | --- | --- |
| B1 候选隔离 | 正式运行版本与工作目录分离 | Agent改源码时，正在使用的旧版不混入半成品资源 |
| B2 增量回归 | 关键行为与变更范围绑定 | 已有笔记程序新增搜索/标签后，原新增/编辑/保存/重开仍通过 |
| B3 迁移恢复 | 备份、迁移演练、更新/恢复入口接通 | 100条固定旧记录经过多次修改仍保留ID和内容；故意迁移失败能恢复 |

备份不等于已经验证能恢复。B3必须实际恢复并重新读取记录，不以备份文件存在作为通过。

## 5. C：环境准备与独立交付

### 5.1 工程环境

建立项目运行时清单，优先尊重已有engines/锁文件/工具链约定。平台在自身管理目录准备版本固定的Node/Python等运行时和依赖缓存；不要求用户自行选择包管理器或修改PATH，不默认系统级安装。

缓存绑定平台、CPU架构、运行时ABI和依赖锁；原生模块必须实际加载验证。下载校验完整性并保留来源/许可信息，网络失败给出可恢复状态；已有可用环境不反复研究或重装。Electron作为Node的兼容运行方式不能替代独立Node发行版验收。

首期打通少数成熟组合，积累按需工程范例和可复用组件；允许Agent按任务选择其它栈，不恢复“唯一模板/禁止npm”的约束。

### 5.2 交付产物

区分源码包、依赖本机环境运行的程序、便携包和安装包。识别package.json/pyproject等已有入口，必要时由Agent补充少量启动元数据，不交给用户填协议。用户要求独立程序时，源码导出不能直接标为完成。

打包后以实际成品入口复验，清单绑定exe/asar/dll/node及业务资源，不只绑定原始源码。大文件采用有界流式摘要，避免把所有内容塞入当前源码指纹32MiB预算。跨机器验证应确认没有借用开发机绝对路径、缓存和环境变量。

用户数据与成品配置继续放项目专属目录。API配置在成品设置界面完成，未配置时有明确引导；平台Agent渠道密钥不成为成品依赖。签名、云发布和付费服务按实际需求单独安排，不作为本地工具首期的隐性开销。

### 5.3 分批与验收

| 批次 | 实现结果 | 必须通过的用户路径 |
| --- | --- | --- |
| C1 运行时管理 | 探测、准备、缓存、失败恢复 | 未装Node/Python的受控Windows环境能准备项目；相同环境可复用；缺失报告准确 |
| C2 成品清单 | 源码/便携/安装包明确，启动绑定实际产物 | 隔离验收环境不挂载开发目录，成品仍运行；修改打包业务资源使旧验证证据失效 |
| C3 干净环境 | 独立机器/干净虚拟环境实际验收 | 无Bloma工程和开发缓存，启动、主操作、保存重开、升级均通过 |

C3环境需真实具备。没有新机器/虚拟环境时明确未验证，不用当前开发机上的模拟路径充当跨机器证据。

## 6. D：已有工程与长期任务

### 6.1 接手已有项目

提供本地目录/仓库接入，记录用户未提交改动和当前分支。复用已有工程结构、测试、运行入口和依赖约定，不重新生成骨架。只提交Agent自己的相关变更，不覆盖用户工作，不默认push；旧worktree逻辑的自动建基线/强制清分支行为须先适配外部仓库。

检索从文件/符号/导入关系和已验证事实入手，按需使用语言服务，变更时增量失效。处理源码验证规模上限，区分源码、依赖、构建产物和运行数据，不靠单纯扩大上下文或生成整仓长文解决问题。MCP/技能按任务加载，不把工具目录全部塞入提示词。

### 6.2 长任务与恢复

在已有Pi原生会话、工具回执和预算上记录可继续状态：目标版本、候选、已完成步骤、最新测试、未解决错误、进程归属与账本引用。已完成副作用不自动重放；旧测试只有输入版本一致且仍适用才能复用。

费用上限与本次执行时限分开。研究如何用真实工程进展、错误类别和剩余费用替代固定两次修复/统一时长对所有任务的截断；不能通过“继续”、改会话或重开操作清零历史消耗。明确运行、暂停、待用户、环境阻塞、取消、已验证交付；流结束不等于软件完成。

崩溃恢复结合活动租约/最后活动记录处理，不能把整段离线等待粗暴算成模型运行，也不能把未知请求当免费。预算不足时保留现场和完成记录，再由用户决定是否继续投入。

### 6.3 隔离协作作为后续能力

复用并改造现有worktree基础，先证明源码、依赖、端口、测试数据和数据库相互独立，再允许子Agent各自执行命令。工作树不等于OS安全隔离。主Agent集成并承担最终行为验证；紧耦合修改仍单Agent，默认并发保持克制，不预先建立前端/后端/测试/裁判流水线。

## 8. 开发期回归与价值判断

基准集放在开发/发版回归中，不加入每个用户项目的额外审查流程。先用固定SDK回放验证机制，再用受控真实模型任务评估实际收益。

| 固定任务 | 观察重点 |
| --- | --- |
| 计算器 | 首次可用、真实界面调用、四则/错误恢复、工具协议是否能直接调用 |
| PDF/Word学习工具 | 实际导入内容、错误文档、界面异步状态和导出，不接受仅文字PRD |
| 本地笔记/账本 | 保存重开、增量功能、旧记录与schema迁移 |
| AI API小程序 | 配置引导、正常HTTP/401/429/取消、错误反馈；供应商生成质量单列 |
| 已有仓库修复 | 跨模块定位、原测试/新缺陷回归、保留用户改动和中断续做 |

每项保留首次可用时间、端到端成功、修改后退化、人工介入、实际费用和失败分类。人民币、Proma积分、订阅额度分别记录。样本增加后再报告分布，不从一次成功推出整体稳定。

比较harness时固定模型/材料/任务；比较模型时固定harness。真实模型实验须先核对当次渠道、额度、费率与项目费用硬上限，不使用历史资格或清账本绕过限制。没有在线模型对照前，不宣称速度、成本或成品质量已优于Proma/Codex。

保留一项新机制的依据是成功率、可恢复性或单位任务成本得到实际改善。若增加调用/等待却无可测收益，应简化或移除，不以Agent数量、文档长度和检查次数作为能力指标。
