## 原因与修复

r4 中，worker-2 已正常结束，但交接保留了早期内联检查的失败和超时，`completion=incomplete`。后续 GUI 核验任务依赖它，依赖检查又要求交接不能 incomplete，形成“需要后续验证来处理失败，却因失败不能启动验证”的循环。worker-1 的旧版本凭据同样不能证明当前版本通过。原始时间、四次依赖拒绝及独立业务验收见 [r4 报告](experiment-r4-G11-results-20261021.md)。

修复集中在实验调度策略，没有删除或自动覆盖诊断记录：

- `dispatch-experiment-recovery.ts` 统一判定执行是否结束：必须实际执行过、委派生命周期 completed、loop_status completed，并且没有终止性预算故障。
- 自主规划及旧版固定任务策略都使用上述执行条件释放依赖，不再用历史交接的 incomplete 阻断后续任务。摘要刷新仍保留失败凭据。
- `experiment_status` 同时提供 `dependency_ready` 和 `verification_state`，前者表示后续任务可以接手输出，后者仍可能为 incomplete/unverified。
- `experimentTasksFinished` 只检查登记任务的执行覆盖，允许进入正式验证；它不证明业务已通过。调度提示同步解释这一区别。

运行中、取消、失败、轮次耗尽、预算耗尽、未派遣及失联记录仍不能释放依赖；累计资源终止仍优先结束实验。已结束执行器可以交出稳定输出，但是否还能续接仍单独受资源检查约束。核心检查、安全扫描、启动门和固定 V 审阅保持原有交付条件；失败或未验证不能进入 delivered。

实现前核对了上游 Proma `bf3e98ca61dd8365eceaef876c0f7473700878a6` 的委派生命周期与续接方式，沿用执行状态和验证事实分开的概念；本项目继续保留自身类型化证据、预算和正式门禁。没有改动上游仓库。
