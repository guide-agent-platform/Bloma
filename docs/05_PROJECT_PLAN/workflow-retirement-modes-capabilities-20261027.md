## 首次实查结论（实施前快照）

1. 新建项目统一由 `main/ipc/projects.ts` 选择 software-v1。需求经 handleLeanGuide，制作经 runLeanProduction；长期/快速当前共用任务单、实现、预算、验收与交付。模式名称/配色有区别，旧阶段矩阵没有进入该主线。
2. 旧执行链仍可达：无新版标记的历史项目及冻结实验不会进入 usesLeanWorkflow。旧 guide、dispatcher、架构/骨架阶段及 MVP 确认仍有消费入口。因此目前不是“只剩可以直接删除的孤立文件”。
3. 新流程仍执行 runCapabilityVerifiers。语音登记缺失、真实音频探针失败、缺少当前麦克风证据，都不能因 DOM/CLI 测试通过而认证完整语音功能。
4. 现有语音能力包括平台输入侧 Node 语音服务、固定资产清单/缓存校验/下载，以及产物侧 Python speech_runtime.py / speech_locator.py。当前宿主 ASR 探针围绕实际产品的 Python callable 和 sherpa 解码；验证固定 WAV、一维 PCM、录音列数组、多声道适配。固定音频通过不等于真实麦克风或所有语言/场景质量通过。
5. **复用入口存在接线缺口**：software 的工具装配过滤了旧 inspect_project_resources / install_packages 路径；prepare_software_environment 只准备通用 Node/Python。旧 installer 在安装 sherpa-onnx 时自动物化 speech_runtime.py / speech_locator.py，这个动作不会因新流程普通 run_command 执行 pip 就自动发生。read_production_context(verification-speech) 有协议说明，但不负责安装或物化。
6. software 主线没有默认物化旧 Python 骨架；Electron/Node 产品也不能直接把旧 Python 转写协议当作原生 Node 能力。平台自身能听写，不等于生成的产品已经获得可独立使用的语音能力。

对应代码入口：`main/desktop/workflow-policy.ts`、`desktop-route.ts`、`capability-verifiers.ts`、`speech-verification.ts`、`resource-discovery.ts`、`install-packages-tool.ts`，`main/software/agent-tools.ts`、`runtime-manager.ts`，`main/templates/tools/speech_probe.py`、`speech_runtime.py`、`speech_locator.py`。

## 批次 B：平台怎样帮助实现复杂能力

采用“能力识别 → 成熟实现复用 → 依赖与资源准备 → 最小能力实测 → 产品集成 → 用户场景验收”的顺序。编码模型负责选择、接线和业务/UI，平台提供可检查的资源与执行接口，不要求模型重新实现 ASR 算法。

语音首例的具体工作：

- 提供新主线可用的只读能力/资源检查，分别报告解释器、依赖、模型资源和硬件证据；安装成功、缓存存在与业务可用是不同状态。
- 封装受控组件准备接口：保护已有用户文件，按需物化已有 Python 组件，绑定项目运行时，安装后 import/调用回读。下载可取消、有时限并校验固定资源；不反复全量下载，不把模型文件或测试音频污染发布候选。
- 先支持已存在且能实际验证的 Python 路径；Electron 可评估独立 Python 子服务与清晰 IPC，再决定是否补原生 Node ASR 适配。没有适配能力时明确 blocked，不把运行时名换掉就宣称已支持。
- 统一开发、正式验收和用户运行时的模型资源定位，核对 getPromaHome、用户 HOME 与 BLOMA_SPEECH_MODEL_DIR 的现行差异；准备证据不得认证另一目录或另一份资源。版本、资产哈希、离线可用性和交付依赖均需绑定。
- 最小真实解码先于 UI 深度集成；然后验证录音/转写/显示/停止/重开及数据不丢。取消、设备缺失、静音、无效音频、资源损坏、超时和写盘失败均需保留实际结果。
- 固定 WAV 只验证解码和适配；真实麦克风必须取得单独授权并检查当前产品采集链；平台输入框已有语音证据不能泛化为新产品整条链已经通过。
- 本机缓存可用与独立机器交付分开验收。资源/运行时不具备时，报告缺口与可恢复动作，不降低原需求，也不借平台渠道密钥给产品使用。

同样的接口模式可用于 OCR、文档解析、图像处理和外部模型 API，但能力仅在真实适配/验证接好后对模型宣称可用。第二个编码模型或独立验收模型本身不提供语音引擎、设备驱动或资源分发能力；新增付费角色仍需明确配置和预算。

## 批次 C：长期型应有的区别

| 维度 | 快速型 | 长期型最小差异 |
| --- | --- | --- |
| 范围组织 | 一轮明确目标与必需功能 | 产品目标、待办、里程碑及其范围版本持久化；本轮只承诺已确认的里程碑 |
| 开工说明 | 短任务单 | 复杂能力/数据/接口有变化时补轻量影响与迁移说明；不恢复整套旧文档层级 |
| 交付 | 本轮目标真实验收通过后交付 | 每个里程碑有版本化试用；用户确认阶段结果后决定下一里程碑；修复过程中不逐工具追问 |
| 变更 | 新增目标进入下一轮确认 | 新建议可加入待办；用户选择本轮采用才改变当前承诺，不因模型提建议暂停制作 |
| 跨轮连续性 | 文件、上下文、可用版本保留 | 关键决策/接口/数据格式、未解决问题、回归基线、迁移/回滚与版本记录有明确身份和恢复协议 |
| 状态 | 本轮完成/未完成 | 当前里程碑完成、后续待办、用户暂停及产品归档分别表示；不能以本轮通过冒充全部产品目标完成 |

两种模式共用安全、真实验收、数据保护与费用硬保护。长期不等于无限调用；每次继续、里程碑或角色调用仍受已授权的 operation 与金额边界约束。用户明确授权的普通工程修复自主完成。

验收重点：不同模式真正走不同范围/里程碑策略；暂停/重启恢复当前阶段；旧确认不能套新版本；待办不自动进入实现；上轮有效行为和真实数据不丢；用户确认的候选与实际试用版本一致。用替身与隔离持久数据先验证。

## 批次 D：删除规则

- 先迁出共享的语音/文件/模型客户端等能力与验证器，再删旧编排。不能把旧工作流与可复用运行时混为一类。
- 历史记录、项目源文件、用户数据、旧实验失败及账本保留。删除执行代码不等于删除历史事实；旧预算/凭据不能因迁移清零或继承为新 PASS。
- 未标记项目不静默改 workflow_version。明确区分只读查看/启动/导出与继续编辑；继续编辑的迁移创建可回退副本并重新核对确认、能力和交付契约。
- 冻结实验保持历史身份，不重新发模型请求。若移除执行入口，应返回明确退役/迁移状态；不能默默按新流程运行旧实验配置。
- 全部旧入口具备去向后，更新调用关系、默认工具和测试，再删除无消费者文件。每批验证后提交，不 push；用户已有改动保持独立。
