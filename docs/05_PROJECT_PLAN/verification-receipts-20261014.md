# 分入口验证证据与交付收口

用户批准先优化重复验证，再用 GLM 常规 API 做真实冒烟，随后准备复杂任务对照。此前 DS 修复后两次成功仍用了 11/12、12/12 次脚本；后续无断言探测覆盖同一种工具的最后通过结果，交接又不能核对代码版本，调度器反复要求验证。

## 修复行为

- `run_project_script` 产生分入口、命令参数与超时绑定的宿主证据：源版本、环境版本、场景计数和 current/stale/unknown。后续探测不会覆盖另一个逻辑或 GUI 入口。
- 证据在受控工具写入审计之后保存到隔离 home 的 `verification-receipts/`，不让越权回滚结果留下通过缓存。真实命令始终执行；没有自动跳过或伪造新输出。
- 子 loop 结束、父读取交接、续接前重新投影当前版本。代码/测试、输入数据、解释器、受控安装代次及 venv 文件版本变化会使旧证据失效；不能核对时降为 unknown。后来的同命令 FAIL 替换先前 PASS。
- 剩余执行次数来自原持久账本，单独保留，不因压缩和续接丢失。成功用完第 12 次仍允许交付；再续接则在改变子状态和购买模型调用前拒绝。不换子会话清零。
- 提示词优先让调度器静态核对声明、补确实缺失或过期的验证。独立核心/GUI 验收照常执行，任务完整性仍由宿主判断。

登记文件 `CORE_CHECK.json / LAUNCH.json`、交付说明 `DELIVERY.md` 与 `00_VERIFY` 报告不作为业务源码版本变化；声明和需求覆盖另由交付门真实核验。环境版本使用解释器/venv 元数据、依赖文件大小与修改时间、白名单环境及受控安装计数，不保证检测恶意保留时间戳的环境篡改；隔离实验不能被外部进程同时改代码/环境。current 只表示该入口已报告断言对应的代码与受控环境，不能扩大成未测场景或全产品证明。
