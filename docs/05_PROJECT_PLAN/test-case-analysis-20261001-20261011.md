## 案例一：最新工艺推演器——复杂链路的技术闭环

### 需求与实际范围

用户提供具体工艺方案示例，并明确选择「内置库打底 + 可选接模型」、SVG/PNG 导出、参数化示意图随参数重绘。PRD 背板有 12 条需求，ProductShape 为 `record_manager`，事实来源是逐轮方案与参数集合，`llm_role=user_config`。

这里可讲的核心是**把自然语言样例转成可以保存、改参、回溯和验证的软件行为**。软件由平台模型生成，与产物内可选的外部 LLM 增强是两个层次。

### 主/子 Agent 实际活动

完整解析该项目索引内 19 个 Bloma 会话，共 1328 条 JSONL、767 个 `tool_use` 记录。包括 13 次 `delegate_agent`、6 次 `continue_delegation`、72 次 `run_project_script`、16 次 `drive_project_app` 和 3 次 `run_project_driver`。次数是协议调用数，不能当作独立测试用例数。

阶段遥测有 6 段：架构 1、骨架 1、实现 3、验收 1。实现前两段分别因 `no-marks` 和缺少 `DELIVERY.md`/`LAUNCH.json` 被退回，第三段完成；验收段一次通过。这说明链路能在返工后正确收口，同时也暴露了实现阶段的推进和产物协调成本。

### 两个真实缺陷与修复证据

**图纸未随改参重绘。** 子会话 `99792c85...` 执行 `00_VERIFY/integration_check.py`，曾输出「改参生成下一轮图纸重绘」FAIL，读不到新参数 1200；随后同一联调脚本该项 PASS。首次失败与后续通过均保留在工具结果中，体现执行反馈如何进入修复。

**数据已经存在，轮次链仍是空态。** 探索报告记录，点击生成后逻辑层 `list_rounds` 返回第 1 轮，但主区与侧栏仍为空列表。定位到 `select_round` 返回对象没有 `chain` 字段，而前端 `applyRound` 依赖 `round.chain` 更新轮次集合，属于 API 返回形态与渲染消费路径错配。

之后子会话 `27883a48...` 的真实程序回归输出四项 PASS：

1. 生成后主区与侧栏都出现第 1 轮。
2. 改参后都出现第 2 轮。
3. 点击节点能回溯，正文参数和图纸同步切换。
4. 切换示例后重新从第 1 轮开始，无上一示例残留。

这是组会最有说服力的一段：逻辑测试可以通过，GUI 探索仍能发现数据消费错配；系统依据复现证据修改，再用针对业务流程的检查证明修复兑现。

### 最终验收结果

- `driver-report.json`：exitCode 0、routing pass，`SUMMARY pass=14 fail=0 blocked=0`。驱动源码确实启动 WebView 程序，通过 `/eval` 的 DOM 动作与 `/call` 观测业务结果。
- `acceptance_coverage` 与交付事件：12 条需求均有映射并记录 passed。该指标按场景声明及其实际结果聚合，仍要结合每项验证范围解释。
- `fault-kill-report.json`：policy 为 standard，3 个核心项的故障注入明确 `not_run`；不能称为变异测试通过。

## 案例二：旧工艺推演器——为什么验收机制需要校准

旧项目保留 18 个会话、1472 条 JSONL、845 次工具调用。五次 verify 的拒因依次为：security-fail、test-invalid、driver-fail、fault-survived、fault-survived。

原排查有三类明确问题：名称扫描把 Python 方法 `.eval()` 当内置危险调用；静态来源比较把操作前后两次读取当同一值；种子报告说修改 `main`，实际修改遗留 `Logic.handle_send`，与产品的方案生成业务路径不对应。第三轮同时发现真实空态界面问题，不能把整次验收统称为误报。

平台 `06f4e90` 修正已复现检查器问题、种子定位和工具/预算装配，并采用 standard/strict 分级。随后新项目完成交付，说明该机制改动已经有真实运行案例支撑。

| 阶段运行段数 | 8 | 6 |
| verify 段数 | 5（均退回） | 1（通过） |

## 案例三：附件币种账本——自主测试 SOP 的完整例子

任务只要求依据附件与 sample.csv 展示/汇总、新增、导出和重启留存，明确不做登录、同步、删除等扩展。它与普通本地记账是两个不同项目。

材料与需求链路保留 source_refs；实施文档记录 10 条需求来源以及 38 次 material_read、13 个读取会话。主进程读取、材料进入上下文与模型理解分别解释，来源引用不自动证明理解准确。

历史中保留过失败：长路径原生 DLL 导入、启动解释器与项目环境不一致、实现子会话预算过小，以及误选旧失败项目续跑。后续使用短隔离 home、固定 project_id/root、统一 venv 并调整预算；正确目标最终续跑 delivered。测试失败和误选没有被抹成成功。

独立 `batch-c-gui-latest.json` 有六项 PASS：真实 WebView2 启动、两条样例及币种展示、表单保存改变 DOM 与磁盘、负数反馈且磁盘不变、CSV 保留 settlement_currency、重启留存。保存后页面记录第三条 USD 数据，导出文件和重启状态可回查。

这个案例可用于讲 SOP 的三个重点：固定身份和环境、验证真实业务差分、独立复验最终软件。报告的 176.223 秒仅是最终续跑；不能拿来作为从最初需求到完成的 Time-to-MVP。失败尝试、调平台、等待和续跑均应保留在完整时间线中。

## 案例四：快速型番茄钟与普通记账
