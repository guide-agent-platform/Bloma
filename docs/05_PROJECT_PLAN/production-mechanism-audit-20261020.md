# 制作阶段机制复查：硬编码、交接与执行事实

本轮按用户“额度不足时继续审查实现机制和不合理硬编码”的指示执行。没有新增模型调用，也没有改动旧 L1、L2 样本或已冻结的 a4b2054 运行副本。本文只记录实现审查与本地验证，不把它解释为新一轮模型性能结果。

## 发现与修复

| 机制 | 原问题 | 当前处理 |
| --- | --- | --- |
| 脚本参数 | 无提示地删除非字符串参数，并只执行前 8 个参数；调用者看到的请求与真实执行不一致 | 完整传递有效参数；最多 64 个、合计 16000 字符的有界请求，超界、错误类型、NUL 都明确拒绝；坏请求不消耗执行次数。 |
| 执行超时 | 非法、无限值或超界请求被静默夹到默认/极值 | 明确拒绝无效超时，90 秒默认与 5–180 秒有效区间一致；有限范围仍为进程保护。 |
| 自测凭据 | 同一命令先 PASS，后来异常、超时、取消或无断言结束，旧 PASS 可能继续被回读 | 后一次实际执行替换同一完整命令的凭据；没有断言保持 unverified。不同参数值的命令仍按完整命令哈希区分，显示标签不是凭据身份。无关的全新诊断不会清空已有业务证据。 |
| 交接事实 | 大量成功凭据可能挤掉失败事实，completed loop 进一步被读成“没有遗留问题” | 失败/阻塞、资源与终止预算按优先级保留；有实际失败的交接明确 incomplete，阶段推进与依赖释放均检查该事实。 |
| 改动文件清单 | loop 先截前 20 项，读取交接再把路径截至 160 字符，长路径变成不存在的文件身份 | loop 保留完整变更列表；交接仍提供有界 20 项摘要，但明确 omitted_changed_files 数量，完整保留列出路径，刷新证据时保留省略计数。 |
| 续接状态 | 状态工具宣称可续接，但实际工具会因累计脚本预算耗尽而拒绝 | 状态查询先刷新宿主凭据，调用与实际续接相同的准入策略，并返回具体禁止原因。 |
| 依赖释放 | 实现者 loop_status=completed 即可释放依赖，忽略已知失败交接 | 已结束但交接 incomplete 的依赖不能放行；需要原负责人修复。不把这个门禁升级成独立 GUI 质量认证。 |
| 跨轮取消与收尾 | stop 后复用委派记录续接，旧轮延迟返回和旧 abort 定时器可能结束/取消新轮；续接又缺少自己的超时收尾监听 | 每轮按自身 AbortController 归属判断回调、隔离元数据和超时收尾。初次与续接均安装自己的取消兜底；旧轮无权改新轮终态。独立取消模块封装单轮归属及兜底生命周期，拆分依据职责，不依据行数。 |
| 委派缓存回收 | 全局只留 50 个已完成记录，可能删掉仍在工作的父会话需要继续集成/修复的任务 | 只回收无活跃父上下文的终态记录；活跃父会话持有的任务不受这条清理规则影响。50 仍是闲置记录保留上限。 |
| 安装包推断 | 未列入平台组件表的发行包强行按包名 import，合法安装可能被误报失败；部分坏包声明又被静默过滤 | 支持显式 imports 映射，合法模块名校验在执行前完成；已有 Pillow/webview 等已知映射仍可复用。拒绝混合输入或错误声明，不悄悄少装包。 |
| 安装副作用 | 只有直接写文件和脚本接受范围审计，安装工具能间接改 requirements.txt 或写业务辅助源码 | 安装后的源码变更同样检查任务写入范围和冻结输入，越界回滚；.venv 的包安装属于既有环境通道，不将源文件回滚描述成能撤销 pip。 |
| 旧案例侵入通用流程 | 安装 pywebview 就生成文件前缀改名专用组件，并向任意 GUI 项目讲解改名业务；安装刀还常驻语音版本/组件清单 | 移除 GUI 安装到改名源码的隐式关联；组件目录注明按需使用及实际物化状态。安装刀只提供安装/导入协议，语音指引走按需领域上下文。已有骨架工具不因本次审查删除。 |
| 专用探针适用条件 | 将所有功能描述拼接后找关键词，两个无关功能的“前缀”“改名”能拼出不存在的能力；任意“撤销”需求会强迫改名功能带撤销 | 前缀与改名必须在同一功能中成立；撤销必须明确关联前缀/改名。保留已有文件反例及失败门禁，不凭普通 GUI 库选业务验收。 |
| 验证指纹 | data、00_VERIFY、00_UX 被整体当成可变数据，目录内执行代码改变后可能仍复用通过记录 | 这些目录中的 Python/JS/HTML/CSS 等可执行输入纳入指纹；脚本收据也不再忽略 00_VERIFY 内的可执行测试代码。宿主交付预览页是输出，使用与生成方同源的路径定义明确排除，避免生成报告反而使自身验收过期。 |
| 架构门禁 | 物理行数超过 800 即判失败，却另列大文件豁免；注释、排版与清晰的同职责逻辑也会被误当成架构违规 | 移除尺寸硬断言与豁免表，独立 `npm run report:source-size` 输出可配置阈值的审查清单。依赖方向、入口归属和过渡桩检查仍保留。 |

用户明确追问了 800 行限制是否合理。经历史核对，尺寸断言由 `aa2b48e` 的 PR3b 大文件拆解引入；这是一项历史治理约定，没有“801 行必然架构恶化”的测量依据。默认 800 现在只方便对比历史清单，允许 `--threshold` 修改，尺寸报告不会因为超出该数值失败，也不再隐藏旧豁免文件。职责内聚、依赖方向和可测试性需要结合具体改动审查，不能用行数测试替代。

## 保留的边界及理由

- 委派深度 1 层、普通父会话并行 4 名，是当前协作机制的边界；G11 的独立冻结配置仍是最多 2 名实现者。并行人数、总名额和调用次数分别判定，不以提高默认人数代替并行实证。
- 普通制作默认脚本 12 次/安装 4 次；本实验显式的脚本 64 次/安装 8 次、D60/E100、256 请求及 60 分钟墙钟保持原条件。用户取消的是金额上限，不是这些操作保护。
- V 的 12 个普通 loop 轮次是当前有界审阅策略；通用 loop 的辅助收口仍计入同一请求账本，因此实际请求数可能高于 12。已完成的真实 V 诊断为 12 主轮 + 2 收口，不能说“只花了 12 次”。这与 E 的轮次独立。
- 脚本和安装期间的项目写租约仍串行，避免另一个实现者的合法改动被快照审计误当成副作用。它限制的是修改/执行临界区；模型请求仍可并行。这个取舍会影响吞吐，不能声称上下文精简已消除所有耗时。
- 20 项路径、6 项待办和有界凭据是交接摘要预算；当前路径不再损坏，省略改动明确标记。摘要之外仍应查子会话历史、实际文件和宿主报告，不能把摘要当全量修改清单。
- 代码读写范围、源文件回滚、输入封存不是操作系统沙箱；受控 Python 可运行任意产品逻辑，不能据此声称恶意代码隔离成立。

## 仍然明确存在的设计限制

专用文件探针仍只认识平台的两类 Logic 接口；能力选择仍存在需求文字匹配，语音/LLM 同样如此。此次修正了跨功能拼词与无关撤销误触发，没有把词匹配包装成完整语义理解。后续扩展应由需求侧确认的能力与显式适配协议选择探针；遇到未支持的接口仍如实 environment_blocked，不删除失败门禁来获得绿色结果。这个限制不额外施加到 L1 待办应用。

可变目录里的 JSON 等数据不自动都成为验证输入；业务夹具或外部输入仍需显式归入验证协议。目录内可执行代码已补入指纹，这不等于验证器能自动发现任意程序的完整输入依赖。

本轮修复以具体反例为界：不修改冻结 L1 六项业务期望，不加入 L2 的额外功能，也不据本地测试推算模型提速或质量。

## 验证与发布纪律

首批针对性 8 文件 136 例通过；后续架构、核心验收、指纹、凭据、协作及通用 loop 的 6 文件 172 例通过。首轮全量 279 文件出现 1 个当时的行数断言失败（协作文件 803 行），其余 2592 例通过；取消生命周期已按职责独立，随后用户追问促成对行数硬门本身的修正，不能把机械缩短文件称为架构质量提升。

下一轮全量 279 文件/2598 例中，2594 例通过，4 例暴露交付确认预览 HTML 误入验证输入的问题。已将宿主预览输出的声明集中，并修正两个指纹消费者；核心、路由、交付确认、凭据与架构等 7 文件/93 例回归通过。尺寸报告的独立 2 文件/4 例也验证“大文件提示仍退出成功”和可调整阈值。最终全量、类型及构建结果在主流程文档补记，失败日志保留。

最终稳定源码全量 280 文件/2598 例通过，集成 2 文件/8 例通过，类型检查与完整构建均成功。完整回归日志 `production-v2-mechanism-unit-release.log`，其余最终日志为 `production-v2-mechanism-closure-typecheck.log`、`production-v2-mechanism-final-build.log` 和 `production-v2-mechanism-final-integration.log`。没有把删掉行数断言当成修复交付流程；预览页指纹的 4 个失败由输出/输入语义区分修复，并继续保留实际代码变化使证据过期的断言。

新的实现补丁必须经过匹配代码版本的运行封存才可启动。审查期间 resume-G11 控制器以 audit-ready.json 门禁保持等待，旧 prototype cohort 不会因为供应商恢复额度自动启动。任何后续真实样本继续使用独立新 home/run id，旧样本与失败证据不改写。
