# 开发工作流定义

> 项目：向导Agent与编程Agent多智能体协同开发平台
> 文档ID：DOC-5.3
> 版本：v1.0 | 日期：2026-07-10 | 状态：已确认
> 依赖：PRD v5.0（§6.6、§8、§10、§16）、DOC-3.1 `architecture.md`、DOC-5.1 `sprint-plan.md`、DOC-5.2 `team-config.md`、`proma-core-demo`

---

## 1. 文档目标

本文档定义本平台开发过程中的三套核心工作流：

1. **文档工作流**：文档产出 → 评审 → 确认
2. **代码工作流**：编码 → 审查 → 测试 → 合并
3. **Sprint 工作流**：计划 → 执行 → 验收 → 回顾

同时定义异常处理和阻塞升级规则。所有工作流遵守 PRD §8 三道门模型和 PRD §10 裁判 Agent 机制。

## 2. 文档工作流

### 2.1 文档生命周期

```
草稿 ──→ 待审 ──→ 已确认
  │         │         │
  └─── 修订 ───┘         │
                         ↓
                    冻结（可被后续版本引用）
```

### 2.2 草稿 → 待审

**触发条件**：作者完成文档全部必填章节，自检通过。

**自检清单**（作者执行）：
- [ ] 元信息完整（文档ID、版本、日期、状态、依赖）
- [ ] 必填章节齐全（对照 `设计阶段-文档产出清单与质量标准.md`）
- [ ] 跨文档引用路径可解析
- [ ] 无明显的与 PRD 矛盾

**产出**：文档状态更新为"待审"，通知评审人（见 §5 角色分工）。

### 2.3 待审 → 已确认

**评审流程**（评审人执行）：

```
评审人收到待审文档
       │
       ▼
┌─────────────────┐
│ G1 完整性检查    │ ← 对照清单检查必填章节、元信息、依赖文档是否已确认
└──────┬──────────┘
       │ 通过
       ▼
┌─────────────────┐
│ G2 一致性检查    │ ← 与 PRD v5.0 及其他已确认文档逐项核对
└──────┬──────────┘
       │ 通过
       ▼
┌─────────────────┐
│ G3 可执行性检查  │ ← 文档内容是否可直接用于下一阶段（编码/测试可据此开工）
└──────┬──────────┘
       │ 通过
       ▼
┌─────────────────┐
│ G4 可读性检查    │ ← 结构清晰、术语一致、图表有标注
└──────┬──────────┘
       │ 通过
       ▼
  状态: 已确认
```

**不通过处理**：
- G1/G4 不通过 → 标注具体问题，退回作者修改
- G2 不通过 → 标注矛盾项（引用 PRD 章节 + 矛盾内容），退回作者修改或发起跨文档协同修订
- G3 不通过 → 标注不可执行的具体原因，退回作者补充

**评审时限**：每份文档评审不超过 1 个工作日。超时未完成 → 升级给 A 角色协调。

### 2.4 已确认文档的修订

已确认文档如需修订（因 PRD 更新、架构变更等原因）：

1. 提出修订原因和影响范围
2. 更新文档内容，版本号 +0.1
3. 状态回退为"待审"
4. 重新走 §2.3 评审流程
5. 评估是否需同步修订依赖此文档的下游文档

### 2.5 文档依赖链管理

文档产出必须遵守清单 §三 的优先级顺序：

```
第零层 PRD ✅
    ↓
第一层 user-stories、glossary（可并行）
    ↓
第二层 UX 文档（顺序依赖：sitemap → user-flows → wireframes/design-system/interaction-spec 可并行）
    ↓
第三层 架构文档（顺序：architecture → class-diagram → sequence-diagrams → data-model）
    ↓
第四层 api-spec（依赖架构全部确认）
    ↓
第四层 sprint-plan、team-config、workflow（可并行）
    ↓
第五层 test-plan → features（依赖 user-stories 和 user-flows）
    ↓
第六层 changelog、README（依赖以上全部）
```

当前状态：第零层至第四层（除 team-config、workflow）及第五层、第六层已产出，待确认。

**规则**：
- 依赖链上层的文档确认后，下层方可标记"已确认"
- 上层文档修订 → 下层文档需评估是否受影响 → 受影响则同步进入修订流程
- 并行组内的文档互不阻塞，可同时推进

## 3. 代码工作流

### 3.1 总览

```
Sprint 任务分配
       │
       ▼
┌──────────────┐     ┌──────────────┐
│  开发编码     │ ←→ │  即时审查     │  ← 每个模块完成后触发
│  (R1 全栈开发)│     │  (R3 代码审查员)│
└──────┬───────┘     └──────┬───────┘
       │                    │
       │    ┌───────────────┘
       │    ▼
       │ 审查通过
       │    │
       ▼    ▼
┌──────────────┐
│  测试验证     │ ← R2 编写/更新 Feature → 运行 E2E
│  (R2 测试)   │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  安全扫描     │ ← R4 自动 OWASP + 依赖 CVE 检查
│  (R4 扫描器) │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  裁判门禁     │ ← 硬约束（脚本自动）+ 软约束（AI 评估）
│  (裁判 Agent) │
└──────┬───────┘
       │ 通过
       ▼
     合并
```

### 3.2 开发编码（R1）

**启动条件**：对应用户故事的状态为"已确认"（P0）或"已规划"（P1/P2），且无阻塞依赖。

**编码规范**：
- 所有新增 IPC 通道从 `shared/types.ts` 常量定义开始
- 使用 `safeStorage` 加密 API Key（`channel-manager.ts`）
- Renderer 代码通过 `window.electronAPI` 调用能力，不直接 import Node.js 模块
- 存储操作只写 `~/.proma/` 下的 JSON/JSONL/工作区目录
- 关键架构决策标注为 `[DECISION]` 格式（见 PRD §5.4）

**自动修复循环**（代码运行失败时）：
```
运行失败
  → R1 自动分析错误
  → 修复代码
  → 重新运行
  → 成功 → 继续
  → 失败（第 2 次） → 再修复
  → 失败（第 3 次） → 熔断 → 回滚到最近健康快照 → 通知人类开发者（A 角色）
```

**自动修复上限**：3 次（与长期迭代型一致，见 PRD §6.6）。安全问题不计入普通修复次数（见 PRD §10.5）。

### 3.3 代码审查（R3）

**触发条件**：R1 完成一个模块或一组关联文件后提交审查。

**审查维度**（按优先级排序）：

| 优先级 | 维度 | 检查内容 |
|:---:|------|---------|
| 1 | Proma core 边界 | Renderer 是否直接访问 Node.js API；IPC 通道是否从 shared 常量引用；API Key 是否进入 renderer |
| 2 | IPC 链路完整性 | shared 定义 → main handler → preload bridge → renderer atoms 四层是否对齐 |
| 3 | 安全 | `safeStorage` 是否正确使用；是否存在 XSS/注入风险；Electron `webPreferences` 配置是否安全 |
| 4 | 正确性 | 逻辑是否正确；边界条件是否覆盖；错误处理是否完备 |
| 5 | 可维护性 | 模块边界是否清晰；命名是否一致；是否有冗余代码 |

**审查结果**：

| 结果 | 含义 | 下一步 |
|------|------|--------|
| ✅ 通过 | 无问题或仅有 cosmetic 建议 | 进入测试 |
| ⚠️ 建议修改 | 有非阻塞问题，建议修改 | R1 决定是否修改后进入测试 |
| ❌ 退回 | 有阻塞问题（Proma core 边界违规/安全漏洞/逻辑错误） | R1 必须修复后重新提交审查 |

### 3.4 测试验证（R2）

**触发条件**：代码通过 R3 审查（或标记为"建议修改"但 R1 选择暂不修改）。

**测试流程**：
1. 对照 user stories 和 interaction-spec 编写/更新 GWT Feature 文件
2. 运行 Feature → 记录通过率
3. 运行现有回归测试套件 → 确保无回归
4. 验证 Proma core 边界测试骨架仍通过
5. 输出测试报告，更新 `test-plan.md` 中的通过率数据

**测试不通过处理**：
- GWT 场景失败 → 标注失败场景 → 退回 R1 修复 → 修复后重新运行
- 回归测试失败 → 排查是否为修复引入 → 如是则退回 R1；如为测试过时则更新测试
- Proma core 边界被破坏 → 立即阻塞，升级给 A 角色

### 3.5 安全扫描（R4）

**触发条件**：代码通过测试后自动触发。也可在 R1 提交任意模块后手动触发。

**扫描内容**：
- OWASP Top 10 漏洞（XSS、注入、敏感信息泄露等）
- 依赖项已知 CVE（`npm audit`）
- Electron 安全配置（`nodeIntegration`、`contextIsolation`、`sandbox`）
- API Key 明文检测（grep `ANTHROPIC_AUTH_TOKEN` / `apiKey` 在 renderer 目录）

**扫描结果**：

| 严重度 | 处理 |
|--------|------|
| Critical / High | 阻塞合并。R1 必须修复 → 重新扫描 → 全部清除后方可继续 |
| Medium | 记录 issue，不阻塞当前 Sprint 但必须在下一个 Sprint 修复 |
| Low | 记录 issue，可延后处理 |

### 3.6 裁判门禁

**触发条件**：代码通过测试且安全扫描无 Critical/High 后方可触发。

**硬约束**（脚本自动执行，不通过直接退回）：

| 检查项 | 规则 | Phase 1 适用性 |
|--------|------|:---:|
| 文档存在性 | PRD 文件存在且含必填字段（项目名称、核心功能） | ✅ |
| GWT 存在性 | 每个 P0 用户故事至少有 1 个 Feature 场景 | ✅ |
| 测试通过 | 所有 GWT Feature 全量通过 | ✅ |
| 安全 | 无 Critical/High 漏洞 | ✅ |
| PlantUML 一致性 | 代码结构与 PlantUML 一致 | ❌ Phase 2 启用 |
| API Spec 完整 | 每个端点完整定义 | ❌ Phase 2 启用 |

**软约束**（AI 评估）：

| 评估维度 | Phase 1 适用性 |
|---------|:---:|
| 逻辑一致性（PRD 功能与代码模块对齐） | ✅ |
| 完整性（边界条件和异常覆盖） | ✅ |
| 可执行性（代码可直接运行） | ✅ |
| 可读性（代码注释和文档可理解） | ✅ |

**退回处理**（PRD §10.4）：
- 第 1 次退回 → R1 自动修复 → 重新进入裁判
- 第 2 次退回 → R1 再次自动修复 → 重新进入裁判
- 第 3 次退回 → 系统提示人类开发者（A 角色），附具体偏差描述
- 人类选择：继续修复 / 接受现状（记录为"已知偏差"）

安全问题不计入此退回次数（见 PRD §10.5）。

### 3.7 合并

**合并条件**（全部满足）：
- [ ] R3 审查通过或建议修改已处理
- [ ] R2 GWT Feature 全部通过
- [ ] R4 安全扫描无 Critical/High
- [ ] 裁判硬约束全部通过
- [ ] 裁判软约束通过或已知偏差已记录
- [ ] 人类开发者（A 角色）最终确认

**合并后**：
- 触发快照（如是关键节点：草图生成后 / MVP 首次生成后 / 一轮修改确认后）
- 更新 changelog
- 通知团队成员

## 4. Sprint 工作流

### 4.1 Sprint 周期

```
Sprint 计划会（1-2h）
       │
       ▼
┌──────────────────────────────┐
│  执行期（1-2 周）              │
│                              │
│  每日站会（15min，异步可替代） │
│  文档/代码按 §2-3 工作流推进  │
│  阻塞问题在 4h 内升级         │
└──────────────┬───────────────┘
               │
               ▼
        Sprint 验收会（1h）
               │
               ▼
        Sprint 回顾会（30min）
```

### 4.2 Sprint 计划会

**参与人**：A（工程负责人）、B（前端/UX）、C（测试/研究）

**输入**：`sprint-plan.md` 当前 Sprint 定义、上一 Sprint 回顾结论

**产出**：
- 本 Sprint 的用户故事列表（从 `user-stories.md` 挑选）
- 每人的任务卡片（含验收标准）
- 风险识别和缓解措施

**约束**：
- 每个 Sprint 不超过 2 周
- 每人至少认领 1 个任务
- P0 用户故事优先

### 4.3 每日站会（异步）

每个工作日成员在共享频道更新：
- 昨天完成了什么
- 今天计划做什么
- 有没有阻塞

阻塞问题在 4 小时内无人响应 → 升级给 A 角色。

### 4.4 Sprint 验收会

**参与人**：A、B、C 三人全部参与

**验收标准**（按角色）：

| 角色 | 验收重点 |
|------|---------|
| A 工程负责人 | 运行链路可走通；Proma core 边界未破坏；IPC 四层对齐；Agent 编排逻辑正确 |
| B 前端/UX | P0 用户体验可走通；等待/错误/成功状态文案符合心理防御规范；预览和点选纠错可交互 |
| C 测试/研究 | GWT Feature 全部通过；Proma core 边界测试通过；埋点事件正确写入 `analytics.jsonl`；脱敏导出可用 |

**验收结论**：
- ✅ 全部通过 → Sprint 完成，进入回顾
- ⚠️ 部分通过 → 未通过项记录为下个 Sprint 的优先任务
- ❌ 核心目标未达成 → Sprint 不关闭，未完成任务延续至下个 Sprint（需调整下个 Sprint 的容量规划）

### 4.5 Sprint 回顾会

**讨论三个问题**：
1. 这个 Sprint 什么做得好？（保持）
2. 什么做得不好？（改进）
3. 下个 Sprint 试什么新做法？（实验）

**产出**：回顾记录（追加到 `sprint-plan.md` 对应 Sprint 章节下）。

## 5. 角色分工与审批矩阵

按 `sprint-plan.md` §1 固定三人分工：

| 角色 | 人员 | 职责 |
|------|------|------|
| A | 工程负责人/全栈 | Proma fork、主进程、IPC、AgentOrchestrator、权限服务、沙箱、MCP 工具 |
| B | 前端/UX 工程 | 工作区 UI、Jotai atoms、全局监听器、预览区、点选纠错、时间轴、P0 文案 |
| C | 测试/研究工程 | GWT Feature、E2E、文档一致性、埋点、脱敏导出、研究指标校验 |

**审批矩阵**：

| 审批事项 | 必须审批人 | 可选审批人 |
|---------|-----------|-----------|
| 文档"待审"→"已确认" | 与该文档领域最相关的人（非作者） | 另外两人 |
| 代码合并 | A（必须） | B、C |
| 架构变更 | A（必须） | B、C |
| UX/交互变更 | B（必须） | A |
| 测试策略变更 | C（必须） | A |
| Sprint 计划 | 三人全部 | — |
| Sprint 验收 | 三人全部 | — |

## 6. 异常处理与阻塞升级

### 6.1 异常分类

| 异常类型 | 示例 | 处理方式 |
|---------|------|---------|
| **技术阻塞** | SDK binary 不可用、依赖安装失败、沙箱崩溃 | R1 自行排查 2h → 未解决则升级给 A |
| **需求模糊** | 文档描述有歧义、用户故事边界不清 | 回溯 PRD 或发起快速讨论 |
| **文档矛盾** | 两份已确认文档对同一概念定义冲突 | 按照文档优先级链裁决（见 `UX设计自动化方法论-v0.9.md` §0.4） |
| **Agent 失败** | Agent 生成代码无法通过裁判、自动修复 3 次熔断 | 人类接手，分析根因后决定方向 |
| **跨角色分歧** | R3 认为要修，R1 认为不用修 | 提交给对应领域的人类角色裁决 |
| **时间风险** | Sprint 过半但关键任务未启动 | A 角色重新评估 Sprint 容量，必要时调整范围 |

### 6.2 升级路径

```
问题发现者
    │
    ├── 自行处理（如能在 2h 内解决）
    │
    └── 无法解决 → 升级给领域负责人（A/B/C）
                    │
                    ├── 能解决 → 记录解决方案
                    │
                    └── 无法解决 → 三人讨论
                                    │
                                    ├── 能解决 → 记录决策
                                    │
                                    └── 涉及范围变更 → 更新 sprint-plan
```

### 6.3 回滚与恢复

代码层面的回滚（PRD §13.4）：
- 严重 bug 或架构跑偏 → 从时间轴选择最近健康快照 → 线性回滚
- 回滚后：被回滚的提交不丢失（保留在时间轴上），继续从回滚点开发
- 回滚前必须创建当前状态快照

**文档层面的回滚**：不适用。文档修订通过版本号管理（见 `changelog.md`）。

## 7. 工具链与自动化

### 7.1 必要的自动化检查

| 检查点 | 触发时机 | 工具 |
|--------|---------|------|
| TypeScript 类型检查 | 每次 commit 前 | `npm run typecheck` |
| Lint | 每次 commit 前 | ESLint |
| 单元测试 | 每次 commit 前 | Vitest |
| GWT Feature | 每次 push 前 | Playwright + Cucumber |
| 安全扫描 | 每日 + push 前 | `npm audit` + 自定义扫描脚本 |
| Proma core 边界 | push 前 | 自定义边界测试（`features/proma-core-boundary.feature`） |

### 7.2 手动操作清单

| 操作 | 谁执行 | 何时 |
|------|--------|------|
| 创建快照 | A | 关键节点（草图/MVP/修改确认/高风险操作前） |
| 裁判门禁触发 | A 或 CI | Sprint 交付前 |
| 埋点数据脱敏导出 | C | Sprint 3 起每 Sprint 结束时 |
| 文档一致性检查 | C | 每份文档"待审"→"已确认"时 |
| changelog 更新 | 变更执行者 | 每次合并后 |

## 8. Proma Core 约束的贯彻

所有工作流步骤必须遵守 `proma-core-demo` 的三条核心设计：

### 8.1 IPC 四层链路

**新增 IPC 通道的操作顺序**（不可跳过任一步）：
```
1. shared/types.ts  → 定义通道常量 + 请求/响应类型
2. main/ipc.ts      → 注册 ipcMain.handle
3. preload/bridge.ts → contextBridge.exposeInMainWorld 白名单
4. renderer atoms    → Jotai atomFamily + useGlobalAgentListeners
```

代码审查（§3.3）必须验证此顺序。

### 8.2 Agent SDK 编排

关键检查点（来自 `orchestrator.ts` 的 5 个工程难题）：
- SDK env 是否以 `process.env` 为底构建？
- for-await 循环是否正确触发 `iterator.return()`？
- 并发守卫 `activeSessions` Set 是否生效？
- 自动重试是否在 25 次/5 分钟限制内？

### 8.3 Local-First 存储

- 运行时存储只能使用 `~/.proma/` 下的 JSON/JSONL/工作区目录
- 不得引入 SQLite 或其他运行时数据库
- API Key 必须经 `safeStorage.encryptString()` 加密后写入 `channels.json`
