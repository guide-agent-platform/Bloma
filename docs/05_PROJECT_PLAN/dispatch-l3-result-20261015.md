## 条件与执行

- 样本：`l3-method-S1-20261015-r2-640k`；项目 `8d8cf9fe-9d5e-4e27-bd9a-ab5520d83d4a`。
- 代码版本 `1a21d6d16240a3c97459b916f3a340f21a6ef740`，运行包 SHA256 `6099528698adda92fb9bb6d354e0b4ad888a8751d829d97eed97f9471b5b7969`。
- 直接实现 S1，实际请求均为 `api.deepseek.com` 的 `deepseek-flash`，thinking_level=low；没有新增 GLM 付费请求。
- 主循环请求的 max_tokens=640000，表示思考和可见回答合计的输出上限，并非强制消耗、专门思考配额或服务端保证可生成长度。显式较小的辅助请求仍保留自身上限。GLM 常规 API 另有 131072 的本地模型上限，未宣称向它实际发送 640000。
- 冻结限制：单执行者、16 个任务、D40/E64、整样本最多 128 次逻辑请求、30 分钟；脚本 12 次、安装 4 次为会话范围。
- 实际运行约 14 分钟（840137ms），106 次逻辑/106 次物理请求，3 次实现阶段尝试。首次交付检查未通过后继续两次，不能描述为一次没有续跑的 64 轮样本。
- 106 次均有用量，输入 6166209、输出 124692、缓存读取 5840000。结束原因：101 tool_use、4 end_turn、1 max_tokens。最后一项来自上限为 1024 的 handoff 辅助请求；不能称所有请求均未截断。
- 主循环单次实际最高输出 21440，另有 8739、11106 的响应超过旧 8192 上限。这说明旧限制影响了本样本，不能证明 640000 必要或对所有任务充分。

三项失败：

1. **project-delete-guard**：界面没有可到达的项目删除入口，后台存在函数不能满足界面删除验收。
2. **import-atomic-idempotent**：使用全新 ID，先放合法记录、再放 `2026-02-30` 记录，界面提示成功，任务从 3 条变成 5 条。证明导入缺少真实日历日期校验；不能由此额外推断“已报错操作只回滚一半”。
3. **multiwindow-conflicts**：两个独立进程共享同一数据目录，编辑不同任务出现覆盖丢失。进一步打开同一任务的旧表单，先保存 `A-new`，再从旧窗口保存 `A-stale`，仍提示成功，重启后保持 `A-stale`，没有拒绝过期版本。
