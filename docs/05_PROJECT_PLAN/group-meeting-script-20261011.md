## 一、研究目标（约 45 秒）

老师、同学们好，我今天汇报一下 Bloma 的整体流程、关键技术和评价指标，最后简要介绍最近的推进。

Bloma 是一个基于多 Agent 协作的软件生成实验平台，目前聚焦 Windows 桌面应用。面向的用户是有使用需求、但缺少开发经验的人。用户可以用自然语言描述想法、提供参考材料，再通过需求确认、界面预览和修改反馈，逐步得到可以运行的软件。

我们关注的研究问题是：怎样组织非专业用户的自然语言需求，能让大模型更准确地理解意图，并以更少的沟通和资源消耗完成开发。这需要同时观察生成结果、开发过程和用户体验，最终用对照实验来检验。

## 二、从想法到交付的流程（约 1 分 45 秒）

对用户来说，流程可以概括为五步：想法、需求、界面、制作、试用与交付。

第一步是表达想法。用户可以输入一句话，也可以提供图片、文本或表格材料。比如用户说：“我要一个记账工具，能导入记录，拒绝负数金额，导出时保留币种。”向导 Agent 会围绕使用场景、输入输出和边界继续澄清。

第二步是形成并确认需求。我们把这段描述转为结构化的需求文档，明确功能、约束和验收条件。比如“拒绝负数”要具体成：出现什么提示，是否允许保存，原来的数据会不会被改动。用户确认之后，这份需求成为后续开发共同遵循的依据。

第三步是看界面草图。这里主要确认页面结构和操作方向，还不能把草图当成已完成的软件。用户可以认可，也可以说明或标记哪里需要调整，让界面层面的理解偏差尽早暴露。

第四步进入制作。快速型偏向尽快做出可用工具，减少工程阶段；长期型内部则经过架构、骨架、实现和验证。用户不用逐个批准内部步骤，平台根据阶段产物和检查结果推进。

第五步是试用和交付。平台做相应检查，长期型还提供成品过目节点。用户继续提出修改意见时，系统记录修改意图，再进入相应的调整流程。项目也保留版本和会话记录，支持回看与恢复。

这个流程里，用户主要负责确认需求、判断界面方向和试用结果；平台负责把这些选择转为开发任务，并组织执行和验证。

## 三、关键技术（约 2 分钟）

这里有四个关键技术点。

第一个是需求的结构化传递。我们保留用户原始描述，同时提取功能、约束和可验证的行为条件；使用附件时，还能记录材料的版本、哈希和来源范围。实现 Agent 得到完整需求和相关上下文，验证阶段再把测试场景映射回对应需求。这样可以检查用户要求有没有在多次转述中丢失。

第二个是有状态的多 Agent 编排。向导负责澄清，架构、实现和验证角色负责不同任务，编排器维护当前阶段、合法推进方向和已有证据。每个角色获得与任务匹配的工具和上下文。模型提出行动和推进建议，平台再检查产物和结果。看门狗负责超时、预算和挂起状态，检查点保存阶段结论，减少无效重跑。

第三个是受控执行与真实反馈。Agent 可以在项目范围内读写文件、安装依赖和执行脚本，也可以通过驱动操作生成程序。当前默认桌面骨架使用 Python 处理业务逻辑，pywebview 和 WebView2 承载本地界面；Bloma 平台自身使用 Electron。验证时可以检查逻辑结果、界面变化和磁盘数据，例如点击保存后，记录是否真的写入，重启后是否仍然存在。

第四个是证据分级和可追踪记录。长期型把核心需求、驱动场景和执行结果关联起来，并保留入口、安全检查及启动证据。当前默认标准模式中，静态检查作为诊断；严格模式再增加静态反空和故障种子检查。没有执行的检查会明确记录，不能写成通过。会话、工具调用、阶段结果和 token 使用写入本地记录，方便失败归因和后续统计。

这几部分共同形成一个闭环：需求可定位，任务可执行，结果有证据，失败能追踪。

## 四、评价指标怎样定义（约 2 分 30 秒）

指标上，我把它们分成效率、质量、资源和交互四个维度。

效率首先看 Time-to-MVP，也就是从统一的实验开始时刻，到软件通过预先定义的独立验收需要多久。还可以记录首次可交互界面出现的时间，用来观察用户多久能得到第一份可看、可操作的结果。这两个时间终点要分开：草图出现不等于软件已经可用。我们也会区分模型与执行耗时、用户等待时间，并报告中位数和较慢任务的表现。

质量首先看成功闭环率：在固定时间和资源限制内，通过同一套关键任务验收的试验数，除以有效试验总数。结束运行或标成完成，不能直接算成功。比如记账任务，就要实际检查导入、保存、负数拒绝、导出和重启留存。失败的任务也要保留，避免只统计成功样例。

另一个质量指标是需求覆盖。评价时需要分别记录多少已确认需求有验证场景，以及多少需求真正通过。分母使用预先确定的需求集合，未映射或未通过的项也保留。场景数量多不一定表示覆盖更好，关键是它们是否检验了用户真正关心的行为。

资源方面记录整个任务的输入、输出 token，以及重试和子会话的消耗。比较时可以看每次试验的总 token，也可以看每个通过验收的固定关键任务消耗多少 token。统计需要避免父子汇总重复计数，缺失的数据要标出来，不能当成零。

交互方面记录用户澄清和修改的轮次，尤其是用户为同一个理解错误反复解释了多少次，再结合易用性、操作负担评分和访谈。这里要区分用户主动增加新需求，与系统没有理解原需求造成的返工。

此外，我们用阶段尝试次数、失败分类和耗时长尾解释原因：到底是软件业务错误、验证协议错误、模型或环境故障，还是预算耗尽。当前这些过程字段已有采集；完整实验口径和主观评价仍需要统一。最近的工程测试通过，只能证明相应实现经过检查，还不能证明上述研究指标已经提升。

## 五、最近的推进（约 1 分钟）

最近从十月一日到十一日上午，工程上有一百二十五次提交，主要推进了三方面。

第一是收敛生成路线，集中到 Windows 桌面软件，并补齐实现者的执行工具、项目环境和委派反馈。第二是完善附件、草稿、消息恢复和会话分支，让原始需求与材料能够可靠传到实现者。第三是修正验收误报和预算不匹配，并重做界面，采用白色通透画室，把软件画布和简短交流作为主要内容。

验证方面，最近一轮全量平台回归有两千二百零二项单元测试通过记录，后续细节也做了定向和真实界面检查。另有一个附件驱动的记账样例，走通了真实模型生成，并独立验证保存、错误输入、导出和重启留存。这证明了部分链路能跑通，还不能推广为所有任务或模型都稳定。

## 六、下一步（约 30 秒）

下一步，我准备先固定任务、模型、环境和总资源预算，完成小规模试验。先比较 Bloma 与普通对话流程的整体完成效果，再在相同执行条件下比较不同需求组织方式，逐步判断收益来自哪里。

接下来会优先统一指标起止点和验收标准，保留失败样本，补齐交互记录与问卷。希望最终回答的是：哪些自然语言组织方式和协作机制，能够持续降低非专业用户完成软件任务的成本。

我的汇报到这里，谢谢大家。
