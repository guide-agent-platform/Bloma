## 一、目前做到哪一步（约 45 秒）

老师、同学们好。今天我主要汇报 Bloma 的关键技术，以及 Agent 自主测试是怎样组织的。

Bloma 面向缺少开发经验、但有明确使用需求的人，通过自然语言和参考材料驱动软件开发。目前从需求澄清、界面确认、代码实现，到测试、修复和交付，整条链路已经跑通并通过测验。我们已经有一套能够实际执行和验证的软件生成流程。

研究上，接下来关注的是：这种需求组织和协作方式，怎样影响用户完成软件任务的效率、质量和资源消耗。

## 二、整体流程（约 30 秒）

用户看到的是五步：想法、需求、界面、制作、试用与交付。用户确认需求和界面方向后，平台组织开发；发现问题则携带反馈进入修复，再复验和交付。

内部有快速型和长期型两条路径。快速型减少工程阶段，尽快做出可用工具；长期型经过架构、骨架、实现和验证，并增加成品过目节点。下面重点讲支撑这两条路径的技术。

## 三、关键技术（约 4 分钟）

### 1. 自然语言需求的结构化规约

第一个技术是把用户的话转成可传递、可验证的开发约束。

比如用户说“金额不能是负数”，我们会把它具体化为条件、操作和预期结果：输入负数并点击保存时，界面给出提示，新增记录不落盘，原有记录保持不变。需求文档中保留功能、边界、优先级和行为断言，后续实现与验证角色使用同一份已确认需求。

对于附件，我们保存不可变材料快照，用 ID、哈希和行范围定位来源，并把授权材料传到子会话。这样，从用户原始材料到需求、实现和测试，都有可以回查的对应关系。

另外，我们引入了 ProductShape，把即时工具、记录管理、文件处理和任务运行等类型的主流程、状态和数据来源表达清楚。这让 Agent 能根据产品类型组织实现和测试，减少开发过程中对任务形态的反复猜测。

### 2. 阶段状态机与多 Agent 委派

第二个技术是把阶段状态机和模型自主决策结合起来。

平台用阶段表描述每个阶段的目标、产物、检查条件和合法下一阶段。编排器读取当前状态，把具体工作委派给架构、实现、研究或验证角色。每个子会话有独立任务、上下文和执行记录，再把结果返回父会话。

模型负责阶段内的行动选择，平台负责核对推进条件。例如进入下一阶段，要检查规定的产物是否存在、执行结果是否满足要求、推进方向是否合法。子 Agent 报告结束后，系统还会单独核对业务结果。

工具也按角色和阶段装配。实现者获得项目读写和受控执行工具，探索者获得程序操作工具；调度员主要组织工作。执行过程由轮次预算、超时和看门狗约束，委派心跳反馈当前进展，检查点保存已有阶段结论，供续跑使用。

### 3. Harness 与真实程序执行

第三个技术是 Harness，也就是围绕模型构建的执行、约束和反馈机制。

Agent 可以在项目范围内读写文件、安装声明的依赖、执行 Python 脚本，并获得退出码、输出和错误反馈。平台统一项目虚拟环境解释器，避免依赖装在一个环境，启动时却用了另一个环境。

桌面产物默认采用 Python 业务逻辑，加 pywebview 和 WebView2 渲染本地界面。驱动通过逻辑调用和 DOM 操作两种通道测试程序：既能调用业务方法，也能输入内容、点击按钮，再读取界面与磁盘状态。

这样，开发形成了“实现、执行、观察、修复、再执行”的循环。例如保存功能要检查按钮反馈、实际文件变化和重启后的记录。错误反馈会带回具体失败场景、输出及相关证据，让修复有明确目标。

### 4. 需求与测试证据的映射

第四个技术是把验收做成可检查的协议。

长期型用契约文件声明入口、执行方式和测试场景。每个场景关联需求 ID，平台根据实际执行结果聚合核心需求的覆盖和通过情况，同时核对入口、安全检查和启动证据。探索测试则补充真实操作中的问题发现，形成修复记录。

验收分为标准和严格两种策略。标准模式保留业务执行及核心检查，把静态疑点作为诊断；严格模式再做静态反空和故障种子检查。这个分级用于控制误报和额外验证成本，让检查强度与任务需要相匹配。

点选纠错也进入这条证据链：组件定位、选区和用户意见一起形成修改任务。纠错预览使用隔离实例和数据副本，修改后再查看新结果，便于把用户指出的问题与实际修复对应起来。

## 四、Agent 自主测试 SOP（约 2 分钟）

在这些机制之上，我们还建立了一套 Agent 自主测试 SOP，用于研发阶段的独立测试。

系统内部有验证和探索角色；独立测试 Agent 则按 SOP 模拟用户，驾驶 Bloma 完成从输入需求到交付的整个过程，并检查最终软件。

首先，它核对测试对象：源码版本、构建、模型渠道、项目 ID 和数据目录。测试使用隔离环境与业务数据，固定任务目标，区分新建任务和续跑任务。

然后，它通过驾驶脚本连接真实界面，发送普通用户需求，处理澄清、需求确认、草图和成品过目。明确的需求保持原范围；确认节点需要结合当前产物和问题记录作出选择。

测试期间，它持续监控日志、子会话和界面状态，区分模型处理、等待确认、执行错误和连接问题。同时沿途审阅原始需求、PRD、草图、源码、自测及交付说明，核对这些内容是否一致。

产物完成后，再做独立的业务操作。例如记账工具，要实际输入并保存记录，检查界面与磁盘都发生预期变化；输入负数后检查提示和数据不变；导出后查看内容；再用同一隔离数据重启程序，检查记录是否保留。

遇到失败，测试 Agent 保存复现步骤、退出码、截图、日志和文件变化，定位到具体层次，再反馈修复。修复后重新执行相关场景，保留首次失败和最终通过两份记录。回炉有次数与时间限制，避免无进展地反复续跑。

最后核对目标项目的持久化终态、实际测试结果和证据，关闭测试实例，生成报告。报告把需求、真实操作、结果和修复过程连起来，使每次自主测试都能复现、追踪和比较。

## 五、指标和近期推进（约 1 分钟）

指标主要看四类：效率、质量、资源和交互。效率看从统一起点到独立验收通过的 Time-to-MVP；质量看固定任务的闭环成功率和需求通过覆盖；资源统计父子会话及重试的总 token；交互看澄清、修改和重复解释次数，并结合用户反馈。

技术诊断还记录阶段尝试次数、失败分类和耗时长尾。这些数据与自主测试报告关联，帮助分析成本主要花在需求澄清、代码修复、验收还是环境问题上。

最近的推进主要是补齐执行工具和环境、完善附件及会话可靠性、修正验收误报与预算失配，并把界面整理为白色通透画室。当前链路已经通过测验，下一步重点是在统一条件下积累任务数据，量化这些机制的实际收益。
