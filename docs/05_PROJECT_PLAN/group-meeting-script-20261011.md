## 一、当前进展（约 40 秒）

老师、同学们好。今天我主要汇报 Bloma 的关键技术、自主测试方式，以及实际测试中的成本问题。

Bloma 面向有使用需求、但缺少开发经验的人，通过自然语言和参考材料驱动软件开发。目前需求澄清、界面确认、实现、测试、修复和交付的链路已经跑通。

这段时间整理出了十一个有名称的已交付案例，包括贪吃蛇、扫雷、教务管理、AI 聊天、批量文件改名、喝水记录、番茄钟、两类记账任务和工艺推演器等。下面结合这些案例，介绍系统怎样工作，以及成本主要出现在哪里。

## 二、整体流程（约 30 秒）

用户看到的是五步：想法、需求、界面、制作、试用与交付。向导澄清并形成需求文档，用户确认需求和草图后进入制作，发现问题则带着具体反馈修复、复验。

快速型减少工程阶段，尽快形成可用工具；长期型经过架构、骨架、实现和验证，并增加成品过目节点。这两种路径都由同一套编排和执行机制支撑。

## 三、关键技术及测试结果（约 3 分钟）

### 1. 需求规约与产品形状

第一个技术是把自然语言变成可传递、可验证的需求。

比如“金额不能是负数”，会具体化为：输入负数并保存时，界面提示错误，非法记录不落盘，已有数据不变。需求中保留功能、边界、优先级和行为断言；使用附件时，记录材料 ID、哈希和来源范围，后续角色使用同一份已确认需求。

我们还用 ProductShape 描述产品的主循环、数据来源和任务策略。番茄钟需要开始、暂停、恢复和归零；批量改名则需要预览、执行进度和部分失败处理。不同形状对应不同状态和测试场景。

实际测试中，番茄钟的十八项逻辑断言通过；批量改名的十五个驱动场景通过，其中包括预览不改变文件、规则校验、执行进度和部分失败后继续处理。这里能看到需求怎样落到具体程序行为。

### 2. 阶段状态机与多 Agent 委派

第二个技术是用阶段状态机组织多 Agent。

阶段表定义目标、产物、检查条件和合法下一阶段。编排器把工作委派给架构、实现、研究或验证角色，每个子会话都有自己的任务、上下文和执行记录。模型选择阶段内的行动，平台核对实际产物和执行结果后推进。

工具按角色和阶段装配，轮次预算、超时和看门狗控制执行范围，心跳反馈进展，检查点保存已有结论。这样可以追踪任务卡在哪个阶段、哪个子会话，以及卡住的原因。

最新工艺推演器的一次完整运行就有十九个会话和七百六十七次工具调用，包含委派、读取、代码执行和真实程序探索。这也说明编排有实际工作量，需要把协调成本计入评价。

### 3. Harness 与真实执行反馈

第三个技术是 Harness，也就是模型外围的执行、约束和反馈机制。

Agent 可以在项目范围内读写文件、安装依赖、执行脚本，并获得退出码、输出和错误信息。平台统一项目虚拟环境。桌面产物默认采用 Python 业务逻辑与 pywebview、WebView2 界面，驱动可以调用逻辑，也可以输入、点击和读取 DOM，再核对磁盘数据。

工艺推演器中，逻辑层已经保存了轮次，界面却仍显示空列表。探索 Agent 通过真实操作和接口读回，定位到返回结构与前端读取字段不一致。修复后，生成、改参、回溯、切换示例四项 GUI 回归通过，最终十四个驱动场景全部通过。这体现了发现、定位、修复和复验的闭环。

### 4. 验收协议与证据分层

第四个技术是把需求与测试证据关联起来。长期型用契约声明入口和场景，每个场景对应需求 ID，再根据实际结果聚合覆盖情况。当前默认标准验收保留业务执行与核心检查；严格策略再增加静态反空和故障种子，控制检查强度和误报成本。

不同能力分别验证。例如教务管理的驱动报告是十五项通过；AI 聊天是十项通过，并且有一次成功的真实模型渠道验证。逻辑断言、GUI 操作和真实服务调用各有对应证据，报告中保留它们的具体范围。

## 四、Agent 自主测试 SOP（约 1 分 30 秒）

研发阶段，独立测试 Agent 按 SOP 模拟用户，驾驶整个平台并验收生成的软件。

首先固定源码和构建版本、项目 ID、模型渠道与隔离数据目录；然后通过驾驶脚本发送普通用户需求，处理澄清、需求、草图和成品过目。过程中持续监控日志与子会话，并沿途核对原需求、PRD、草图、源码和测试结果。

产物交付后做独立业务操作。附件币种账本就完成了六项 WebView2 检查：真实启动、显示两条附件样例、表单保存改变界面与磁盘、负数拒绝且数据不变、CSV 保留币种字段、重启后新增记录仍在。

遇到失败，测试 Agent 保存复现步骤、截图、退出码和文件差分，定位问题并反馈修复，再重新执行相关场景。最后核对项目终态和实际结果，关闭测试实例，生成报告。

这套 SOP 还强调保留整个时间线。附件账本最终一次续跑用了约一百七十六秒，但从创建到首次交付约三十二分钟，中间有失败、环境与预算调整。因此不能只用最后一次成功运行的时间代表整个开发成本。

## 五、实际耗时与 token 成本（约 2 分 30 秒）

成本方面，目前先看耗时、轮次和 token。下面的耗时是已记录开发阶段的累计时间；token 是阶段主会话的输入、输出记录，不包含未完整落盘的所有子 Agent 用量，因此它们用于描述当前成本数量级。

小任务中，贪吃蛇累计约两分四十七秒，二十个主轮次，二点二六万 token；扫雷约一分二十五秒，十二轮，一点七万 token。相对复杂的长期型中，批量改名约二十四分二十秒，一百六十九轮，三十点二四万 token；最新工艺推演器约三十九分五十七秒，一百六十四轮，四十七点七六万 token。

把这十一个已交付案例合起来，记录到一千零一十个主轮次，输入与输出合计约二百零三点四八万 token。快速型六个案例的中位数约二点六八万，长期型五个案例约三十二点五八万。这些任务的复杂度和版本不同，数据说明当前样例的成本差异，还不能把差异全部归因于模式。

一个明显现象是，输入 token 占百分之八十二点七，这个比例指用量，不是账单金额。输入包含需求、历史、工具结果和反馈，所以成本优化需要关注上下文传递、检索和重复续跑。后面会进一步分析哪些读取和协调是必要的，哪些是重复开销。

另一个问题是未交付尝试也会消耗大量资源。历史中记录用量最高的六个阻塞项目，主会话输入、输出合计约二百二十三点七八万 token。因此成本统计必须保留失败和阻塞过程，才能看到得到一个成功结果之前付出了多少资源。

验收本身也有可观测成本。旧工艺运行五次验收退回，累计约十七分七秒、二十二点三万主会话 token；新运行一次验收通过，约七分二十三秒、七万 token。但新旧需求和实现不同，而且全阶段时间约从三十五分钟变为四十分钟，所以这组结果用于定位验收返工成本，不能直接当作总体提速的结论。

后续指标会把完整任务耗时、闭环成功率、需求覆盖、总资源消耗和交互次数关联起来，同时补齐子会话及辅助调用用量，让成本统计更完整。

## 六、近期推进与下一步（约 20 秒）

最近主要补齐了执行工具和环境、附件与会话可靠性，修正验收误报和预算失配，并完成白色通透画室的界面整改。当前链路已通过测验，下一步重点是用固定任务和统一口径分析成功、失败与返工成本，再验证哪些机制能够降低用户和系统的负担。
