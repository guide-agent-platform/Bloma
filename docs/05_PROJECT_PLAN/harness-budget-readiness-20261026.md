## 修复

物理请求发出前，按当前责任上界计算剩余可用的输出长度。只有原请求因预留不足无法准入、且保留至少原输出上限的一半和最小实用长度时，才降低本次 max_tokens。显式 thinking 预算也必须满足。输入继续按整上下文预留，不用字符估算冒充硬保证，不依赖缓存命中猜测。

这不是取消保护或减少已发生费用。降低后的真实请求体依次经过原请求守卫、原子金额预留和传输，回执仍按真实 usage 结算。并发时只读计算不能代替原子准入；旧预留和失败责任不释放。新请求记录实际输入、输出上限，便于追溯。流式请求和非流式资格探测使用同一逻辑，无预算策略时不改原始请求。

这项修复解决“输出上限略高导致整次请求被拒绝”的边界，尚未解决所有整输入窗口预留过大的情况。官方文档说明字符比例和离线 token 用量存在模型差异，实际 usage 为准，因此当前没有用未经确认的估算器削弱硬保证。来源：[DeepSeek token 用量](https://api-docs.deepseek.com/quick_start/token_usage/)、[兼容接口说明](https://api-docs.deepseek.com/guides/anthropic_api/)。

inspect_app 返回一个只读的 verification_readiness：区分目标未确认、规则缺失、规则过期/不可读及规则已登记，并给出下一步工具。它不增加审批、阶段或模型调用，不生成规则、不改变预期、不输出业务 PASS。规则登记后及时运行 verify_app，已有规则的免费宿主检查继续沿既有通路执行。
