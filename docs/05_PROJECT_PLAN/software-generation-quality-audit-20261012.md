# 软件生成质量核查：记账、文件、工艺

核查日期：2026-10-12；平台基线 `1d2b2c3`。本批核查已有产物，没有重新生成、调用付费模型、下载模型或采集麦克风。原产物只读；执行均在隔离源码副本与新测试数据上。

## 结论

首要抓手是**需求、验收与测试的语义关联**。现有代码已经能产生可用业务，但“编号相同、测试通过”不能保证“这个编号代表的功能已经实现”。工艺项目存在明确反例：F-004 是可选真实模型增强，验收文字和驱动却把 F-004 当参数编辑，正式报告将该项记为 passed；真实增强分支没有发送请求。

另有明确用户功能缺优先级而被兼容规则读作 P2、实施任务允许仅做 mock、架构文档与代码布局脱节，以及文件状态边界遗漏。不能把这些统一归为模型能力不足。

## 已确认问题

### GQ-01：需求 ID 语义错位，测试覆盖可能证明另一个功能（优先修）

工艺当前 PRD 的 requirements[F-004] 为“可选填入模型 Key，用大模型增强冷门材料组合的方案”，但 acceptance[F-004] 写“参数可点改、非法值保留原值”，contract.scenarios 将“参数点改-非法值拦截保留原值” covers 到 F-004，driver-report.acceptance_coverage[F-004].passed=true。

四份已有确认快照也包含该错位；不是本次审计造成。F-007 的需求为图纸、同号 acceptance 却为换材料；F-012 有需求且为 P0，却没有对应 acceptance 条目。requirements 与 acceptance 不只是描述风格不同，而是功能指代不同。

当前 `prd-store.ts` 读取仍返回 requirements/acceptance 原关联，只修正文的优先级标记；阶段需求契约仍会读取同号 acceptance。这说明同类不一致没有被读写边界消解。旧运行实际 system 全文没有保存，不能仅用现行源码断定全部历史提示词；本批有实际任务与输出证据。

归因：需求结构化/版本同步/测试语义绑定。改进方向：已确认 ID 不重新分配；验收断言跟随稳定需求对象；确认内容与工程契约绑定语义版本；覆盖关联漂移时待验，不能把错号 PASS 聚合成完整实现。

### GQ-02：明确用户功能缺优先级，被默认放到 P2（验收保证弱化）

`requirementPriority` 缺省 F-001=P0，其余=P2，为历史兼容设计。三案分别有 3、5、6 条未声明优先级：记账新增/列表/留存，文件输入/确认执行/撤销等都在其中。核心门只强制 P0 的场景证据。

这不等于这些功能都没有实现：记账实际通过，本次文件宿主专用反例也补了部分保护。但作为通用生成验收策略，原话功能可能没有强制验证；主题锚点 F-001 的长原话只要被一个场景 covers，也不能证明原话内所有效果。

归因：需求元数据/必做范围与优先级混用。改进方向：新需求明确 priority 与必做/可延期状态，未填不静默成为可忽略项；历史数据保留旧状态，重新运行时呈现缺口，不批量改写过去交付。

### GQ-03：只做 mock 的实施出口，与真实能力承诺不一致

工艺 `Logic.enhance` 的真实分支直接返回 network_error，没有 HTTP 请求代码。隔离探针设置非空测试 Key、指定 real 路径，观察到零网络尝试；mock 路径能返回成功。该探针不验证真实 Key 有效性，也没有实际外网请求。

联调子会话 `99792c85...` 初始任务又明确允许“若本版仅实现 mock provider，则注明 mock 模式与真实端点待用户自填”。因此模型选择 mock-only 有任务书原因；这不能作为完整真实增强的实现。DELIVERY 虽写明只有 mock，却也将后续使用描述成填 Key/端点即可启用；界面直接承诺填 Key 可以补充冷门组合，实际没有相应调用分支。

归因：任务书完成出口/能力声明/实现与验证两轴未分清。改进方向：not_implemented、implemented_unverified、partial 分开；未实现功能明确不可用，不伪装成认证/网络失败；mock 只覆盖它的断言范围，独立本地 HTTP 替身可先验证实际客户端路径，不消耗模型额度。

### GQ-04：旧预览与当前输入未绑定，生成自测漏掉关键反例

文件 Logic.execute_rename 信任调用方传入的 plan，未绑定当前目录/前缀/纯文件名。四个固定反例均有真实文件变化，包括修改测试目录外的自有哨兵。前端非法前缀提示后保留旧确认资格，原 GUI 自测绿不代表这个乱序操作正确。

归因：状态契约与测试充分性。现有平台 file_plan_guard 是局部防线；还应把预览失效、异步响应代次、执行前校验、执行结果与撤销作为同一状态契约，并验证生成代码确实消费组件。

### GQ-05：异常回滚恢复到了新名字

进度回调在第一阶段后抛异常时，rollback 把临时文件改为目标新名，而不是原名。隔离实测抛出异常后留下 `done-a.txt` 与 `b.txt`；这与代码自己的“异常回滚、不留半截状态”说明不符。

仅在第二份隔离副本修正 rollback 到原名、且原名未被占用时恢复：同一反例消失，正常两文件改名/撤销仍保持原字节。没有修改原产物，也没有宣称该回调异常在当前 GUI 可触发；它是后端异常路径证据。

归因：事务/状态恢复原语与失败注入。方向：复用经过反例验证的文件操作原语；进度通知失败与业务提交分开，失败恢复检查名称及内容，而不只看异常被捕获。

### GQ-06：模块规划与最终结构没有闭环

工艺架构文档规划 app.py 入口、core/*、bridge/api.py、storage/db.py 的 SQLite 分层；最终源码是 app.py 1517 行 + record_store.py，使用 JSON。两个内置方案构造函数合计 485 行，Logic 333 行，Api 144 行。

当前平台任务书仍要求业务/持久化集中在 app.py 的 Logic，存在结构诱导因素。代码可运行不意味着内部架构规划被遵从；但存储技术变化本身不等于违反用户的本地留存目标，独立业务留存实测通过。不能仅凭行数判软件坏，也不能仅凭架构文档存在判架构实现了。

归因：骨架/实现任务书/架构消费。方向：允许按职责拆分，保持 app 的兼容导出与正常启动；冻结真实采用的接口和存储策略；轻量任务允许简单布局，不设机械行数门。

### GQ-07：已有正确业务没有正确注册成宿主证据

记账 CORE_CHECK.json 登记了 GUI 场景，但 command 指向明确不启动 GUI 的 core_check.py，未登记已有 test_ui.py 为 gui_command。独立 GUI 业务通过，正式门却拿不到对应回读。这是证据装配缺口，不应把它算成记账业务失败。

方向：运行工具输出可追溯的场景/入口/版本清单，生成证据声明时复用真实已执行入口，避免手工重复填错；保留核心真实业务要求，不能为解决注册错误而去掉 GUI 检查。

## 独立测试器的缺陷与修正

文件首轮三次失败中两次被 harness 的路径比较抢先中止。详细复验确认：Path.resolve 在并发文件操作时返回 `\\?\C:\...` 表示，和普通盘符路径直接比较导致误报。该路径实际仍在自有测试目录内，不是越界证据。

修正只归一化 Windows 盘符/UNC 命名空间，再做解析后的包含关系检查；仍拒绝真实 `../outside`。两项边界单测通过。保留初始 JSON、详细 JSON，最后三轮均因原名变为 done-* 而失败；另四个独立后端反例证明真实越界风险。没有通过降低期待使产物转绿。

## 下一批建议

1. **先修需求契约一致性**：确认对象的稳定 ID、验收关联及版本；新需求的必做状态/优先级；禁止错号覆盖。
2. **再修实现完成度判定**：区分功能实现与测试执行，mock-only/未实现不能报整体功能通过；生成任务书的完成出口与确认目标一致。
3. **再做垂直业务链与组件消费**：接口统一、成功/失败/取消/乱序状态、预览与数据保护原语；先跑通一条 UI→业务→存储→UI 链后扩展。
4. **随后对齐产物架构**：拆职责、固定真实接口与采用策略，保留现有启动/驱动兼容面。

以上是基于已有产物的工程抓手；尚无修复后重新生成的可比样本，不给生成质量提升百分比。旧工艺业务的 14/14、映射 12/12 只能按实际场景范围解释，不能再被转述成“12 个功能全部完整实现”。
