> 项目：向导 Agent 多智能体协同开发平台

> 版本：v1.2 | 日期：2026-07-25 | 状态：已确认

## 1. 目的与适用范围

本规范定义测试文件、测试用例、GWT 场景、缺陷和测试报告之间的对应方式，目标是：

- 按功能快速定位问题，而不是按“通过/失败”移动测试文件。
- 详细测试步骤只维护一次，报告通过稳定 ID 引用测试。
- 区分产品缺陷、测试代码缺陷、环境问题、未实现能力和不稳定测试。
- 保证测试可重复、可隔离，不污染真实用户数据。
- 让 Pull Request、Sprint 验收和发布门禁采用同一套结果口径。

本规范适用于单元、集成、安全、E2E、GWT 和 Sprint 独立验收测试。

规范中的“必须”表示合并门禁要求；“建议”表示新代码应遵守、旧代码可逐步迁移。

---

## 2. 分类原则

测试采用三个维度分类：

1. **功能域**：说明测试的是哪个业务或工程能力。
2. **测试层级**：说明测试覆盖单模块、跨模块还是完整用户流程。
3. **执行结果**：说明本次运行是通过、产品缺陷还是环境问题。

其中：

- 功能域和测试层级属于测试的稳定属性，应体现在文件名、测试 ID 或目录中。
- 执行结果会随代码变化，只能出现在测试运行结果和报告中。
- 禁止建立 `passing/`、`failing/`、`passed/`、`failed/` 等按结果划分的测试目录。
- 禁止为了让流水线变绿，把当前 Sprint 的失败门禁移动到不执行的目录。

## 3. 功能域编码

测试 ID 和报告统一使用以下功能域编码：

| 编码 | 功能域 | 典型内容 |
|---|---|---|
| `PROJECT` | 项目与模式 | 项目创建、两道门、模式升级 |
| `AGENT` | Agent 会话 | SDK env、流式事件、取消、并发守卫 |
| `IPC` | IPC 边界 | channel 常量、handler、preload 白名单、`ApiResult` |
| `PERM` | 权限 | `pendingRequests`、允许/拒绝、会话隔离 |
| `STORE` | Local-First 存储 | JSON、JSONL、目录、临时 `PROMA_HOME` |
| `SECRET` | 密钥安全 | `safeStorage`、API Key、日志脱敏 |
| `SANDBOX` | 沙箱预览 | 启停、端口、目录边界、错误捕获 |
| `SKETCH` | 验证草图 | 澄清、生成、预览确认 |
| `CORRECT` | 点选纠错 | 元素上下文、用户说明、重新生成 |
| `SNAPSHOT` | 快照与回滚 | 创建、健康状态、事务回滚 |
| `DOCUMENT` | 文档同步 | PRD、PlantUML、GWT、检查点更新 |
| `JUDGE` | 测试与裁判门禁 | GWT、硬约束、退回、熔断 |
| `ANALYTICS` | 研究数据 | 埋点、脱敏、导出、隐私边界 |
| `UI` | Renderer 交互 | Jotai 状态、全局监听器、用户文案 |

新增功能域时，必须先更新本表，禁止同一能力出现多个近义编码。

## 4. 测试 ID 规则

### 4.1 格式

需要追踪的测试使用以下格式：

```text
S<阶段>-<功能域>-<三位序号>
```

示例：

```text
S0-IPC-004
S0-AGENT-003
S1-SKETCH-001
S3-ANALYTICS-002
```

规则：

- `S0`、`S1` 等表示首次引入该测试的 Sprint，不随以后执行阶段变化。
- 功能域必须来自第 3 节编码表。
- 序号在同一 Sprint 和功能域内递增，已使用的 ID 不得分配给其他行为。
- 测试重命名或移动文件时保留原 ID。
- 测试永久删除时，在变更记录或 PR 中说明原因；禁止静默复用 ID。

### 4.2 哪些测试必须有 ID

| 测试类型 | 是否必须有 ID |
|---|:---:|
| 纯函数、内部实现细节的单元测试 | 可选 |
| IPC、存储、权限等跨模块集成测试 | 必须 |
| 安全与隐私测试 | 必须 |
| Sprint 独立验收测试 | 必须 |
| E2E 和 GWT 场景 | 必须 |
| 已关联产品缺陷的回归测试 | 必须 |

## 5. 文件与用例命名

现有仓库保留按测试层级组织的目录，不要求一次性重构：

```text
tests/
├── unit/
├── integration/
├── regression/
│   ├── sprint0/
│   └── sprint1/
├── acceptance/
│   ├── sprint0/
│   ├── sprint1/
│   └── support/
├── security/
└── e2e/
```

每个测试文件必须聚焦一个功能域或一个紧密相关的边界：

```text
tests/unit/project-service.test.ts
tests/integration/local-first.test.ts
tests/security/api-key-boundary.test.ts
tests/regression/sprint1/mode-workspace-regression.test.tsx
tests/acceptance/sprint0/ipc-contract.test.ts
tests/e2e/sprint1/sketch-workflow.e2e.ts
```

禁止使用以下低信息量文件名：

```text
test1.test.ts
misc.test.ts
fix.test.ts
new-tests.test.ts
```

测试标题应描述“条件下应发生的可观察行为”，不要只写函数名：

```ts
it('[S0-IPC-004] 非法项目模式应返回失败的 ApiResult', async () => {
  // ...
})
```

不推荐：

```ts
it('test validateProjectCreate', () => {
  // ...
})
```

## 6. 单条测试的编写要求

每条测试必须满足以下要求：

1. **单一行为**：一条测试验证一个主要行为；多个断言可以共同证明该行为。
2. **可观察结果**：优先断言公开返回值、事件、文件或 UI 状态，不绑定无关内部实现。
3. **独立运行**：不能依赖其他测试的执行顺序或残留数据。
4. **确定性**：禁止依赖真实时间、随机端口、真实网络和不可控模型输出；应使用 fake timers、fixture 或 mock。
5. **完整清理**：测试结束后恢复环境变量、监听器、临时文件、进程和端口。
6. **失败可诊断**：断言应能直接说明预期与实际差异，避免只返回 `false`。
7. **不泄密**：fixture、快照、日志和失败输出不得包含真实 API Key 或个人数据。
8. **不降低标准**：发现产品缺陷时修复实现，不得先放宽断言让测试通过。

推荐使用 Arrange-Act-Assert 结构；关键业务验收使用 Given-When-Then：

```ts
it('[S0-STORE-002] 会话事件应写入临时 PROMA_HOME', () => {
  // Arrange: 创建临时目录和会话
  // Act: 追加会话事件
  // Assert: JSONL 位于临时 PROMA_HOME，真实用户目录未被访问
})
```

## 7. 环境与 Mock 要求

### 7.1 文件系统

- 所有会写文件的测试必须使用测试专属临时 `PROMA_HOME`。
- 禁止写入真实 `~/.proma/`、桌面、下载目录或用户项目目录。
- setup 必须在被测模块首次读取路径前设置 `PROMA_HOME`。
- teardown 必须恢复原环境变量并清理临时目录。恢复时原值可能是 `undefined`，直接赋值会被 Node 转成字符串 `"undefined"`（后续用例即以相对路径写到 `./undefined/`），因此须 `delete` 而非赋值；`tests/support/proma-home-guard.ts`（全局 setupFile）已做兜底归位。
- 路径工具中「文件路径」getter 不建目录（`getProjectEventsPath`/`getAnalyticsPath`），父目录由 `json-store` 写入时自建；只有「目录」getter 才 `ensureDir`。新增读路径勿引入 mkdir 副作用。

### 7.2 Agent 与模型

- CI 默认使用确定性的 Agent SDK mock。
- mock 至少覆盖：正常完成、部分输出后失败、权限请求、取消、超时和并发请求。
- 真实模型调用只能用于明确标记的本地或 nightly smoke，不作为普通单元测试依赖。

### 7.3 Electron 与安全存储

- 单元和集成测试可 mock Electron API，但必须验证 Renderer 不接触 Node.js 和明文密钥。
- `safeStorage` mock 必须同时覆盖加密、解密和不可用状态。
- Electron 真实启动由单独 smoke 或 E2E 命令执行。

### 7.4 时间与重试

- 5 秒、10 秒、60 秒、120 秒等待策略使用 fake timers 验证。
- 禁止用任意 `sleep` 掩盖竞态条件。
- 不稳定测试不能通过自动重跑被长期隐藏。

## 8. 测试结果分类

报告使用以下结果分类，测试文件位置不随结果变化：

| 状态 | 含义 | 处理要求 |
|---|---|---|
| `PASS` | 行为符合要求 | 自动统计，无需逐条人工解释 |
| `FAIL_PRODUCT` | 产品实现不符合已确认要求 | 创建或关联缺陷，保留失败断言 |
| `FAIL_TEST` | 测试代码、fixture 或断言错误 | 修复测试后重新执行，不能登记为产品缺陷 |
| `FAIL_ENV` | CI、权限、依赖、端口或环境配置问题 | 记录环境证据，修复环境后重跑 |
| `TODO` | 行为已规划但尚未进入当前实现范围 | 使用 `it.todo()`，不得计为已验证 |
| `SKIP_BLOCKED` | 被明确外部条件阻塞 | 使用 `it.skip()`，必须关联问题和解除条件 |
| `FLAKY` | 同一代码和环境下结果不稳定 | 立即登记并限期修复，不得作为通过项统计 |

禁止使用“暂时失败”作为模糊分类。必须判断是产品、测试还是环境问题。

## 9. 已知失败与缺陷管理

当前 Sprint 的验收门禁发现缺陷时：

1. 保留原测试和失败断言。
2. 为测试分配稳定 ID。
3. 在缺陷系统或 Sprint 待办中建立缺陷 ID。
4. 测试报告记录 `测试 ID -> 缺陷 ID`，不复制完整测试步骤。
5. 修复后由同一测试证明回归通过。

示例：

```text
S0-IPC-004 -> BUG-S0-001
S0-AGENT-003 -> BUG-S0-002
```

以下处理方式被禁止：

- 注释掉失败测试。
- 删除断言或把严格断言改为宽松断言。
- 把测试移动到默认不执行的目录。
- 使用 `skip` 隐藏当前 Sprint 必须修复的产品缺陷。
- 只在报告中写缺陷，但没有可执行回归测试。

## 10. GWT、测试文件与报告的对应

只对关键用户流程、架构门禁和发布门禁建立 GWT 对应，不要求每条单元测试都有 Feature 场景。

GWT Feature 使用同一测试 ID 作为 tag：

```gherkin
@S0-IPC-004
Scenario: 非法项目模式返回统一错误结果
  Given 用户提交非法项目模式
  When Renderer 通过 IPC 创建项目
  Then 响应应为失败的 ApiResult
```

可执行测试使用同一 ID：

```ts
it('[S0-IPC-004] 非法项目模式应返回失败的 ApiResult', async () => {
  // ...
})
```

测试报告只引用 ID：

| 测试 ID | 功能域 | 结果 | 缺陷 |
|---|---|---|---|
| `S0-IPC-004` | IPC | `FAIL_PRODUCT` | `BUG-S0-001` |

详细步骤由 Feature 和测试文件维护，报告不得再次复制 Given/When/Then 或测试代码。

## 11. 测试报告要求

### 11.1 必须记录的运行信息

- 项目版本或 commit SHA。
- 分支名称。
- 执行时间和测试环境。
- 执行命令。
- 测试总数、通过数、失败数、跳过数和 TODO 数。
- 按功能域和测试层级汇总的结果。

### 11.2 必须提供测试摘要

每份测试报告必须在运行元数据之后、详细执行范围之前提供“测试摘要”。摘要用于让读者不展开失败日志也能判断当前阶段是否通过，禁止省略或只写“测试完成”。

摘要必须包含：

- 被测 Sprint、版本或功能范围。
- 总体结论：`PASS`、`FAIL_PRODUCT`、`FAIL_TEST` 或 `FAIL_ENV`；存在多类失败时全部列出。
- 通过数、产品失败数、测试失败数、环境失败数、跳过数和 TODO 数。
- 阻塞当前 Sprint、合并或发布的稳定测试 ID。
- 环境状态和仍需人工完成的测试范围。
- 一句话说明影响最大的未关闭问题；详细原因和证据留在失败项章节。

统计口径必须明确：

- 同一命令或同一完整测试范围可以汇总为一组数字。
- 不同时间、不同命令或补充定向测试必须分开列出，不得直接相加后伪装成同一轮全量结果。
- 重复执行同一测试时只统计最终有效结果，并保留必要的初始失败记录用于回归追踪。
- 只要当前范围存在未豁免的 `FAIL_PRODUCT`、`FAIL_TEST` 或 `FAIL_ENV`，摘要不得写成“通过”。

推荐格式：

```markdown
## 测试摘要

| 项目 | 结论 |
|---|---|
| Sprint 1 | `FAIL_PRODUCT`，当前不能完成 Sprint 验收 |
| 基线自动化 | 40 项 `PASS`、3 项 `FAIL_PRODUCT`、0 项 `FAIL_TEST` |
| 补充定向测试 | 1 项 `PASS`、1 项 `FAIL_PRODUCT`，与基线分开统计 |
| 当前阻塞 ID | `S1-STORE-001`、`S1-SKETCH-004` |
| 环境状态 | 类型和文档检查通过；正式构建存在文件占用 |
```

### 11.3 失败项必须记录

- 测试 ID 和测试标题。
- 结果分类：`FAIL_PRODUCT`、`FAIL_TEST` 或 `FAIL_ENV`。
- 一句话问题结论。
- 缺陷 ID、负责人和目标 Sprint；环境问题记录环境证据。
- 失败日志、截图或产物路径，不把大段日志直接复制进正文。

### 11.4 通过项如何记录

- 自动列出 ID、标题、结果和耗时即可。
- 详细章节中的人工汇总只写功能域统计，例如“IPC：6/7 通过”。
- 不需要为每条通过测试重复描述步骤和断言。

## 12. 测试命令边界

每条测试命令必须只运行其声明的测试层级，并加载对应 setup：

| 命令 | 应包含 | 不应包含 |
|---|---|---|
| `test:unit` | `tests/unit/**` | 集成、E2E、角色验收 |
| `test:integration` | `tests/integration/**` | 单元、E2E |
| `test:security` | `tests/security/**` | 普通单元测试 |
| `test:regression:sprint0` | Sprint 0 既有行为与缺陷回归 | Sprint 1、独立验收 |
| `test:regression:sprint1` | Sprint 1 既有行为与缺陷回归 | Sprint 0、独立验收 |
| `test:acceptance:sprint0` | Sprint 0 独立阶段验收 + 必要构建 | Sprint 1、普通单元测试 |
| `test:acceptance:sprint1` | Sprint 1 独立阶段验收 | Sprint 0、普通单元测试 |
| `test:e2e:sprint1` | Sprint 1 Playwright Electron 用户流程 | Vitest 验收和未来 Sprint |
| `test:e2e` | `tests/e2e/**` | 单元和静态扫描 |
| `test:all` | 依次调用各层命令 | 用一个无 include/setup 的通用 Vitest 命令混跑所有测试 |

任何依赖临时 `PROMA_HOME` 的命令必须加载相应 setup。若测试因为命令包含范围或 setup 错误而失败，应分类为 `FAIL_TEST` 或 `FAIL_ENV`，不能误报为产品缺陷。

## 13. 合并与发布门禁

### 13.1 Pull Request

- 新增或修改功能必须有相应测试。
- 测试必须在本地和 CI 中可重复执行。
- 不允许新增无问题记录的 `skip`、`todo` 或 flaky 测试。
- 新增 IPC、权限、存储和密钥能力必须有集成或安全测试 ID。
- PR 描述应列出执行过的命令和结果，不粘贴全部测试正文。

### 13.2 Sprint 关闭

- 当前 Sprint 的全部验收门禁必须为 `PASS`。
- `FAIL_PRODUCT` 必须修复，不能通过改成 `skip` 关闭 Sprint。
- `FAIL_TEST` 和 `FAIL_ENV` 必须先修复并重新执行，不能被统计为产品通过。
- `TODO` 只有在明确不属于当前 Sprint 范围时才允许存在。

### 13.3 发布

- GWT、E2E、安全、隐私和回滚门禁全部通过。
- 不存在未处理的 P0/P1 flaky 测试。
- 测试报告能够从测试 ID 追溯到 Feature、测试文件和缺陷。

## 14. Code Review 检查表

评审测试代码时至少检查：

- [ ] 文件和测试标题能识别功能域。
- [ ] 需要追踪的测试具有唯一稳定 ID。
- [ ] 一条测试只验证一个主要行为。
- [ ] 测试不依赖执行顺序、真实网络或真实用户目录。
- [ ] 临时环境、监听器、进程和文件得到清理。
- [ ] 断言验证公开行为而不是无关实现细节。
- [ ] mock 覆盖成功、失败和边界条件。
- [ ] 失败测试没有被注释、弱化或无理由跳过。
- [ ] GWT、可执行测试和报告使用同一 ID。
- [ ] 测试命令的 include 和 setup 范围正确。
- [ ] 测试报告在元数据之后提供摘要，并明确总体结论、统计口径和阻塞 ID。

## 15. 现有测试迁移要求

现有测试不要求一次性移动目录，按以下顺序渐进迁移：

1. 为 Sprint 0 的 19 项独立验收测试分配稳定 ID。
2. 将两个已知失败分别关联产品缺陷 ID。
3. 让 `test:unit` 只包含 `tests/unit/**`，避免误收角色验收测试。
4. 公共验收夹具统一放在 `tests/acceptance/support/`，并使用临时 `PROMA_HOME`。
5. 后续新增测试从提交时直接遵守本规范。
