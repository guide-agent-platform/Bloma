## §2 渠道管理（channel-manager）

### §2.1 渠道存储加载与迁移

### loadChannels — `main/channel-manager.ts:106`

- 输入：无（读 `~/.proma/bloma-channels.json`；缺失时读旧共享 `channels.json`）
- 副作用：**一次性迁移落盘**（`bloma-channels.json` 不存在即写迁移结果，文件存在即迁移完成标记）
- 返回值：`ChannelsConfig { version, channels }`

```text
loadChannels():
  path = getBlomaChannelsPath()
  if exists(path):  return readJsonFile(path, {version:1, channels:[]})
  # 迁移（2026-08-26 渠道存储独立化）：Bloma 曾与 Proma 共用 channels.json，
  # 但 Proma(v9) 写入会整体丢弃本项目 snake_case 条目 → 迁出独立文件
  legacy = readJsonFile(getChannelsPath(), {version:1, channels:[]})   # 只读旧文件，绝不回写
  migrated = { version:1, channels: legacy.channels.filter(isOursChannel) }
  writeJsonFile(path, migrated)          # 空迁移也落盘（=迁移完成标记）
  return migrated
```

### isOursChannel — `main/channel-manager.ts:137`

判定渠道条目归属本项目：要求 `provider_type` 与 `api_key` 都是 string（snake_case 契约）。与 Proma 共用的 `channels.json` 中 camelCase + base64 加密的条目视为外部渠道跳过。返回 `false` 即过滤。

- `saveChannels`（`channel-manager.ts:121`）— `writeJsonFile(getBlomaChannelsPath(), config)`；落盘单一入口。
- `redact`（`channel-manager.ts:125`）— `{...channel, api_key:'***'}`，出 IPC 的脱敏。
- `getChannelByIdRaw`（`channel-manager.ts:143`）— 取原始渠道（含密文），非本项目条目返回 undefined；仅供 main 内部。
- `getChannelById`（`channel-manager.ts:153`）— IPC 侧读，`redact` 后返回。
- `listChannels`（`channel-manager.ts:176`）— 全部本项目渠道，脱敏后返回。
- `listEnabledRawChannels`（`channel-manager.ts:184`）— 全部**启用**本项目渠道（未脱敏，含真实 api_key 密文），供 §3 运行时被动回退枚举备用渠道；密钥只在 main 解密，不经 IPC 外泄。

### buildSdkEnv — `main/channel-manager.ts:80`

- 输入：`apiKey`（已解密明文）、`baseUrl`、`model`、`providerType?`
- 副作用：无（纯构造环境对象）
- 返回值：SDK 子进程环境 `Record<string,string>`

```text
buildSdkEnv(apiKey, baseUrl, model, providerType?):
  env = {}
  for key in SDK_ENV_ALLOWLIST:                      # PATH/HOME/代理等白名单宿主环境
      if process.env[key] != undefined: env[key] = process.env[key]
  # Anthropic 协议 provider 的 base_url 规范化到协议根（SDK 内部会拼 /v1/messages）：
  # 修复 deepseek/minimax 等渠道 base_url + /v1/messages 拼错路径的问题
  effectiveBaseUrl = providerType ∈ ANTHROPIC_PROTOCOL_SET
                       ? normalizeAnthropicBaseUrlForSdk(baseUrl) : baseUrl
  env.ANTHROPIC_AUTH_TOKEN = apiKey
  env.ANTHROPIC_BASE_URL  = effectiveBaseUrl
  env.ANTHROPIC_MODEL     = model
  return env
```

> **要点**：`SDK_ENV_ALLOWLIST`（`channel-manager.ts:42`）是刻意白名单——避免宿主机历史 `ANTHROPIC_`/`CLAUDE_` 环境变量污染 Agent 渠道。`ANTHROPIC_PROTOCOL_SET`（`:68`）消费 shared 的 `ANTHROPIC_PROTOCOL_PROVIDERS`（`shared/types.ts:420`）单一真相源。

### §2.6 channel-test-error（错误归一化）

### classifyHttpStatus — `main/channel-test-error.ts:59`

- 输入：HTTP `status` + 可选 `bodyText`（仅消解 400/403/429 三个歧义状态）
- 副作用：无（纯函数）
- 返回值：`ChannelTestErrorType`

```text
classifyHttpStatus(status, bodyText=''):
  if status >= 500: return 'server'          # 5xx 全归服务端异常
  switch status:
    401 → 'auth'                             # 认证失败，无需文本
    402 → 'quota'
    403 → AUTH_TEXT.test(bodyText) ? 'auth' : 'permission'   # 403 歧义：正文含「invalid key/unauthorized」→ auth
    404 → 'not_found'
    408 → 'timeout'
    429 → QUOTA_TEXT.test(bodyText) ? 'quota' : 'rate_limit' # 429 歧义：正文含「insufficient quota/欠费」→ quota
    400 → AUTH_TEXT.test(bodyText) ? 'auth' : 'bad_request'  # 400 歧义：正文含认证类词 → auth
    405/409/413/415/422 → 'bad_request'
    default → 'unknown'
```

> **要点**：HTTP 语义是标准化的，分类以**状态码为主轴**，文本匹配只用于消解三个真正存在歧义的状态。`AUTH_TEXT`（`:35`）/`QUOTA_TEXT`（`:37`）含中英文特征词。`ERROR_LABELS`（`:21`）是各分类的用户可读提示（已带处置建议）。

- `extractErrorMessage`（`channel-test-error.ts:103`）— 从响应体取可读消息：兼容 OpenAI/Anthropic/Google 的 `{error:{message}}` 与顶层 `{message}`；非 JSON 原样返回。
- `summarizeDetail`（`channel-test-error.ts:126`）— 凭证脱敏（`SENSITIVE_PATTERNS`，`:46`）→ 压空白 → 截断 500 字（`MAX_DETAIL_LENGTH`）。
- `buildFailure`（`channel-test-error.ts:138`）— 组装 `{ok:false, message:标签+状态码+脱敏摘要, errorType, statusCode?, detail?}`。
- `readBoundedText`（`channel-test-error.ts:159`）— 流式读响应体到 16KiB 上限（`MAX_ERROR_BODY_BYTES`），防异常端点超大内容耗内存。
- `normalizeHttpResponse`（`channel-test-error.ts:211`）— 2xx → `{ok:true,'连接成功'}`；否则 `readBoundedText` → `classifyHttpStatus` → `extractErrorMessage` → `buildFailure`。
- `normalizeRequestError`（`channel-test-error.ts:225`）— 无 HTTP 响应异常归一化：AbortError/TimeoutError/`timeout` 特征 → timeout；`invalid url` 特征 → bad_request；否则 network（detail 聚合 error.cause 链）。

## §3 M5 类别路由与 M4 模型解析

**职责划分**（与 T9 正交）：
- `category-routing` 决定**哪个渠道**（主路由 `resolveRoutedChannelId` + 备用顺序 `getCategoryFallbackChannelIds`）；
- `model-resolution`（M4）在赢家渠道内决定**哪个模型**；
- `runtime-fallback`（§4）负责基础设施故障的跨渠道切换留痕（内容型失败不切）。

**参与路由的类别**：`ROUTABLE_CATEGORIES`（`category-routing.ts:29`）= `['sketch','mvp','guide','prd','judge','summary']`；`gwt` 走浏览器探针/静态启发式、从不解析 LLM 渠道，不在列。`CATEGORY_LABELS`（`:32`）为中文职责名。

### §3.1 路由表读写与缓存

- `loadRoutingConfig`（`category-routing.ts:45`）— 模块缓存 `routingCache`；无配置文件是正常态（空表直接生效，不落警告）；文件 version≠1 / 损坏 → `console.warn` + 回退空表。
- `loadCategoryRouting`（`category-routing.ts:69`）— 返回路由表副本。
- `saveCategoryRouting`（`category-routing.ts:74`）— `{version:1, routing}` 落盘并刷新缓存。

### resolveRoutedChannelId — `main/category-routing.ts:87`（主路由，§4.1 ②）

- 输入：`category`
- 副作用：悬空/非 Anthropic 协议时 `console.warn`（不静默）
- 返回值：`string | undefined`（渠道 id；未配置/各类回退均 undefined，由调用方落入全局兜底）

```text
resolveRoutedChannelId(category):
  entry = loadRoutingConfig()[category]
  if !entry?.channel_id: return undefined
  channel = getChannelByIdRaw(entry.channel_id)
  if !channel:
      console.warn('渠道已删除（悬空），回退全局默认渠道'); return undefined
  if !channel.enabled: return undefined          # 禁用不落警示——保留意图，重新启用自动恢复
  if !isAnthropicProtocolProvider(channel.provider_type):
      console.warn('非 Anthropic 协议，运行时无法走 /v1/messages，回退全局默认'); return undefined
  return channel.id
```

- `getCategoryFallbackChannelIds`（`category-routing.ts:110`）— 读 `fallback_channel_ids`，过滤「不存在/非本项目/禁用」条目（`getChannelByIdRaw` 已含 isOursChannel 校验）。

### §3.2 路由视图模型与保存校验

- `buildCategoryRoutingViews`（`category-routing.ts:127`）— 6 类职责视图：`effective` 三态——`routed`=命中路由、`auto`=全局默认（含禁用渠道生效期）、`dangling`=指向已删除渠道（保留原配置值供 UI 行内警示）；`model_name` 经 `resolveCategoryModel` 解析（失败 undefined）。
- `keepChannelReference`（`category-routing.ts:177`）— 保存时单引用剥离判定：非字符串/空 → 抛 `CATEGORY_ROUTING_INVALID`；渠道不存在 → 剥离 + warn；非 Anthropic 协议（含禁用）→ 剥离 + warn；禁用但 Anthropic 协议 → 保留（重启用自动恢复）。

## §4 T9 运行时被动渠道回退（runtime-fallback）—— 问题高发区

> **设计意图**：M4 类别解析是「主动链」（运行前一次性选好模型）；渠道瞬断（429/5xx/网络错误）或密钥损坏时，原行为是整次生成静默降级（引导落规则路由、草图落模板）。本模块补「被动链」——构建期切备用渠道而非直接降级；请求期首调基础设施故障且未流出正文时切备用重试一次。**内容型失败（截断/解析错）在引擎层，永远到不了这里的判定**；每次切换落 T2 决策日志 + 用户可见 `[channel-switch]` 系统行，绝不静默。

```mermaid
flowchart TD
    A[resolveChannelEnv<br/>runtime-fallback.ts:155] --> B{resolvePrimaryChannel}
    B -->|①显式 channel_id| C1[getChannelByIdRaw]
    B -->|②类别路由表| C2[resolveRoutedChannelId]
    B -->|③全局兜底| C3[getFirstEnabledChannel]
    C1/C2/C3 --> D{主渠道存在?}
    D -->|否| E[return unusableReason:'no_channel']
    D -->|是| F[tryBuildChannelEnv<br/>解密 + 类别解析 + supports_tools]
    F -->|ok| G[attachFallbackContext<br/>+ recordCategoryRoute 若 routed]
    F -->|failed: decrypt/model/tools| H{主渠道不可用}
    H --> I[pickBackupChannelEnv<br/>类别路由 fallback → channels.json 配置序]
    I -->|有备用| J[recordChannelSwitch<br/>决策日志 + [channel-switch] 系统行]
    J --> K[attachFallbackContext 备用]
    I -->|无备用| L[return unusableReason: 失败原因]
    G/K --> M[env 携带 BLOMA_FALLBACK_* 回退上下文]
    M --> N[请求期 queryWithRuntimeFallback<br/>orchestrator.ts:1059 消费]
```

### §4.1 回退上下文随 env 携带

- `attachFallbackContext`（`runtime-fallback.ts:54`）— 在 env 挂 `BLOMA_FALLBACK_CHANNEL_ID`/`BLOMA_FALLBACK_CATEGORY`（+可选 PROJECT_ID/SESSION_ID）四个保留键。
- `readFallbackContext`（`runtime-fallback.ts:62`）— 从 env 读回 `RuntimeFallbackContext { channelId, category, projectId?, sessionId? }`；缺 channelId 或 category → undefined。

> **要点**：引擎到 query 的入参链路深，显式透传需改动全部引擎接口；env 是 string record，上下文字段恰全是字符串，挂保留键是最小侵入载体。`anthropicMessagesQuery` 只读 `ANTHROPIC_*` 键，这些键不会进请求体。

### resolveChannelEnv — `main/runtime-fallback.ts:155`（构建期解析链核心）

- 输入：`{ channelId?, category, projectId?, sessionId?, requireTools? }`
- 副作用：命中路由落 `category_route` 决策日志；主渠道不可用切备用时落 `runtime_channel_switch` 决策日志 + 用户可见 `[channel-switch]` 系统行（均 30s 节流）
- 返回值：`ChannelEnvResolution { env?, channel?, modelName?, supportsTools?, unusableReason? }`

```text
resolveChannelEnv({channelId?, category, projectId?, sessionId?, requireTools?}):
  # ---- 主渠道选择（M5 §4.1 解析链）----
  primarySelection = resolvePrimaryChannel({channelId, category})
  primary = primarySelection.channel
  if !primary: return { unusableReason: 'no_channel' }       # 无任何渠道

  context = { channelId: primary.id, category, projectId, sessionId }

  # ---- 主渠道构建尝试 ----
  attempt = tryBuildChannelEnv(primary, category, requireTools)
  if attempt.status == 'ok':
      if primarySelection.routed and projectId and sessionId:
          recordCategoryRoute(...)                            # 路由命中落决策（静态配置非事件，不加系统行）
      return {
          env: attachFallbackContext(attempt.env, context),
          channel: primary, modelName: attempt.model, supportsTools: attempt.supportsTools,
      }

  # ---- 主渠道不可用：切第一个可用备用渠道（T9 构建期回退）----
  backup = pickBackupChannelEnv(context, requireTools)
  if backup:
      recordChannelSwitch({ context, reason: attempt.reason, to: backup })   # 决策日志 + [channel-switch] 系统行
      return {
          env: attachFallbackContext(backup.env, { ...context, channelId: backup.channel.id }),
          channel: backup.channel, modelName: backup.model, supportsTools: backup.supportsTools,
      }

  # ---- 无备用可用：如实返回原因，调用方维持既有降级语义 ----
  #   降级链：草图回模板 / MVP 抛错 / 引导回规则路由（调用方决定，本模块不代劳）
  return { unusableReason: attempt.reason }   # 'decrypt_failed' | 'model_not_found' | 'tools_unsupported'
```

> **`requireTools`（废旧管道方案 §4.2）**：调用方要求模型支持 tool use（agent loop 唯一运行时后 MVP 类别必传）时，`supports_tools === false` 的模型按「不可用」走备用链；备用也全不支持则如实返回 `tools_unsupported`，**绝不静默降级**。不传时行为与改造前完全一致。

### tryBuildChannelEnv — `main/runtime-fallback.ts:101`（单渠道构建尝试）

### pickBackupChannelEnv — `main/runtime-fallback.ts:218`（备用渠道枚举）

- 输入：`context { channelId, category }`、`requireTools?`
- 返回值：`BackupChannelEnv { channel, model, env, supportsTools } | undefined`

```text
pickBackupChannelEnv(context, requireTools?):
  fallbackOrder = getCategoryFallbackChannelIds(context.category)      # ① 类别路由的 fallback_channel_ids 顺序
  candidates = fallbackOrder.map(getChannelByIdRaw) + listEnabledRawChannels()  # ② channels.json 配置序
  seen = { context.channelId }                                         # 跳过主渠道，保序去重
  for channel in candidates:
      if !channel or channel.id ∈ seen: continue
      seen.add(channel.id)
      try:    apiKey = decryptApiKey(channel.api_key)   catch: continue  # 密钥损坏跳过
      try:    model = resolveCategoryModel(channel, category).model  catch: continue  # 无模型跳过
      supportsTools = readSupportsTools(channel, model)
      if requireTools == true and supportsTools == false: continue       # 同主渠道口径
      return { channel, model, env: buildSdkEnv(apiKey, channel.base_url, model, channel.provider_type),
               supportsTools }
  return undefined
```

> **要点**：备用顺序先按类别路由的 `fallback_channel_ids`（§4.4），未命中回退 `channels.json` 配置序；`getChannelByIdRaw` 已含 isOursChannel 校验、`getCategoryFallbackChannelIds` 已过滤禁用。

### §4.2 故障分类（只切基础设施故障）

- `isInfrastructureFailure`（`runtime-fallback.ts:260`）— HTTP `429/529/5xx/401/403` 或网络层错误信号 → true；用户取消/请求级失败（400 等）→ false。与 `orchestrator.shouldRetry` 口径一致但多覆盖「凭证级」故障——key 被吊销时同渠道重试无意义，切渠道才有出路。
- `isUserCancelledQuery`（`runtime-fallback.ts:270`）— `AbortError` 或消息含 `AGENT_CANCELLED` → true；用户主动停止不是故障，绝不切渠道重试。
- `extractErrorStatusCode`（`runtime-fallback.ts:280`）— 优先 `statusCode` 属性，其次消息里 3 位数字词边界匹配（`anthropicMessagesQuery` 抛 `SDK request failed with 500`）。
- `hasNetworkErrorSignal`（`runtime-fallback.ts:291`）— 消息或 cause 链里的 `ECONNRESET/ETIMEDOUT/ENOTFOUND/EAI_AGAIN/ECONNREFUSED/EPIPE/EHOSTUNREACH/ENETUNREACH/fetch failed` 正则。

### queryWithRuntimeFallback — `main/orchestrator.ts:1059`

- 副作用：首调基础设施故障切备用时经 `recordChannelSwitch` 落决策日志 + `[channel-switch]` 系统行

```text
queryWithRuntimeFallback(prompt, options):
  context = readFallbackContext(options.env)     # env 无回退上下文 → 纯透传
  emitted = false
  iterator = anthropicMessagesQuery(prompt, options)  # 原 query 流
  try:
    for next in iterator:
        if next.type == 'assistant': emitted = true   # 已流出正文标记
        yield next
  catch error:
    # 首调基础设施故障 + 尚未流出正文才切；内容型失败（引擎层）/用户取消/已流出正文 → 原样上抛
    if !context or emitted or isUserCancelledQuery(error) or !isInfrastructureFailure(error):
        throw error
    backup = pickBackupChannelEnv(context)
    if !backup: throw error                       # 无备用：保持原错误
    statusCode = extractErrorStatusCode(error)
    recordChannelSwitch({ context, reason: statusCode ? `http_${statusCode}` : 'network_error',
                          to: backup, statusCode })
    yield* anthropicMessagesQuery(prompt, {
        ...options,
        env: backup.env,
        # 备用渠道有自己的 max_tokens 上限（16384 主渠道对备用渠道可能 400）
        maxTokens: backup.channel.max_tokens ?? options.maxTokens,
    })
  finally:
    iterator.return()                             # 收尾 no-op 保护
```

> **要点**：`sdkQuery` 模块级默认即 `queryWithRuntimeFallback`（`orchestrator.ts:129`），所有引擎经 `sdkQuery` 发请求自动获得请求期回退。切换**绝不静默**，且已流出正文后不再切（重试会导致 delta 重复拼接）。

### circuitBreakRollback — `main/recovery-service.ts:245`

- 输入：`CircuitBreakInput { request_id, session_id, project_id, reason, publish }`
- 副作用：停沙箱→回滚快照→重启沙箱（经 `rollbackSnapshot`）、清零全部修复计数、收敛阶段、写用户消息 + 事件流、落 `circuit_rollback` 决策日志
- 返回值：`CircuitBreakResult { rolled_back, stage?, snapshot_id?, error? }`

```text
circuitBreakRollback({request_id, session_id, project_id, reason, publish}):
  project = findProject(project_id)
  healthy = latestHealthySnapshot(project_id)
  if !healthy: return { rolled_back: false }               # 无健康快照 → 交回让渡，不留半事务态

  # ---- 1. 回滚（最多重试 2 次）----
  lastError = undefined; rollback = undefined
  for attempt in 0..1 while !rollback:
      try:
          rollback = await rollbackSnapshot({
              request_id, project_id, snapshot_id: healthy.snapshot_id,
              reason: 'repair_fuse',          # 受 api-spec 枚举约束；完整语境在决策日志
          })   # rollbackSnapshot = guard 保护 + 停沙箱 + 恢复文件/文档 + 重启沙箱（platform-services）
      catch error: lastError = error

  # ---- 2. 回滚失败 → 如实告知，交回 blocked_for_user_decision 让渡 ----
  if !rollback:
      message = '自动修复多次都没有成功，回滚到上一个健康版本也没有成功。…可从时间轴手动选快照回滚，或告诉我重新生成一版。'
      appendAssistantMessage(session_id, message)
      publish('message_delta', { text: message })
      recordDecision({ type:'circuit_rollback', title:'熔断回滚失败（让渡）', why, detail })
      return { rolled_back: false, error: describeError(lastError) }

  # ---- 3. 回滚成功：按磁盘证据收敛阶段 + 清零全部修复计数 ----
  stage = convergeStageFromEvidence(evaluateDiskArtifact(project.root_path))
  updateProject(project_id, {
      current_stage: stage,
      runtime_repair_count: 0, test_repair_count: 0,
      security_repair_count: 0, judge_return_count: 0,     # 全部修复计数归零
      blocked_action: undefined,
  })

  # ---- 4. 收尾话术（按收敛阶段区分）+ 事件流 + 决策日志 ----
  message = stage=='ready'       ? '…已经自动回到之前的版本，内容都还在，没有丢失。…'
          : stage=='sketch_ready' ? '…当前回到的是草图版本，可以重新确认草图后再生成完整功能。'
          :                         '…但该版本没有留下可用产物。请重新描述你的想法，我们再来一次。'
  appendAssistantMessage(session_id, message)
  publish('rollback_done', { snapshot_id: rollback.current_snapshot_id, preview_url: rollback.preview_url })
  # rollback_done 先行（渲染端契约：用它回填预览地址，与旧让渡路径一致），再收敛阶段、发消息收尾
  publish('stage_changed', { stage })
  publish('message_delta', { text: message })
  publish('completed', { subtype: 'success' })
  recordDecision({ type:'circuit_rollback', title:'修复循环耗尽，熔断回滚', why, detail:{reason,snapshot_id,stage} })
  return { rolled_back: true, stage, snapshot_id: healthy.snapshot_id }
```

## §9 记忆蒸馏（memory-distiller）

**职责**：T4-L3 蒸馏层（兜底）——把确定性两层（L1 约束走门 / L2 全量扫描）装不下的**对话性记忆**（被否决方案/口头偏好/非功能诉求）蒸馏到 `documents/{pid}/memory.json`。**默认关闭**（`BLOMA_MEMORY_DISTILL=1` 才启用，main 进程环境变量非用户配置）。与背板重叠的三类（已确认功能/用户约束/关键决策）一律不存——冲突时以背板为准（OMO 作者教训：专用记忆系统极易冗余）。

## §10 需求归一化 / 增强 / 约束抽取

三条需求侧管线：**normalizer**（修改诉求并入需求清单前归一化）、**enricher**（澄清薄项加厚为行为契约）、**constraint-extractor**（约束的确定性提取，T4-L1/L2 主路）。共同原则：**LLM 判定 + 确定性守卫，失败一律回退不阻断生成链路**。

### §10.1 约束抽取（确定性，不依赖 LLM）

### extractConstraints — `main/constraint-extractor.ts:51`
