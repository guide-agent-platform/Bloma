## 当前装配顺序

调度员：共同核心验证说明 → 调度角色 → PRD需求与正文、体验契约 → 已确认UX路径与阅读要求 → 快速制作任务书（实验版替换单实现者措辞）及实验协议 → 阶段约束 → 推进协议、交付门清单 → 只读编排与委派工具纪律 → 验证证据复用/收口纪律 → 中文输出要求。起跑消息另外明确要求两名实现者并行。

执行者：桌面制作领域基底 → 中文汇报与实现/事务/GUI证据纪律 → 同一共同核心验证说明 → quick约束 → 同一完整需求上下文 → UX阅读要求 → implement职责与委派边界（不能再委派、不能直接向用户提问）→ 本次任务消息。任务消息还追加100轮预算及保留约四分之一轮数做验证收口的要求。续接时重放执行者自己的历史。

`loop-system`支持从隔离home的`prompts/loop-system.md`追加；本轮该文件不存在，没有制作自定义追加规则。隔离home只有`sketch-system.md`，它服务此前草图阶段。设置页单个提示词文件不代表制作阶段全部system。

## 已核实的指导缺口

1. 有平台指引，但散落在构建器、任务书、实验规则、工具描述和运行反馈中。规则侧重权限、落盘、测试与诚实报告，缺少简洁的多实现者协作工作方法。
2. 调度和执行者都拿到15,371字符的完整需求与PRD正文；所有执行者都被要求先读完整确认UX。保真规则有价值，但当前没有按职责分配必要上下文，容易重复阅读。
3. 不含语音/模型功能的待办项目，仍收到语音、HTTP模型接入及无关组件的指导。它们属于通用段无条件拼入，并非本产品新增需求。
4. `experiment_plan`已登记完整instruction，派工包装器会自行取出正文；`delegate_agent`又允许可选task并把它追加为“调度反馈”。本轮两名执行者的反馈开头和主体重新描述了对应实现任务，形成近似重复：worker-1登记段约4,312字符、反馈后缀约4,402字符；worker-2约2,950与3,063字符。不是完全相同的字节串，不能说同一字符串重复两次。
5. 快速任务书中仍写脚本每次≤90s、最多12次，本轮真实脚本次数上限为64；说明与运行资源存在过期差异。预算应由实际资源配置生成，避免多个事实来源。
6. 实验运行协议明确最多2名实现者、最多16任务、首次派工后锁计划、整轮结束才释放跨执行者依赖，但没有简洁说明“已有两名后应续接而非再创建”等操作方法。本轮发生过人数与依赖拒绝。
7. V的遗漏不能只靠提示词修复：原生quick会跳过desktop-verify。共同V阶段是否运行，必须由宿主路由和真实请求证据保证。

## 平台指引的建议结构（未启用）

建议把现有规则整理成短的按角色工作指引，并让详细规范按需读取，避免在原有system后再堆一份总说明。

- 平台事实：当前模式、环境资格、现成入口与协议、确认文档路径、工具能力和真实剩余资源，由宿主生成。
- 调度职责：确定任务目标、接口、依赖、写入范围和验收引用；实现细节交给对应执行者。独立任务满足边界后尽早派出，不要求先写成方法级实现方案。
- 执行职责：读取自己任务关联的需求/规则与接口事实，共同业务约束始终可见；需要时读取完整权威文档。按实际证据实现与汇报。
- 协作协议：任务只登记一次，派工引用task_ids，补充反馈仅承载新增事实；说明执行者复用、依赖释放粒度、写入冲突与集成归属。
- 收口协议：引用新鲜真实证据、补缺失验证、报告未验项；V作为明确的宿主阶段，不能用“配置了模型”代替实际执行。

这是当前提示词审阅与下一版设计建议，未改动任何组的运行条件。若用于后续比较，应登记新协议版本及新的共同输入/运行指纹；本轮52分48秒与103次请求保留原样。
