## 查清的原因

- **S1**：已有业务代码原本即可通过独立验收；新会话补齐交付说明并重做验证，完成原生收口。不能据此算一次从零开发成功。
- **S2**：原产物 F-016 验证指纹抄错一个字符；旧反馈只说“版本不一致”，自动修复误改场景名。新反馈明确给出当前值后，模型修正登记。同时复现并修复旧的隐藏定时器提前收起新反馈的问题，独立导入场景由失败变为通过。
- **G12**：首次恢复完成主要界面后用尽同一执行会话的 12 次脚本额度；文件选择错误调用模块方法。扩大资源段后修正窗口实例 API 并正常交付，外部验收又发现：非法日期 `2026-02-30` 的备份被接受，磁盘任务从 3 条增至 5 条，随后列表刷新报错；错误提示约 227 毫秒即被旧定时器隐藏。该诊断未修改模型源码，使用隔离测试数据。Pro 定向修复后，非法日期、缺字段、冲突整份拒绝，正确合并、重复幂等和重启差分均通过。
- **G22**：常规 GLM API 明确返回 HTTP 429、错误码 1113、“余额不足或无可用资源包”。传输层把它当普通限流重试三次，形成未知用量预留，继而本地保护线阻断。实际窗口仍是提示 `no api: list_items` 的通用骨架，因此 Q 保留 null，不能填成 0 或成功。
- **Pro 新任务 P1**：API 调用及 high 条件正常，但生成应用没有正确检查/解包桥接错误回包，重复名称、项目删除保护、非法日期被界面错误呈现为成功；文件选择返回的路径序列又直接传给要求字符串的业务方法，真实导出未创建文件，界面仍显示 `undefined` 成功信息。五个独立场景失败是产品质量结果，不是供应商调用格式失败。P1 的原始 9/14 保留为有效对照结果，未反复重抽到成功才报告。

## 验收方法与校准

所有业务变更经真实 pywebview 窗口的渲染控件、DOM 输入/变化/点击事件发生，核对列表、导出文件、稳定 ID 和实际重启。需要选择文件的样本使用真实 Windows 文件对话框；路径输入与确认限制在该测试进程及其子进程窗口，不使用业务 API 直写替代导入/导出。窗口截图仅按自有 PID 捕获。这不是完整的鼠标、键盘或可用性评估。

P1 暴露了适配器的一处弱检查：全页面包含“日期”也可能来自任务名“无日期”。首次因此在错误关闭表单后找不到取消按钮，保持 pending；第二次明确检查非法输入后表单保留及错误反馈，实测失败。旧 pending 与修正来源均保留。对 S1、S2、RP12 的既有 14/14 原始观察作只读复核，两个非法日期都确有明确错误文本和表单保留，不靠任务标题判通过；见 `calendar-observation-audit-20261016.json`。

原生门禁通过与外部功能通过分别记录。P1 与 G12 的“交付”不被当成外部全通过，也不采用模型自行编写的日志作为独立评分。
